# Пример 030: проведение и сохранённые проводки

Для закреплённого стенда `base-for-test`, 1С 7.70.027 и зарегистрированного
`copy_path` задачи 021. Данные создаются только на свежей копии каждого `run`.
Нужны checkout harness77, установленный пакет и локальные файлы стенда.
Генератор задаёт 240 секунд на открытие базы, 120 на расчёт и 600 на весь сеанс:
в первых пробах этого стенда открытие иногда превышало прежние 120 секунд.
Пределы можно переопределить обычными параметрами CLI `run`/`suite`.

Сценарий создаёт «Готовую продукцию» с двумя строками товара. В форме меняет
количество первой строки с 1 на 3, проверяет сумму 30, записывает и закрывает
документ. `fixture_post = true` добавляет `post` после шагов: новый объект читает
записанный документ и вызывает `Провести(1)`. Ещё один объект проверяет сохранённый
признак проведения. Тест `document-post` ожидает `1|1`.

`fixture_verify` создаёт новую `Операцию`, находит её **по ссылке документа**,
читает все проводки, проверяет ссылку товара и возвращает признак проведения,
число проводок и счета/количества/суммы каждой. Ожидается
`1|2|1|43>40:3:30;43>40:2:40;`. Проверка обнаружит лишнюю проводку, неверную
ссылку, счёт, количество или сумму; один успешный `Провести` её не заменяет.

Из корня checkout:

```powershell
python examples/document-posting/prepare.py --stand .local/stage21-native/stand.toml --output .local/stage30-example
python -m harness77 suite --suite .local/stage30-example/suite.toml --stand .local/stage30-example/stand.toml --output-root .artifacts/suites
```

Генератор создаёт три профиля и два набора. `suite.toml` выполняет успех,
ожидаемый отказ, повторный успех; ожидаются код 0 и три прошедших testcase JUnit.
В варианте `refused` **только на копии** в модуль проведения добавлены сообщение
«Harness77 отказ 030», `СтатусВозврата(0)` и выход. `post` ожидается `failed`
со значением `0|0`, а проверка отсутствия проводок — `passed`, `0|0|1|`.

```powershell
python -m harness77 suite --suite .local/stage30-example/suite-failure.toml --stand .local/stage30-example/stand.toml --output-root .artifacts/suites
```

Во втором наборе `wrong` намеренно ждёт количество 999; проведение проходит,
проверка проводок падает, следующий сценарий выполняется. Ожидаются код 1,
один `failure` и один успех. Отдельный профиль запускается обычным `run`:

```powershell
python -m harness77 run --project .local/stage30-example/success/project.toml --stand .local/stage30-example/stand.toml --output-root .artifacts/runs
```

В дочернем `platform-result.json` операция `post` содержит `posting.returned`,
`posting.posted`, ошибки и диагностики; `verify.value` содержит прочитанные проводки.
Полные сообщения 1С находятся в `native/Протоколы проверки/post.txt`.
`run.json` и общий `suite.json` связывают результаты, а `junit.xml` отражает итог
каждого сценария с учётом объявленных отрицательных ожиданий.

Первый охват — бухгалтерские проводки одного вида документа, проведение через
OLE после записи формы. Это не проверка кнопки проведения, движений регистров,
перепроведения или отмены проведения. `fixture_verify` — обычный доверенный код
теста 1С, как и `fixture_setup`; произвольные изменения рабочей базы не нужны.
