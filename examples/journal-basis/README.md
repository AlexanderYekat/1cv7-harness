# Пример 040: ввод документа на основании из журнала

Закреплённый DBF-стенд `base-for-test`, 1С 7.70.027, установленный 1С++.
Нужен checkout: launcher находится в `research/forms`. Каждый запуск использует
новую проверенную копию базы; модули, диалоги и метаданные конфигурации исходные.

Пара — «Расходная накладная» → «Приходный кассовый ордер». Подготовка создаёт
три непроведённые накладные и тестовые товар, контрагента, договор, кассу,
подразделение. В каждой накладной две строки 1 × 10 и 2 × 20, всего 50,
НДС/НП — ноль. Сохраняются ссылки, даты, номера, исходное число документов
обоих видов и общее число документов всех видов. Независимое чтение проверяет поля, строки, признаки и проводки
основания и двух соседей до UI. Проведение основания не требуется этой парой.

```toml
form_object = "Документ.ПриходныйОрдер"
fixture_mode = "journal_existing"
journal_form = "Журнал.Товары.ФормаСписка.ФормаСписка"
steps = [
    { journal_period = true, start = "2026-07-31", end = "2026-08-01" },
    { find_document = true, limit = 100, open = false },
    { journal_basis = "Прих.касс.орд. (Приходный кассовый ордер)", source = "РасходнаяНакладная", link = "ДокументОснование", caption_control = "ндСфетФактураУжеСформирована", caption_text = "Не требуется", return_journal = "Журнал.Касса.ФормаСписка.ФормаСписка" },
]
```

Полный профиль — [scenario.toml](scenario.toml). `form_object` задаёт вид
результата, `source` — вид подготовленного основания. `link` должен быть
реквизитом результата документного типа, принимающим вид основания; это
проверяется по метаданным копии до запуска 1С.

Штатный период и End/Up выбирают точную ссылку без Enter. Перед командой
`journal_basis` снова проверяет ссылку/HWND и сохранённые данные всех трёх
накладных. Команда `0x806D` «Ввести на основании» (Alt+F9) установлена по
ресурсам 135/253 `1crcrus.dll` и проверяется в живом меню своего окна.
Выбор вида требует единственного полного совпадения с текстом списка;
неизвестный или неоднозначный вид не выбирается, окно отменяется.

Активный контекст подтверждает новый незаписанный ордер, новый HWND,
`ДокументОснование`, исходный сформированный комментарий и отсутствие
проведения/пометки. Дата наследуется от накладной; номер выдаёт штатная форма.
До записи сохранённых ордеров больше не становится. Сама форма заполняет
сумму 50, кассу, подразделение и аналитику контрагента/договора.

Через UI меняется комментарий на «Harness77 основание 040». «Записать» и
`created` подтверждают новую сохранённую ссылку, отличную от основания,
прежние дату/номер, сумму и отсутствие проводок. «ОК» вызывает исходную
`ПровестиМоя()` и закрывает ордер без вопроса о проведении. Автоматически
открывается «Касса»: её ожидаемое описание задаёт `return_journal`.
Проверяются геометрия, подписи, новый HWND своего PID/TID и активный
контекст журнала с точной сохранённой ссылкой на ордер.

`reopen` требует уничтожения прежних окон и открывает ту же сохранённую
ссылку; контроллер вновь сравнивает `ДокументОснование` с исходной ссылкой.
Независимое чтение подтверждает ровно один новый ордер, сумму 50, одну
проводку Дт 50.1 Кт 62.1 с суммой 50, количеством 0 и ожидаемой аналитикой.
Общий счётчик всех документов также должен вырасти ровно на один: это
исключает создание дополнительного счёта-фактуры исходным обработчиком «ОК».
Основание и соседи, их поля, строки, даты, номера, признаки и проводки
сохраняются. Программного создания, записи и проведения результата нет.

У этой формы надпись о счёте-фактуре меняется исходным модулем. Для нового
ордера со счётом 62.1 ожидается «Не требуется»; для повторно открытого
проведённого — исходное «Счет-факутра ещё не сформирована». Ожидания заданы
в сценарии через `caption_control`/`caption_text` для двух состояний. Они
меняют только проверяемое описание STATIC-надписи; конфигурация сохраняется.
Остальные подписи и геометрия проверяются полностью.

```powershell
python -X utf8 examples/journal-basis/prepare.py --stand .local/s39b/stand.toml --output .local/journal040
python -m harness77 suite --suite .local/journal040/suite.toml --stand .local/journal040/stand.toml --output-root .artifacts/suites/journal040-main
python -m harness77 suite --suite .local/journal040/suite-failure.toml --stand .local/journal040/stand.toml --output-root .artifacts/suites/journal040-negative
python -m harness77 suite --suite .local/journal040/suite-kind-failure.toml --stand .local/journal040/stand.toml --output-root .artifacts/suites/journal040-kind
python -m harness77 suite --suite .local/journal040/suite-limit-failure.toml --stand .local/journal040/stand.toml --output-root .artifacts/suites/journal040-limit
```

Основной набор: успех, повтор на новой копии, отмена выбора вида и отказ от
сохранения изменённого ордера. Отрицательные наборы дают ровно один failure
JSON/JUnit и успешное продолжение: неверная сумма проводки в ожидании,
отсутствующий вид и недостаточный предел поиска. При пределе 1 не отправляются
Enter и команда ввода на основании. `no-copy/project.toml` блокируется до 1С.

`scripts/verify_journal_basis77.py` принимает четыре `--suite UUID_DIR`,
`--blocked-run UUID_DIR`, `--disabled-run UUID_DIR`, `--output NEW_JSON`; `--excluded-run`, `--test-log`,
`--regression-report`, `--control-report` связывают остальные свидетельства.
Он перечитывает сырые ответы/протоколы, команды/окна, выбор вида, ссылки,
данные/проводки, JSON/JUnit, хеши и очистку. `verify_journal_basis_controls77.py`
проверяет намеренные искажения, включая отдельную временную копию сырого ответа.

Пара «Готовая продукция» → «Сторно» оказалась недоступной: наличие обработчика
`ВводНаОсновании` не даёт разрешённой связи в метаданных. Нативный отказ
до отправки команды сохранён отдельно. Другие пары, журналы и SQL не проверены.
