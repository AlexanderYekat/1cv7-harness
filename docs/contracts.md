# Контракты harness77 0.1

Реализованы операции: `lint`, `compiler-protocol`, `extract`, `build`, `run`, `catalog`,
`form-extract`, `triage`, `visual`.
`harness77 --version` и `python -m harness77 --version` выводят версию пакета.
У каждой операции есть `--help`. Пути разрешаются относительно CWD вызывающего;
пакет, словарь и зависимости от CWD не зависят. Stdout/stderr CLI — UTF-8.

## Статический анализ и импорт протокола

`harness77 lint PATH [--globals FILE] [--allow NAME] [--dialog FORM.ert|FORM.json] [--strict]
[--format text|json] [--output FILE]` сохраняет прежний контракт lint77:
JSON `schema_version=1`, `tool=lint77`, диагностические коды L77xx.
Коды выхода: 0 — нет ошибок (предупреждения возможны), 1 — ошибки кода,
2 — ошибка входа/операции. Отчёт не подтверждает компиляцию. `--output`
сохраняет прежнюю перезапись отчёта, но отклоняет совпадение с входом/контекстом,
включая hardlink; отчёт линтера пока не публикуется атомарно.

Версия lint 0.2.0 ([задача 005](tasks/005-kudir-rules.md)) добавляет коды, уровни
которых установлены пробами на 1С 7.70.027:
L7708 — зарезервированное имя (ключевое слово или одна из 51 встроенной функции
компилятора) объявлено параметром, `Перем`, счётчиком `Для` или присваиванием, error;
L7709 — у `.Метод(…)` аргументов больше, чем в любой сигнатуре каталога, warning;
L7710 — строка длиннее 500 символов (предел Конфигуратора), warning;
L7711 — чтение необъявленного к этому месту имени, warning. L7711 проверяется
только при известном диалоге: модуль ERT или текст с `--dialog` (ERT или описание
формы JSON, задача 008). `--allow` добавляет
имя глобального контекста конфигурации; `--strict` делает L7709/L7711 ошибками.
В отчёте добавлены `catalog` (версия платформы и хеши источников каталога)
и `form_context_modules`; прежние поля и коды не менялись.

## Каталог платформы

`harness77 catalog --als BIN/1cv7Lang.als --strings BIN/1crcrus.dll --output NEW.json`
строит каталог имён установленной 7.7: записи справочника (вид, рус./англ. имя,
папка, компоненты, число параметров каждой сигнатуры, `max_params=null` — без
предела), пары `English,Русское` и блок `reserved` из ресурсов. Описания и шаблоны
не копируются. Выход только новый, повтор на тех же байтах даёт те же байты.
Код 0 — JSON с путём, размером и SHA-256 результата, версией и хешами источников
в stdout; код 2 — `blocked` в stderr. Пакет содержит каталог 7.70.027
(`catalog77.json`) и список глобальных имён стенда (`lint77-globals.json`).
Задача 009 добавила раздел `messages`: номер строки ресурса, текст и блок
(`compile` — 72, `runtime` — 23) сообщений языка из `1crcrus.dll`; блоки
определяются по опорным строкам, другая раскладка — `blocked`. Прежние разделы
не изменились.

`harness77 compiler-protocol INPUT [--encoding auto|utf-8|cp1251]
[--format json] [--output OUTPUT]` сохраняет [контракт 1.1](tasks/001-compiler-protocol.md).
Код 1 и `failed` означают пригодный протокол ошибок; код 2 и `blocked` —
непригодный вход. Ошибки файлов/публикации дают код 2 и сообщение stderr.
Импорт никогда не выдаёт `passed`. Он не связывает старый протокол с новой ERT.

## Корень и каскад — команда `triage` ([задача 009](tasks/009-protocol-root-cascade.md))

`harness77 triage PROTOCOL [--source МОДУЛЬ.txt | --ert ФАЙЛ.ert] [--encoding auto|utf-8|cp1251]
[--output NEW.json]` размечает протокол Конфигуратора (с завершающим маркером) или
нативный протокол загрузки (`native/Протоколы проверки/*.txt`, без маркера).
JSON `schema_version=1`, `operation=triage`: `protocol` (имя, SHA-256, вид, кодировка),
`module` (`used`, `verified`, причина отказа, вид и SHA-256 источника), `catalog`,
`summary`, `rules` (код → нативные пробы-основания), `diagnostics`, `issues`,
`limitations`. Каждая диагностика сохраняет поля разбора и получает `index`,
`message_id`, `argument`, `role` (`root`|`cascade`|`link`|`unknown`), `cause`
(`index` корня для каскада), `confidence` (`high`|`medium`|`low`), `rule` и
`explanation`. `summary`: число диагностик по ролям, `complete` (нет признаков
остановки компиляции), `compiled_through_line`, `to_fix` (корни и `link`).
Диагностики не удаляются и не переставляются. Модуль используется, только если
строки протокола совпадают с ним без учёта пробелов по краям. Код 1 — `failed`
(протокол ошибок размечен), код 2 — `blocked` (непригодный протокол, существующий
выход, ошибка файла). `--output` — только новый файл, без него — stdout.
Разметка — подсказка: после исправления корней нужна новая компиляция.

## Сборка и извлечение

```text
harness77 extract INPUT.ert --output NEW.txt
harness77 build --template INPUT.ert --source MODULE.1s --output NEW.ert
                [--encoding auto|utf-8|cp1251|utf-16] [--legacy-normalize]
                [--form FORM.json [--metadata 1Cv7.MD]]
harness77 form-extract INPUT.ert --output NEW.json [--metadata 1Cv7.MD]
```

Выход обязателен и должен отсутствовать. Родительский каталог должен существовать.
Существующий файл, каталог, hardlink или symlink не перезаписывается. Входы
перечитываются перед публикацией; обнаруженное изменение останавливает операцию.
Применяются CFB v3 и один поток `MD Programm text`. Контейнеры с несколькими
модулями, включая полную MD, не являются входом сборки.

Извлечение сохраняет текст в UTF-8 без BOM, оставляя исходные переводы строк.
Сборка использует CP1251/CRLF. `auto`: UTF-16 с BOM, затем валидный UTF-8,
иначе CP1251. Автоопределение неоднозначно для части байтов; если кодировка
известна, следует задавать её явно. NUL и некодируемые символы отклоняются.
По умолчанию нет замен символов, в том числе представимых тире и кавычек.
`--legacy-normalize` разрешает прежние замены devtools и перечисляет каждую
в `normalizations`; неизвестный непредставимый символ всё равно даёт отказ.

Запись: подготовка → сверка текста/потоков/каталога → временный файл рядом
с выходом → flush/fsync → повторное чтение и сверка → публикация через hardlink
без замены существующего файла → удаление временного имени. Неподдерживаемая
файловой системой операция даёт отказ, обходного копирования нет. Сохраняется
содержимое посторонних потоков и метаданные записей каталога; физическое
размещение секторов и размеры модульного/root потоков меняются.

Код 0: JSON в stdout, `schema_version=1`, `tool=harness77`, `status=passed`.
`scope` равен `ert_container_build` или `ert_module_extract`.
У результата есть путь, размер и SHA-256; входы также имеют SHA-256.
Сборка дополнительно сообщает выбранную кодировку, хеш текста CP1251,
сохранённые потоки и выполненные сверки. `platform_checked=false` всегда.

Код 2: JSON `blocked` в stderr и сообщение об ошибке; неверные аргументы
дают штатный usage argparse и код 2. При ошибке очистки/stdout файл уже может
быть опубликован: существование файла само по себе не означает успех команды.
Операции не обеспечивают защиту от параллельной враждебной подмены родительских
каталогов; входы и каталог результата должны принадлежать текущей работе.

### Описание формы ([задачи 008](tasks/008-form-description.md), [011](tasks/011-form-elements.md) и [012](tasks/012-reference-fields.md))

`form-extract` пишет описание формы ERT — JSON UTF-8 без BOM, LF:
`schema="harness77-form"`, `schema_version=3`, `template_dialog_sha256` (SHA-256
текста диалога шаблона в CP1251), `form` (`caption`, `width`, `height`, `layers`)
и `controls` в порядке формы (`id`, `class`, `caption`, `x`, `y`, `width`,
`height`, `formula`, `identifier`, `layer` и необязательный `type`). Координаты —
числа формы без пересчёта. `type` — тип реквизита (поля 14–16 записи):
`{"kind": "string"|"number"|"date"|"undefined"|"reference"|"other", "length",
"precision", "code"}`; пишется, если тип не «неопределённый с нулями», нулевые
длина и точность опускаются, `code` (исходный код типа) — только у `other`.
Ссылочный тип (поля 14 и 17 — код и номер объекта метаданных, длина и точность 0) —
`{"kind": "reference", "object": "<имя>"}`: `Справочник`, `Справочник.<вид>`,
`Документ`, `Документ.<вид>`, `Перечисление.<вид>`, `Счет`, `Счет.<план счетов>`,
`ВидСубконто`, `ПланСчетов`. «Любой» (номер 0) пишется именем всегда; вид —
именем по `1Cv7.MD` из `--metadata`, без него — по копии метаданных, которую
несёт сама ERT (поток `Main MetaData Stream`); номера, которого там нет, —
номером: `{"kind": "reference", "code": "B", "object_id": 133}`. Описания версий 1
(без `type`) и 2 (ссылочные — `other` с кодом) принимаются и собирают то же самое.
Выход и отказы — как у `extract`; `scope=ert_form_extract`, в отчёте также
`template_dialog_sha256`, число элементов, `names_from` (`metadata`|`ert`),
`references_by_number` (поля, вид которых записан номером), `ert_metadata`
(SHA-256 потока копии, имя конфигурации) и с `--metadata` — `metadata` (путь,
SHA-256 файла, имя конфигурации). Неизвестный или неканонический
диалог (не восстановимый байт в байт), повреждённый контейнер и контейнер без
модуля дают код 2.

`build --form` собирает модуль и диалог за один раз. Описание обязано быть
сделано для этого шаблона (хеш диалога). Остальные поля и разделы диалога
берутся из шаблона, поэтому описание без правок даёт диалог байт в байт.
Поддерживаются: заголовок и размер формы; у существующих элементов — подпись,
x, y, ширина, высота, идентификатор, слой, формула кнопки или поля; новые
элементы в конце списка (ID — только следующий по порядку: 1С нумерует записи
с 4152 подряд и раздаёт ID окон по их порядку; остальные поля — самая частая
запись класса и типа в корпусе):

| Класс | Элемент | Обязательно | `type` | Формула |
|---|---|---|---|---|
| `BUTTON` | кнопка | `caption`, `formula` | — | вызов `Имя(…)` |
| `STATIC` | надпись | `caption` | — | — |
| `1CGROUPBOX` | рамка группы | `caption` | — | — |
| `1CEDIT` | поле строки | `identifier`, `type` | `string`, длина ≥ 0 (0 — без ограничения) | пусто или `Имя(…)` |
| `BMASKED` | поле числа или даты | `identifier`, `type` | `number` (длина ≥ 1, 0 ≤ точность < длина) или `date` | пусто или `Имя(…)` |
| `CHECKBOX` | флажок | `caption`, `identifier` | `number` длины 1 (по умолчанию) | пусто или `Имя(…)` |
| `BMASKED` | поле ссылочного типа (012) | `identifier`, `type` | `reference` по имени, кроме `ПланСчетов` | пусто или `Имя(…)` |

**Ссылочные типы (задача 012).** Номер вида принадлежит конфигурации, поэтому
имя вида нового поля переводится в номер по `1Cv7.MD` целевой базы (`--metadata`;
регистр букв не важен). Неизвестное имя или раздел, вид у `ВидСубконто`/`ПланСчетов`,
`Перечисление` без вида, номер вместо имени и имя вида без `--metadata` у нового
поля дают отказ. У существующего поля тип не меняется: имя сравнивается с номером
шаблона по метаданным сборки, без них — по копии метаданных шаблона; другой номер —
отказ (шаблон или описание другой конфигурации). **Копия метаданных ERT.** 1С ищет
вид поля в копии, которую несёт ERT (задача 012, R1–R1c): если копия шаблона уже
содержит новый вид с тем же номером и именем, что в базе, она остаётся (`kept`);
иначе сборка заменяет её потоком `Main MetaData Stream` целевой базы с байтом NUL
в конце (`replaced`) — только если прежние поля вида шаблона означают в базе те же
объекты, иначе отказ; шаблон без копии — отказ. Отчёт сборки содержит `form.metadata`
(путь, SHA-256 файла `1Cv7.MD`, имя конфигурации), `form.ert_metadata` (`action`,
SHA-256 и конфигурация копии до и после замены), а у нового ссылочного поля
в `changes` — имя, код и номер; заменённая копия не входит в `preserved_streams`.
`--metadata` без `--form` — отказ.

Формула — вызов процедуры модуля или глобальной функции каталога. Проверяется
только заданное описанием: новый или сдвинутый элемент — в клиентской области
`[4, W − 3] × [15, H − 3]` единиц формы (измерено в задаче 008) и без новых
наложений на элементы своего слоя (наложения шаблона не проверяются; рамка
группы может целиком содержать элемент); новый или изменённый идентификатор —
допустимое и уникальное имя, не совпадающее с процедурой, функцией или
переменной `Перем` модуля (1С такой модуль принимает, но `Перем` перекрывает
реквизит формы, задача 011); слой — из формы. Удаление, перестановка, смена
ID/класса или типа существующего элемента, изменение слоёв, другие классы
новых элементов, тип или формула не своего класса, неизвестные свойства
и неверные типы JSON дают отказ (код 2). Отчёт сборки дополняется `form` (путь
и SHA-256 описания, хеши диалога до и после, `dialog_unchanged`, `changes`)
и `verification.dialog`; поток диалога не входит в `preserved_streams`. Работу
формы в 1С это не подтверждает: она проверена нативно для одного шаблона
(задачи 008, 010, 011).

## Полный цикл — команда `run`

```text
harness77 run --project PROJECT.toml --stand STAND.toml [--output-root DIR]
              [--open-timeout-s N] [--calculation-timeout-s N] [--cancel-timeout-s N]
              [--shutdown-timeout-s N] [--total-timeout-s N] [--run-id ID]
```

Связывает статику (`lint77`), сборку (`artifacts.build`), проверку платформой и
тесты в один запуск. Статика проверяет текст модуля в контексте диалога шаблона
сборки (L7711) или описания формы, если в профиле задано `[build] form`; оно же
передаётся сборке. Профиль проекта задаёт идентификатор, шаблон и исходник ERT,
контекст анализа, тесты (`[[platform.tests]]` с `name`, `command`, `expect`,
необязательным `expect_value`) и сроки. Профиль стенда задаёт backend
(`native`|`simulation`|`import`), машинные пути, выбранную существующую базу,
пользователя и закреплённые хеши. Пароли в профиле не хранятся. Относительные пути
разрешаются от каталога профиля. Полное описание — [задание этапа 4](tasks/004-full-cycle.md).

Ссылочные поля формы (задача 012): `[build] metadata` — `1Cv7.MD` для номеров
видов; если не задано, а описание называет вид (`Справочник.Контрагенты`),
сборка берёт `1Cv7.MD` базы стенда. Этап `build` записывает `form.metadata`
(SHA-256, имя конфигурации, источник `project`|`stand`). Если ERT собрана по
метаданным, а `1Cv7.MD` базы стенда другой, `platform_check` — `blocked`
(`metadata_mismatch`), 1С не запускается.

Каждый запуск получает новый `run_id` и каталог `<output-root>/<run_id>`. Входы,
шаблон, собранная ERT, платформенные свидетельства и тесты связаны по `run_id` и
SHA-256; проверяется именно ERT этого запуска. Старый, чужой, частичный или
отсутствующий результат успехом не считается.

Сроки (раздел 8.5): пять конечных положительных значений `open/calculation/cancel/
shutdown/total`; общий покрывает сумму фаз; несогласованные отклоняются до старта.
Источник — CLI > проект > стенд; умолчаний нет, прототипные 30/145 с не
применяются. Срок `open` покрывает и переиндексацию, которую 1С выполняет при
открытии базы после прерванного сеанса: по наблюдению владельца на некоторых
базах она идёт час и больше. Нормальный запуск срок не ждёт, поэтому `open`
задаётся по худшему случаю для своей базы; общий срок его включает. Нативно каждая
команда обработки получает срок `calculation`. Задача 007: необязательный
`reindex_timeout_s` (CLI `--reindex-timeout-s`) добавляется к `open` только если
стенд до запуска видит след прерванного сеанса (`1Cv7.LCK`, который никто не держит);
общий срок покрывает `open + reindex + calculation + cancel + shutdown`. Открытие —
от начала сеанса до первой команды обработки — ограничено своим сроком
(`timeout_phase=open`); в отчёте этапа `platform_check` поле `open`: срок,
ожидание переиндексации, след до и после, время открытия. Эффективные значения и источник — в отчёте. Часы внешние монотонные;
срок фазы абсолютен, тишина и прогресс его не меняют.

Отчёт `run.json` (`schema_version=1`, `tool=harness77`, `operation=run`): входы и
проверенный артефакт с хешами; идентификация платформы и базы без секретов и
`platform_checked`; этапы `static`/`build`/`platform_check`/`tests` со статусом,
длительностью, диагностиками и причиной неполноты; `deadlines` с источником;
`result_files` с путём, размером, SHA-256 и `complete`; `cancelled`,
`timeout_phase`, `reason`; `shutdown` и `screenshots`. Большие результаты —
файлы каталога запуска; размер и SHA-256 считаются потоком, полная копия файла
в памяти не держится.

Задача 009: если загрузка дала диагностики, этап `platform_check` размечает их
по модулю собранной в этом запуске ERT — поля `triage` выше в `diagnostics`,
`summary`, `module`, `rules`, `catalog` в `triage`. `load.diagnostics` остаются
неразмеченными. Нативный launcher дополнительно передаёт `column` и `source_line`.

Задача 006 ([задание](tasks/006-long-native-report.md)): `[platform.parameters]`
профиля проекта — плоские строки, числа и логические значения — передаются
launcher стенда вместе с командами объявленных тестов (`--parameters-json`,
`--commands-json`) и попадают в `inputs` отчёта. Файл результата может указывать
свою операцию (`operation`): отсутствующий или неполный файл не даёт успеха, если
его операция прошла или не указана; файл операции, которая уже отказала, — её
свидетельство, итог решает тест (так проверяется ожидаемый сбой записи).

Статусы этапа: `passed`/`failed`/`blocked`/`skipped`. Коды выхода: `0` — все
обязательные этапы прошли (включая проверенный ожидаемый отрицательный тест);
`1` — дефект проверяемого кода или провал теста (ошибка компиляции/исполнения,
несовпадение ожидания); `2` — ошибка входа/инфраструктуры или неполный
обязательный результат (недоступная база, тайм-аут, отмена `cancelled`,
`artifact_write_error`, `shutdown_error`, старый/частичный/чужой результат).
При совпадении дефекта и инфраструктуры приоритет у `2`. Пользовательская отмена
(Ctrl+C, а в Windows и Ctrl+Break) запускает ограниченное ожидание возврата и
завершения своего сеанса; принудительное завершение допускается только для
доказанно собственного сеанса и явно отражается в результате. Нативный launcher
работает в своей группе процессов и узнаёт об отмене по файлу `cancel` каталога
запуска; если за сроки `cancel` + `shutdown` и 10 с запаса он не вернулся, его
процесс снимается и результат помечается принудительным. Этап ниже по конвейеру, не выполненный
из-за отказа выше, помечается `skipped` и итог не повышает.

Backends: `simulation` и `import` всегда `platform_checked=false` и автоматической
проверкой платформы не являются. `native` вызывает launcher стенда (принятый
`research/platform77/stage4_launcher77.py`), доказывает владение процессом до
Initialize, работает на отдельном desktop, проверяет завершение и не выводит
успех из исчезновения процесса. Нативная приёмка короткого цикла выполнена;
реальный долгий прикладной отчёт — отдельный прогон (см.
[приёмку](tasks/004-full-cycle-acceptance.md)). Подробные критерия долгих
расчётов — [раздел 8.5 ТЗ](restructuring-spec.md#85-долгие-расчёты-и-большие-отчёты).

## Визуальные тесты формы — `[visual]` и команда `visual` ([задача 010](tasks/010-visual-form-tests.md))

Профиль проекта может объявить сравнение снимков формы с утверждёнными эталонами:

```toml
[visual]
baselines = "baselines"          # каталог эталонов, от каталога профиля

[[visual.checks]]
name = "form-open"               # латиница, цифры, . _ -; имя файлов эталона
state = "open"                   # open — сразу после открытия; clicked — после нажатия click_id
window = "form"                  # form — окно с заголовком; dialog — внутренняя часть
channel_tolerance = 0            # допустимая разница канала 0…255
max_diff_pixels = 0              # сколько пикселей может отличаться
mask_caret = true                # маскировать мигающий курсор ввода
masks = [{x = 0, y = 0, width = 10, height = 10, reason = "часы"}]
```

Неизвестные ключи, повтор имени, маска без причины — ошибка профиля. С `[visual]`
`run` запрашивает у стенда снимки (`--captures-json` launcher, список
`{state, window}`) и после `tests` выполняет обязательный этап `visual`. Этап
`platform_check` получает `captures`: состояние, окно, файл (путь, SHA-256,
`complete`; нативно перепроверяется с диска), размер, среда, курсор, устойчивость,
число попыток или `error`. Каждая проверка сравнивает снимок с эталоном по пикселям
вне масок профиля и курсора (его прямоугольник из снимка и из записи эталона);
провал — разный размер или больше `max_diff_pixels` пикселей с разницей канала
больше `channel_tolerance`. Строка проверки: `status`, `reason`, `size`,
`diff_pixels`, `masked_pixels`, `max_channel_delta`, `diff_box`, `masks`,
`baseline`, `capture`, `files`; в каталоге запуска `visual/<name>/` — `baseline.png`,
`actual.png`, `diff.png` (снимок светло-серым, различия красным, маски синим),
`result.json`.

`blocked` вместо сравнения: нет снимка, ошибка или неустойчивость снимка, нет
эталона, изображение эталона не совпадает с записью, запись для другого состояния
или окна, среда снимка не совпадает со средой эталона или не записана
(`environment_issues`). Среда — `platform_version`, `configuration` (SHA-256
`1Cv7.MD`), `windows_build`, `system_dpi`, `window_dpi`, `theme`, `font`, `locale`,
`capture`. Если платформа не прошла, этап `skipped`. Коды выхода общие: провал
сравнения — `1`, блокировка — `2`.

Эталоны пишет только явное утверждение; `run` их не создаёт и не меняет:

```text
harness77 visual approve --project PROJECT.toml --run RUN_DIR --by WHO [--check NAME ...] [--replace]
harness77 visual compare BASELINE.png ACTUAL.png --output NEW_DIR [--mask x,y,w,h ...]
                         [--channel-tolerance N] [--max-diff-pixels N]
```

`approve` берёт снимки запуска, прошедшего `platform_check`, и пишет
`<name>.png` и `<name>.json` (`harness77-visual-baseline` 1: изображение, среда,
курсор, кто и когда, `run_id`, хеши ERT и описания формы, статус тестов, маски
профиля, хеш заменённого эталона). Отказ без записи: запуск не прошёл платформу,
снимок отсутствует, неустойчив, изменён после запуска или без среды, имя проверки
неизвестно, эталон уже есть без `--replace`. Код `0` — утверждено, `2` — отказ.
`compare` сравнивает два PNG вне запуска: `0` совпали, `1` различаются, `2`
нечитаемый вход. Читаются PNG 8 бит без чересстрочности (серый, RGB, RGBA —
альфа-канал отбрасывается);
пишется RGB без служебных блоков, одинаковые пиксели дают одинаковые байты.

Нативные снимки делает `research/forms/form_launcher77.py`: показывает скрытое
главное окно своей 1С на своём desktop без активации, снимает `PrintWindow`
(`PW_RENDERFULLCONTENT`) серией до двух совпадающих вне курсора (до 6 попыток),
затем скрывает окно. Другой launcher на запрос снимков отвечает отказом.
