# Контракты harness77 0.1

Реализованы операции: `lint`, `compiler-protocol`, `extract`, `build`, `run`, `catalog`,
`form-extract`, `triage`, `visual`, `md-extract`, `md-build`; `mcp` — сервер MCP над ними.
`harness77 --version` и `python -m harness77 --version` выводят версию пакета.
У каждой операции есть `--help`. Пути разрешаются относительно CWD вызывающего;
пакет, словарь и зависимости от CWD не зависят. Stdout/stderr CLI — UTF-8.

## Статический анализ и импорт протокола

`harness77 lint PATH [--globals FILE] [--allow NAME] [--dialog FORM.ert|FORM.json]
[--metadata 1Cv7.MD] [--strict] [--format text|json] [--output FILE]` сохраняет прежний контракт lint77:
JSON `schema_version=1`, `tool=lint77`, диагностические коды L77xx.
Коды выхода: 0 — нет ошибок (предупреждения возможны), 1 — ошибки кода,
2 — ошибка входа/операции. Отчёт не подтверждает компиляцию. `--output`
сохраняет прежнюю перезапись отчёта, но отклоняет совпадение с входом/контекстом,
включая hardlink; отчёт линтера пока не публикуется атомарно.

Версия lint 0.2.0 ([задача 005](tasks/005-kudir-rules.md)) добавляет коды, уровни
которых установлены пробами на 1С 7.70.027:
L7708 — зарезервированное имя (ключевое слово или одна из 51 встроенной функции
компилятора) объявлено параметром, `Перем`, счётчиком `Для` или присваиванием, error;
L7709 — у `.Метод(…)` аргументов больше, чем в любой сигнатуре каталога, warning;
L7710 — строка длиннее 500 символов (предел Конфигуратора), warning;
L7711 — чтение необъявленного к этому месту имени, warning. L7711 проверяется
только при известном диалоге: модуль ERT или текст с `--dialog` (ERT или описание
формы JSON, задача 008). `--allow` добавляет
имя глобального контекста конфигурации; `--strict` делает L7709/L7711 ошибками.
В отчёте добавлены `catalog` (версия платформы и хеши источников каталога)
и `form_context_modules`; прежние поля и коды не менялись.

Версия lint 0.3.0 ([задача 018](tasks/018-metadata-names.md)) сверяет имена объектов
конфигурации в коде с метаданными базы, оба кода — warning (`--strict` — error):
L7712 — `Константа.<Имя>`, `Перечисление.<Вид>[.<Значение>]`, `ВидыСубконто.<Имя>`,
`ПланыСчетов.<Имя>`, которых нет в базе (имя перед `(` — метод атрибута, не проверяется);
L7713 — строка целиком `"<Тип>.<Вид>[.…|#…]"` в аргументе `СоздатьОбъект`, `ОткрытьФорму`,
`ОткрытьФормуМодально`, `ОткрытьПодбор`, `ПолучитьПустоеЗначение`, `ВвестиЗначение`,
`ПравоДоступа`, `НазначитьТип`, `НоваяКолонка`, `ВставитьКолонку`,
`УстановитьПараметрыКолонки`, `УстановитьРеквизитСправочника` (и их английских имён),
вида которой нет в базе; `Тип` — `Справочник`, `Элемент`, `Документ`, `Журнал` (журнал,
вид документа или `Подчиненные`), `Перечисление`, `Счет`, `ПланСчетов`, `Регистр`,
`Отчет`, `Обработка`. Сообщение говорит, что сделает 1С 7.70.027: модуль загружается,
строка прерывается при исполнении, а у функций типа колонки и пустого значения тип
молча остаётся без вида. Имена сравниваются без учёта регистра. Метаданные задаёт
`--metadata` (текстовые модули и ERT); модули самого `1Cv7.MD` сверяются с его
собственными метаданными; без метаданных правила молчат. Неизвестная запись разделов
`Consts`, `SbCnts`, `Documents`, `EnumList`, `Registers`, `ReportList`, `CalcVars`,
`Journalisters`, `Buh` → `Plans`/`SbKind` — код 2. В отчёте добавлены `metadata`
(путь, SHA-256 и имя конфигурации каждого контекста) и `metadata_context_modules`.

Версия lint 0.4.0 ([задача 019](tasks/019-attributes.md)) добавляет L7714, warning
(`--strict` — error): реквизит объекта, которого нет в метаданных базы. Объект — переменная,
каждое присваивание которой в своей области — `СоздатьОбъект("<Справочник|Документ|Регистр>.<Вид>")`
одного вида (локальная процедуры или тела программы; переменная модуля без `Экспорт`, присвоенная
только так во всех процедурах); не отслеживаются параметр, счётчик `Для`, реквизит формы,
глобальное имя и имя, переданное целиком в процедуру модуля. Проверяются `Имя.Реквизит` (чтение
и присваивание, не `Имя.Метод(`) и дальше по ссылочным реквизитам (`Док.Сотрудник.Должность`).
Реквизиты — справочника (`Params`), документа (шапка, табличная часть, общие `GenJrnlFldDef`),
регистра (измерения, ресурсы, реквизиты) и атрибуты класса из каталога платформы (`Код`,
`НомерДок`…, с английскими именами). Неизвестная запись реквизита или повтор имени у объекта —
код 2. L7712–L7714 молчат об имени внутри `Если … КонецЕсли`, условие которого (`Если` или
`ИначеЕсли`) проверяет его через `Метаданные.<Класс>("Имя")`, `.Реквизит("Имя")`,
`.РеквизитШапки`, `.РеквизитТабличнойЧасти`, `.Измерение`, `.Ресурс`, `.Значение`,
`Метаданные.ОбщийРеквизитДокумента("Имя")` — во всех ветках. L7713 не проверяет глобальные
функции, вызванные через точку (`V77.CreateObject(…)` — функция другой базы). В отчёте добавлены
`metadata_guarded` (сколько срабатываний опущено под проверкой `Метаданные`) и
`attributes_checked` (сколько обращений к реквизитам сверено); прежние поля и коды не менялись.

Версия lint 0.5.0 ([задача 020](tasks/020-md-module-context.md)) знает контекст модулей
`1Cv7.MD` и форм. Модуль `1Cv7.MD` привязан к объекту по номеру папки (`Document_<n>`,
`Transact_<n>` — документ; `Subconto_<n>`, `SubFolder_<n>` — справочник; `SubList_<n>`,
`Journal_<n>` — справочник или журнал по форме n в записи). L7711 проверяется в формах `1Cv7.MD`
(диалог — их `Dialog Stream`), в модулях документов и в глобальном модуле; формы операций,
проводок и плана счетов — без L7711. Реквизиты владельца (с общими реквизитами документа) и
атрибуты его класса (`Код`, `НомерДок`…; у журнала `ТекущийДокумент`) читаются без объявления;
ссылочный реквизит владельца начинает цепочку L7714. Контекст формы ERT и `1Cv7.MD` — элементы
диалога, столбцы списка (`Browser/Fixed`), `Таблица`, если форма перечисляет таблицы, и именованные
области таблицы, которую называет `Container.Profile` формы (`MoxelName`); таблица формы, которую
`lint` не может прочитать, — контекст неизвестен, L7711 молчит. `'…'` в пределах строки — литерал
даты. В отчёте добавлено `md_context_modules`; прежние поля и коды не менялись.

Версия lint 0.6.0 ([задача 022](tasks/022-md-forms.md), решение владельца 22 октября): L7711 —
**error**, когда контекст известен целиком: у модуля известен диалог или объект и в анализе есть
глобальный модуль конфигурации — модуль самого `1Cv7.MD` (его глобальный модуль), модуль с
`--globals 1Cv7.MD`, `run` (глобальный модуль базы, на которой исполняется модуль, — см. ниже). Тогда
имя ничем не объявлено, и 1С модуль не компилирует («Переменная не определена»: проба задачи 022 и
форма обработки базы стенда, строка 734). Без глобального модуля конфигурации (текст `--globals`,
`--allow`, база без `1Cv7.MD`) L7711 — warning, как раньше. Сообщение говорит, какой это случай.

`run` (то же решение владельца) берёт в статику глобальный модуль базы, на которой исполняется
модуль, из того же `1Cv7.MD`, что и метаданные: `[build] metadata` проекта, иначе `1Cv7.MD` базы
стенда; с `[configuration]` — собранной конфигурации. `[analysis] globals` с глобальным модулем
`1Cv7.MD` заменяют его. Этап `static` записывает `global_module` (`project`, `stand`,
`configuration`, `globals` или `null`); нечитаемый глобальный модуль статику не блокирует:
`global_module_error`, L7711 остаётся предупреждением.

## Каталог платформы

`harness77 catalog --als BIN/1cv7Lang.als --strings BIN/1crcrus.dll --output NEW.json`
строит каталог имён установленной 7.7: записи справочника (вид, рус./англ. имя,
папка, компоненты, число параметров каждой сигнатуры, `max_params=null` — без
предела), пары `English,Русское` и блок `reserved` из ресурсов. Описания и шаблоны
не копируются. Выход только новый, повтор на тех же байтах даёт те же байты.
Код 0 — JSON с путём, размером и SHA-256 результата, версией и хешами источников
в stdout; код 2 — `blocked` в stderr. Пакет содержит каталог 7.70.027
(`catalog77.json`) и список глобальных имён стенда (`lint77-globals.json`).
Задача 009 добавила раздел `messages`: номер строки ресурса, текст и блок
(`compile` — 72, `runtime` — 23) сообщений языка из `1crcrus.dll`; блоки
определяются по опорным строкам, другая раскладка — `blocked`. Прежние разделы
не изменились.

`harness77 compiler-protocol INPUT [--encoding auto|utf-8|cp1251]
[--format json] [--output OUTPUT]` сохраняет [контракт 1.1](tasks/001-compiler-protocol.md).
Код 1 и `failed` означают пригодный протокол ошибок; код 2 и `blocked` —
непригодный вход. Ошибки файлов/публикации дают код 2 и сообщение stderr.
Импорт никогда не выдаёт `passed`. Он не связывает старый протокол с новой ERT.

## Корень и каскад — команда `triage` ([задача 009](tasks/009-protocol-root-cascade.md))

`harness77 triage PROTOCOL [--source МОДУЛЬ.txt | --ert ФАЙЛ.ert] [--encoding auto|utf-8|cp1251]
[--output NEW.json]` размечает протокол Конфигуратора (с завершающим маркером) или
нативный протокол загрузки (`native/Протоколы проверки/*.txt`, без маркера).
JSON `schema_version=1`, `operation=triage`: `protocol` (имя, SHA-256, вид, кодировка),
`module` (`used`, `verified`, причина отказа, вид и SHA-256 источника), `catalog`,
`summary`, `rules` (код → нативные пробы-основания), `diagnostics`, `issues`,
`limitations`. Каждая диагностика сохраняет поля разбора и получает `index`,
`message_id`, `argument`, `role` (`root`|`cascade`|`link`|`unknown`), `cause`
(`index` корня для каскада), `confidence` (`high`|`medium`|`low`), `rule` и
`explanation`. `summary`: число диагностик по ролям, `complete` (нет признаков
остановки компиляции), `compiled_through_line`, `to_fix` (корни и `link`).
Диагностики не удаляются и не переставляются. Модуль используется, только если
строки протокола совпадают с ним без учёта пробелов по краям. Код 1 — `failed`
(протокол ошибок размечен), код 2 — `blocked` (непригодный протокол, существующий
выход, ошибка файла). `--output` — только новый файл, без него — stdout.
Разметка — подсказка: после исправления корней нужна новая компиляция.

## Сборка и извлечение

```text
harness77 extract INPUT.ert --output NEW.txt
harness77 build --template INPUT.ert --source MODULE.1s --output NEW.ert
                [--encoding auto|utf-8|cp1251|utf-16] [--legacy-normalize]
                [--form FORM.json [--metadata 1Cv7.MD]]
harness77 form-extract INPUT.ert --output NEW.json [--metadata 1Cv7.MD]
```

Выход обязателен и должен отсутствовать. Родительский каталог должен существовать.
Существующий файл, каталог, hardlink или symlink не перезаписывается. Входы
перечитываются перед публикацией; обнаруженное изменение останавливает операцию.
Применяются CFB v3 и один поток `MD Programm text`. Контейнеры с несколькими
модулями, включая полную MD, не являются входом сборки.

Извлечение сохраняет текст в UTF-8 без BOM, оставляя исходные переводы строк.
Сборка использует CP1251/CRLF. `auto`: UTF-16 с BOM, затем валидный UTF-8,
иначе CP1251. Автоопределение неоднозначно для части байтов; если кодировка
известна, следует задавать её явно. NUL и некодируемые символы отклоняются.
По умолчанию нет замен символов, в том числе представимых тире и кавычек.
`--legacy-normalize` разрешает прежние замены devtools и перечисляет каждую
в `normalizations`; неизвестный непредставимый символ всё равно даёт отказ.

Запись: подготовка → сверка текста/потоков/каталога → временный файл рядом
с выходом → flush/fsync → повторное чтение и сверка → публикация через hardlink
без замены существующего файла → удаление временного имени. Неподдерживаемая
файловой системой операция даёт отказ, обходного копирования нет. Сохраняется
содержимое посторонних потоков и метаданные записей каталога; физическое
размещение секторов и размеры модульного/root потоков меняются.

Код 0: JSON в stdout, `schema_version=1`, `tool=harness77`, `status=passed`.
`scope` равен `ert_container_build` или `ert_module_extract`.
У результата есть путь, размер и SHA-256; входы также имеют SHA-256.
Сборка дополнительно сообщает выбранную кодировку, хеш текста CP1251,
сохранённые потоки и выполненные сверки. `platform_checked=false` всегда.

Код 2: JSON `blocked` в stderr и сообщение об ошибке; неверные аргументы
дают штатный usage argparse и код 2. При ошибке очистки/stdout файл уже может
быть опубликован: существование файла само по себе не означает успех команды.
Операции не обеспечивают защиту от параллельной враждебной подмены родительских
каталогов; входы и каталог результата должны принадлежать текущей работе.

### Описание формы ([задачи 008](tasks/008-form-description.md), [011](tasks/011-form-elements.md), [012](tasks/012-reference-fields.md) и [013](tasks/013-kind-name-checks.md))

`form-extract` пишет описание формы ERT — JSON UTF-8 без BOM, LF:
`schema="harness77-form"`, `schema_version=3`, `template_dialog_sha256` (SHA-256
текста диалога шаблона в CP1251), `form` (`caption`, `width`, `height`, `layers`)
и `controls` в порядке формы (`id`, `class`, `caption`, `x`, `y`, `width`,
`height`, `formula`, `identifier`, `layer` и необязательный `type`). Координаты —
числа формы без пересчёта. `type` — тип реквизита (поля 14–16 записи):
`{"kind": "string"|"number"|"date"|"undefined"|"reference"|"other", "length",
"precision", "code"}`; пишется, если тип не «неопределённый с нулями», нулевые
длина и точность опускаются, `code` (исходный код типа) — только у `other`.
Ссылочный тип (поля 14 и 17 — код и номер объекта метаданных, длина и точность 0) —
`{"kind": "reference", "object": "<имя>"}`: `Справочник`, `Справочник.<вид>`,
`Документ`, `Документ.<вид>`, `Перечисление.<вид>`, `Счет`, `Счет.<план счетов>`,
`ВидСубконто`, `ПланСчетов`. «Любой» (номер 0) пишется именем всегда; вид —
именем по копии метаданных, которую несёт сама ERT (поток `Main MetaData Stream`):
так номер читает 1С (задача 013); номера, которого там нет, — номером:
`{"kind": "reference", "code": "B", "object_id": 133}`. Описания версий 1
(без `type`) и 2 (ссылочные — `other` с кодом) принимаются и собирают то же самое.
Выход и отказы — как у `extract`; `scope=ert_form_extract`, в отчёте также
`template_dialog_sha256`, число элементов, `names_from` (`ert` или `null` без копии),
`references_by_number` (поля, вид которых записан номером), `kinds` (поля вида:
элемент, имя по копии, код, номер в ERT), `ert_metadata` (SHA-256 потока копии, имя
конфигурации). `--metadata 1Cv7.MD` видов не переименовывает, а сверяет их по именам:
в `kinds` — номер вида в этой базе `target_object_id` (`null`, если вида нет),
`missing_in_metadata` — поля с видами, которых в ней нет, `metadata` — путь, SHA-256
файла, имя конфигурации. Неизвестный или неканонический
диалог (не восстановимый байт в байт), повреждённый контейнер и контейнер без
модуля дают код 2.

`build --form` собирает модуль и диалог за один раз. Описание обязано быть
сделано для этого шаблона (хеш диалога). Остальные поля и разделы диалога
берутся из шаблона, поэтому описание без правок даёт диалог байт в байт.
Поддерживаются: заголовок и размер формы; у существующих элементов — подпись,
x, y, ширина, высота, идентификатор, слой, формула кнопки или поля; новые
элементы в конце списка (ID — только следующий по порядку: 1С нумерует записи
с 4152 подряд и раздаёт ID окон по их порядку; остальные поля — самая частая
запись класса и типа в корпусе):

| Класс | Элемент | Обязательно | `type` | Формула |
|---|---|---|---|---|
| `BUTTON` | кнопка | `caption`, `formula` | — | вызов `Имя(…)` |
| `STATIC` | надпись | `caption` | — | — |
| `1CGROUPBOX` | рамка группы | `caption` | — | — |
| `1CEDIT` | поле строки | `identifier`, `type` | `string`, длина ≥ 0 (0 — без ограничения) | пусто или `Имя(…)` |
| `BMASKED` | поле числа или даты | `identifier`, `type` | `number` (длина ≥ 1, 0 ≤ точность < длина) или `date` | пусто или `Имя(…)` |
| `CHECKBOX` | флажок | `caption`, `identifier` | `number` длины 1 (по умолчанию) | пусто или `Имя(…)` |
| `BMASKED` | поле ссылочного типа (012) | `identifier`, `type` | `reference` по имени, кроме `ПланСчетов` | пусто или `Имя(…)` |

**Ссылочные типы (задачи 012, 013).** 1С переводит номер поля вида в имя по копии
метаданных, которую несёт ERT, и ищет вид по имени в открытой конфигурации; вида,
которого там нет, она не сообщает — поле молча теряет вид (справочник, документ
и счёт становятся «любыми», перечисление — строкой). Поэтому:
номер каждого поля вида собранной ERT должен быть в её копии (иначе отказ: с пустой
копией 1С не создаёт отчёт, с непустой поле становится «любым»); `--metadata` —
`1Cv7.MD` целевой базы, где каждый вид формы должен быть **по имени** (регистр букв
не важен), иначе отказ со списком всех отсутствующих видов и элементов; другой номер
того же вида — не отказ. Новое поле вида задаётся только именем и только с
`--metadata`; неизвестный раздел, вид у `ВидСубконто`/`ПланСчетов`, `Перечисление`
без вида, номер вместо имени у нового поля дают отказ. У существующего поля тип
не меняется: имя сравнивается с именем его номера по копии метаданных шаблона.
**Копия метаданных ERT.** Если копия шаблона содержит все новые виды (по имени),
она остаётся (`kept`), и новые поля получают её номера; иначе сборка заменяет её
потоком `Main MetaData Stream` целевой базы с байтом NUL в конце (`replaced`), а номер
каждого прежнего поля вида переводится по имени (меняется только поле 17; в `changes` —
`{"control", "property": "object_id", "from", "to", "object"}`); шаблон без копии —
отказ. Отчёт сборки содержит `form.metadata` (путь, SHA-256 файла `1Cv7.MD`, имя
конфигурации), `form.ert_metadata` (`action`, SHA-256 и конфигурация копии до и после
замены), `form.kinds` (поля вида собранной формы: элемент, имя, код, номер в ERT
и с `--metadata` номер в целевой базе `target_object_id`), а у нового ссылочного поля
в `changes` — имя, код и номер; заменённая копия не входит в `preserved_streams`.
`--metadata` без `--form` — отказ.

Формула — вызов процедуры модуля или глобальной функции каталога. Проверяется
только заданное описанием: новый или сдвинутый элемент — в клиентской области
`[4, W − 3] × [15, H − 3]` единиц формы (измерено в задаче 008) и без новых
наложений на элементы своего слоя (наложения шаблона не проверяются; рамка
группы может целиком содержать элемент); новый или изменённый идентификатор —
допустимое и уникальное имя, не совпадающее с процедурой, функцией или
переменной `Перем` модуля (1С такой модуль принимает, но `Перем` перекрывает
реквизит формы, задача 011); слой — из формы. Удаление, перестановка, смена
ID/класса или типа существующего элемента, изменение слоёв, другие классы
новых элементов, тип или формула не своего класса, неизвестные свойства
и неверные типы JSON дают отказ (код 2). Отчёт сборки дополняется `form` (путь
и SHA-256 описания, хеши диалога до и после, `dialog_unchanged`, `changes`)
и `verification.dialog`; поток диалога не входит в `preserved_streams`. Работу
формы в 1С это не подтверждает: она проверена нативно для одного шаблона
(задачи 008, 010, 011).

## Модули конфигурации — `md-extract`, `md-build` (задача 021)

```text
harness77 md-extract 1Cv7.MD --output NEW_DIR
harness77 md-build --template 1Cv7.MD --modules DIR --output NEW.MD
```

`md-extract` пишет в новый каталог все модули `1Cv7.MD` — UTF-8 без BOM, переводы
строк как в 1С (CRLF), — и индекс `modules.json` (`format=harness77-md-modules`: для
каждого файла путь потока в `1Cv7.MD`, объект, модуль, SHA-256 текста в Windows-1251;
SHA-256 и имя конфигурации). Раскладка по метаданным: `ГлобальныйМодуль.1s`,
`Документ/<Имя>/МодульДокумента.1s`, `Документ/<Имя>/Форма.1s`,
`Справочник/<Имя>/ФормаЭлемента.1s`, `…/ФормаГруппы.1s`, `…/ФормаСписка.<Форма>.1s`,
`Журнал/<Имя>/ФормаСписка.<Форма>.1s`, `Отчет/<Имя>/Форма.1s`, `Обработка/<Имя>/Форма.1s`;
папка без названного объекта (бухгалтерские формы) — `Прочие/<Папка>_Number<n>.1s`.
Описания `TypedText/UserHelp_*` — не код, в раскладку не входят. Два модуля одного
файла, нечитаемый модуль — отказ.

`md-build` заменяет в шаблоне только модули, текст которых отличается (сравнение после
приведения переводов строк к CRLF; кодировка файла — как у `build`, `auto`); файла нет —
модуль без изменений; без изменений выход — байты шаблона. Отказ (код 2): файл не из
раскладки шаблона (новые модули не создаются), символ вне Windows-1251 (строка и колонка),
NUL; с `modules.json` — изменённый файл, которого нет в индексе, и модуль, который шаблон
изменил после извлечения (SHA-256 модуля шаблона ≠ индекса): правка не затирает чужое
изменение. Результат читается с диска: изменённые модули — новый текст, остальные потоки
(метаданные тоже) и записи каталога — байт в байт. Отчёт: шаблон (SHA-256, конфигурация),
`modules` (каталог, число файлов, `index` — SHA-256 индекса и `md_sha256` извлечения),
`output`, `rebuilt`, `changed` (файл, поток, объект, модуль, кодировка, SHA-256 и число
строк до и после), `unchanged_modules`, `verification`. 1С это не проверяет — для этого
`run` с `[configuration]`.

**Формы (задача 022, [задание](tasks/022-md-forms.md)).** Рядом с модулем каждой формы
`md-extract` пишет её описание `<модуль>.json` — схема `harness77-form` 3, как у
`form-extract` ERT; виды ссылочных полей названы по метаданным самой конфигурации.
`modules.json` — версия 2: строки `forms` (файл, поток `Dialog Stream`, объект, модуль,
`dialog_sha256`, `described`). Диалог, который описание не пересобрало бы без потерь,
описания не получает: отчёт `forms_not_described` (файл, поток, причина). `md-build`
читает индекс версий 1 и 2; файл `.json` — описание формы своего модуля, диалог
пересобирается, если описание отличается от диалога шаблона. Изменения и отказы — как у
`build --form`, с контекстом конфигурации: вид поля ищется по имени в её метаданных, номер —
из них же; формула вызывает процедуру модуля формы в собранном виде, экспортную процедуру
собранного глобального модуля или функцию платформы; описание другого диалога — отказ.
Формы документа и элемента или группы справочника: новое поле с именем реквизита объекта
(шапки или общего реквизита документа, реквизита справочника) — поле этого реквизита, и его
тип обязан совпасть с типом реквизита (код, длина, точность, вид); отказ — поле с именем
реквизита табличной части, встроенного реквизита (`НомерДок`, `ДатаДок`, `ВремяДок`, `Код`,
`Наименование`, `Родитель`, `Владелец`), элемент без данных с именем реквизита, смена
идентификатора на имя реквизита или с него, новое поле реквизита справочника, который на этой форме
не выводится (использование реквизита — поля 11 и 12 его записи: на форме элемента — «для элемента»,
на форме группы — «для группы»; без известного использования — без отказа). Табличная часть или список формы (запись
`Multicolumn` раздела `Browser`) — препятствие для нового или перемещённого элемента своего
слоя. Новые записи создаются 1С первыми, поэтому первое число раздела `Browser` растёт на их
число (изменение `table_part_position`): табличная часть остаётся после тех же элементов
шаблона. Раздел `Browser` в остальном не меняется. Отчёт дополнен `modules.forms`,
`changed_forms` (файл, поток, объект, модуль, файл и поток модуля, SHA-256 диалога до и после,
`changes`, `kinds`, у поля реквизита — `attribute`), `unchanged_forms`,
`verification.changed_dialogs`. `run` с `[configuration]` проверяет модуль изменённой формы
как изменённый модуль в контексте нового диалога; ошибку компиляции модуля формы относит к её
файлу по имени в журнале копии: «<Документ|Обработка|Отчет>.<Имя>.Форма.Модуль» — `…/Форма.1s`,
«Справочник.<Вид>.Форма.Модуль» — `ФормаЭлемента.1s`, «Справочник.<Вид>.Форма группы.Модуль» —
`ФормаГруппы.1s`, «Справочник.<Вид>.ФормаСписка.<Форма>.Модуль» и «Журнал.<Имя>.Форма.<Форма>.Модуль» —
`ФормаСписка.<Форма>.1s` (задачи 022 и 023).

## Полный цикл — команда `run`

```text
harness77 run --project PROJECT.toml --stand STAND.toml [--output-root DIR]
              [--open-timeout-s N] [--calculation-timeout-s N] [--cancel-timeout-s N]
              [--shutdown-timeout-s N] [--total-timeout-s N] [--run-id ID]
```

Связывает статику (`lint77`), сборку (`artifacts.build`), проверку платформой и
тесты в один запуск. Статика проверяет текст модуля в контексте диалога шаблона
сборки (L7711) или описания формы, если в профиле задано `[build] form`; оно же
передаётся сборке. Профиль проекта задаёт идентификатор, шаблон и исходник ERT,
контекст анализа, тесты (`[[platform.tests]]` с `name`, `command`, `expect`,
необязательным `expect_value`) и сроки. Профиль стенда задаёт backend
(`native`|`simulation`|`import`), машинные пути, выбранную существующую базу,
пользователя и закреплённые хеши. Пароли в профиле не хранятся. Относительные пути
разрешаются от каталога профиля. Полное описание — [задание этапа 4](tasks/004-full-cycle.md).

Ссылочные поля формы (задачи 012, 013): `[build] metadata` — `1Cv7.MD` целевой
базы; если не задано, а у описания есть поле вида (`Справочник.Контрагенты` или номер),
сборка берёт `1Cv7.MD` базы стенда. Этап `build` записывает `form.metadata`
(SHA-256, имя конфигурации, источник `project`|`stand`) и `form.kinds`. Если
`1Cv7.MD` базы стенда отличается от метаданных сборки, `platform_check` до запуска
1С сверяет с ним виды формы по именам: вида нет — `blocked`
(`metadata_missing_kinds` с именами и элементами), 1С не запускается; другой номер
того же вида — не отказ. Итог сверки — `metadata_check` этапа (SHA-256, конфигурация,
`same_as_build`, `missing`).

Изменённые модули конфигурации (задача 021, [задание](tasks/021-md-modules.md)):
`[configuration] modules = "DIR"` (раскладка `md-extract`, достаточно изменённых файлов),
`keep_copy = true` оставляет копию. Этап `configuration` собирает `1Cv7.MD` из `1Cv7.MD`
базы стенда (закреплённый хеш обязан совпасть) и каталога: `md_sha256`, `changed`,
`template_sha256`; отказ сборки — `blocked`, 1С не запускается. `static` проверяет
модуль ERT с экспортом собранного глобального модуля, а изменённые модули — в контексте
собранной конфигурации; в отчёте только замечания, которых у того же модуля шаблона не
было (`configuration_preexisting` — их число, `configuration_modules`). 1С открывает копию
базы по `[stand.base] copy_path` — пути, зарегистрированному в списке баз 1С однажды
(через OLE 1С 7.7 открывает только зарегистрированную базу); `copy_exclude` — подкаталоги
верхнего уровня, которые копия опускает. Прогон берёт замок `<copy_path>.lock`
(занят живым процессом — `blocked`), заменяет только помеченную прежнюю копию, пишет метку
`harness77-copy.json` со своим `run_id`, копирует базу (открыта в 1С — `blocked`) и кладёт в
неё собранный `1Cv7.MD`; launcher принимает копию только с этой меткой, зарегистрированным
путём и `--configuration-sha256`. После сеанса копия удаляется, замок снимается, база стенда
сверяется по перечню файлов (имя, размер, время). `platform_check.base_copy`: путь (тег),
файлы, байты, секунды, `excluded`, `md_sha256`, `removal`, `lock`, `source_check`,
`session_log` — записи журнала копии за сеанс (`SYSLOG/1cv7.mlg`; сырые — файл
`base-session-log.txt` запуска); `base_list` — хеш списка баз до и после. Ошибка
компиляции изменённого модуля в журнале (`GrbgSyntaxErr`: «Глобальный модуль»,
«Документ.<Имя>.Модуль Документа», модули форм — см. `md-build`) делает `platform_check`
`failed` — `configuration_compilation_failed: <файл>:<строка>: <сообщение>`, код 1, —
если сеанс своей 1С завершён чисто; `configuration_diagnostics` — модуль, файл, строка,
колонка, текст строки, `changed`. Так видна и ошибка модуля документа при проведении или
модуля формы при открытии, на которых обработка исключения не получает. `platform.base_usage`
— `copy-per-run`. По истечении срока открытия `open.timeout_windows` — окна своей 1С (только
чтение).

Имена объектов в коде (задача 018): этап `static` проверяет модуль с метаданными
`[build] metadata` проекта, иначе с `1Cv7.MD` базы стенда, если он есть (L7712–L7714);
`static.metadata` — SHA-256, имя конфигурации и источник `project`|`stand`, без
метаданных — `null`. Нечитаемый `1Cv7.MD` — `static` `blocked`.

Каждый запуск получает новый `run_id` и каталог `<output-root>/<run_id>`. Входы,
шаблон, собранная ERT, платформенные свидетельства и тесты связаны по `run_id` и
SHA-256; проверяется именно ERT этого запуска. Старый, чужой, частичный или
отсутствующий результат успехом не считается.

Сроки (раздел 8.5): пять конечных положительных значений `open/calculation/cancel/
shutdown/total`; общий покрывает сумму фаз; несогласованные отклоняются до старта.
Источник — CLI > проект > стенд; умолчаний нет, прототипные 30/145 с не
применяются. Срок `open` покрывает и переиндексацию, которую 1С выполняет при
открытии базы после прерванного сеанса: по наблюдению владельца на некоторых
базах она идёт час и больше. Нормальный запуск срок не ждёт, поэтому `open`
задаётся по худшему случаю для своей базы; общий срок его включает. Нативно каждая
команда обработки получает срок `calculation`. Задача 007: необязательный
`reindex_timeout_s` (CLI `--reindex-timeout-s`) добавляется к `open` только если
стенд до запуска видит след прерванного сеанса (`1Cv7.LCK`, который никто не держит);
общий срок покрывает `open + reindex + calculation + cancel + shutdown`. Открытие —
от начала сеанса до первой команды обработки — ограничено своим сроком
(`timeout_phase=open`); в отчёте этапа `platform_check` поле `open`: срок,
ожидание переиндексации, след до и после, время открытия. Эффективные значения и источник — в отчёте. Часы внешние монотонные;
срок фазы абсолютен, тишина и прогресс его не меняют.

Задача 015 ([задание](tasks/015-launcher-robustness.md)): запуск cdb и 1С — часть
открытия, нативный launcher даёт ему срок `open_timeout_s` без запаса на
переиндексацию (`open.startup_deadline_s`, время — `open.startup_s` с `ownership`
и `debugger_ready`). Временная регистрация COM launcher несёт запись владельца —
процессы своего сеанса; регистрация, оставленная снятым сеансом (снятие дерева
процессов `run`, выход клиента MCP), снимается, только если все её процессы
доказанно завершены, и попадает в `open.stale_com_registrations` (`run_id` того
сеанса, процессы с признаком завершения, ключи). Регистрация без записи владельца
или с живым процессом — по-прежнему отказ `blocked` до запуска 1С.

`shutdown.poll_rounds` — круги опроса launcher: `count`, `max_seconds`, а с задачи 017
([задание](tasks/017-poll-round.md)) — `step_max_seconds`, наибольшее время каждого шага
круга за сеанс (`identity`, `events`, `markers`, `debugger_log`, `inventory`, `exit_check`,
`sleep` — фактическая пауза между кругами), и `slowest`, те же шаги самого долгого круга.
Сведения для разбора; на вердикт они не влияют.

Отчёт `run.json` (`schema_version=1`, `tool=harness77`, `operation=run`): входы и
проверенный артефакт с хешами; идентификация платформы и базы без секретов и
`platform_checked`; этапы `static`/`build`/`platform_check`/`tests` со статусом,
длительностью, диагностиками и причиной неполноты; `deadlines` с источником;
`result_files` с путём, размером, SHA-256 и `complete`; `cancelled`,
`timeout_phase`, `reason`; `shutdown` и `screenshots`. Большие результаты —
файлы каталога запуска; размер и SHA-256 считаются потоком, полная копия файла
в памяти не держится.

Задача 009: если загрузка дала диагностики, этап `platform_check` размечает их
по модулю собранной в этом запуске ERT — поля `triage` выше в `diagnostics`,
`summary`, `module`, `rules`, `catalog` в `triage`. `load.diagnostics` остаются
неразмеченными. Нативный launcher дополнительно передаёт `column` и `source_line`.

Задача 006 ([задание](tasks/006-long-native-report.md)): `[platform.parameters]`
профиля проекта — строки, числа и логические значения, с задачи 025 также массивы
из них или из таблиц таких значений (глубже — отказ профиля) — передаются
launcher стенда вместе с командами объявленных тестов (`--parameters-json`,
`--commands-json`) и попадают в `inputs` отчёта. Файл результата может указывать
свою операцию (`operation`): отсутствующий или неполный файл не даёт успеха, если
его операция прошла или не указана; файл операции, которая уже отказала, — её
свидетельство, итог решает тест (так проверяется ожидаемый сбой записи).

**Данные теста и существующие объекты — задача 024, launcher форм.**
`research/forms/form_launcher77.py` принимает в `[platform.parameters]`:

- `fixture_setup` — непустой текст тела функции на языке 1С 7.7, со своим `Возврат`.
  Выполняется один раз перед `check`; его результат сохраняется для `open` и `verify`.
  Должен вернуть ссылку на записанный элемент/группу справочника или документ.
- `fixture_mode` — `existing` (по умолчанию) либо `owner`. В `existing` открывается
  полученная ссылка (`ОткрытьФорму(Ссылка, Контекст, 0)`), соответствующая `form_object`:
  `Справочник.<Вид>.ФормаЭлемента|ФормаГруппы` или `Документ.<Вид>`. В `owner` открывается
  новая форма подчинённого справочника, а ссылка передаётся пятым аргументом
  `ОткрытьФорму` как владелец. Вид владельца берётся из метаданных копии.
- `fixture_verify` — необязательное тело функции, параметр `Объект77` — ссылка из
  подготовки. Команда `verify` выполняет его после закрытия формы (`result`). Возврат —
  одна строка без перевода строк. При таком параметре обязателен объявленный тест с
  `command = "verify"`; `expect_value` сравнивается обычным механизмом тестов `run`.

Эти параметры допускаются только на подтверждённой копии `[configuration]` текущего
запуска: метку, `run_id`, регистрацию пути и SHA-256 проверяет прежний launcher.
Конфигурация может быть неизменённой. Без копии — `blocked` до старта 1С; на формах
списков, журналов, обработок и отчётов параметры подготовки не поддержаны. Подготовка
проверяет тип, вид, `Выбран()` и признак группы; пустая или неподходящая ссылка и
ошибка исполнения подготовки — `blocked`, причина `fixture_setup_failed`, форма
не открывается. Ошибка исполнения `verify`, отсутствие результата или неверный тип
возврата дают операции `failed`; при `expect = "passed"` это провал теста и прогона.
Неверное `expect_value` также проваливает прогон. Явное ожидание `failed` позволяет
описать отрицательную проверку, как и у остальных операций launcher.

Это обычный доверенный код теста с возможностью записи в копию, а не декларативное
описание данных и не Gherkin. Текст входит в профиль и `inputs` отчёта; сгенерированный
контроллер и нативные протоколы сохраняются в каталоге запуска. Протокол формы
(`loaded:harness77-form`, результаты обработчиков в `Форма.Параметр`) остаётся прежним.
Проверены существующие элемент, группа, документ и подчинённый элемент, новый элемент
с владельцем; новая группа подчинённого справочника отдельно не проверялась.
[Запускаемый пример](../examples/test-data/README.md) готовит форму и протокол автоматически.

**Сценарий шагов на форме — задача 025, launcher форм.** `[platform.parameters] steps` —
массив таблиц, по таблице на шаг, в каждой ровно один ключ вида
([задание](tasks/025-form-steps.md), [пример](../examples/form-steps/README.md)):

- `{ click = "<элемент>" }` — `BM_CLICK` кнопке или флажку; `closes = true` — нажатие закрывает форму;
- `{ input = "<элемент>", text = "…" }` — фокус полю (`WM_NEXTDLGCTL`), выделение его текста, ввод
  символов (пустой `text` очищает поле), переход к следующему элементу описания, после чего 1С
  принимает значение;
- `{ check = "<элемент>", … }` с одним ключом `text`, `checked`, `enabled` или `visible` — что
  показывает окно (текст сравнивается без крайних пробелов: числовое поле показывает « 12.50»;
  `visible` — собственный `WS_VISIBLE`);
- `{ value = "<реквизит>", text = "…" }` — `Строка()` реквизита в контексте открытой формы, без крайних
  пробелов;
- `{ message = "…" }`, `{ no_message = "…" }` — есть или нет строка (без крайних пробелов) среди
  сообщений 1С после последнего действия.

Элемент — идентификатор, иначе подпись без `&`, регистр не важен; ровно один элемент подходящего
класса в описании формы (ERT или `1Cv7.MD`). Неизвестный, неоднозначный или неподходящий элемент,
неверная таблица, шаг после объявленного закрытия, кроме `message`/`no_message`, а также
`steps` вместе с `actions` или `click_id` — `blocked` до запуска 1С. Снимок `clicked` со
шагами не поддержан (отказ); снимок `open` делается до шагов.

Шаги идут после осмотра формы. После каждого шага клиент один раз вызывает контроллер:
сообщения шага сохраняются в `Протоколы проверки/step-<n>.txt`, а запрошенный реквизит читается
через контекст формы. Затем читаются окна. Нажатие и ввод в выключенный или скрытый элемент
отказывают. Ошибка исполнения 1С среди сообщений шага, неверное ожидание, необъявленное закрытие
формы или закрытие, которое не произошло, — провал шага, и сценарий останавливается. Модулю формы
не нужен протокол harness77: в режиме шагов `check` и `open` подтверждаются `ОткрытьФорму() = 1`
и окном, ошибка 1С любой команды — `failed`. Тест `result` проходит, если прошли все шаги и форма
закрыта контроллером или объявленным шагом. Его `steps` в `platform-result.json` — по шагу:
действие, круг через 1С (сообщения, значение, ошибки), состояние окна, `issue`. Разрешённые шаги —
`<run>/form/steps.json`. Подготовка данных и `verify` задачи 024 действуют по-прежнему.
Табличная часть формы документа и списки — задача 027 (ниже).

**Модальные окна в шагах — задача 026.** `{ dialog = "<текст окна>", button = "<кнопка>",
text = "<ввод>", closes = true }` отвечает на окно, которое открыло действие (`click`, `input`)
перед ним ([задание](tasks/026-modal-dialogs.md), [пример](../examples/modal-dialogs/README.md)).
Шаг `dialog` идёт сразу после такого действия или после другого `dialog`; `closes` у действия,
за которым идёт `dialog`, — `blocked` до запуска, его место — на последнем `dialog`. `dialog` —
текст сообщения окна, а если его нет, заголовок (подсказка окна ввода); пробелы и переводы строк
сравниваются как один пробел. `button` — подпись без `&`, без учёта регистра, латинские
и кириллические буквы одного начертания равны; без `button` в окне должна быть одна кнопка.
`text` вводится в единственное поле окна. Ответ — `WM_COMMAND`/`BN_CLICKED` от кнопки.

Последнее сообщение действия отправляется из своего потока; модальное окно — новое видимое окно
верхнего уровня потока 1С с выключенным владельцем или новое `#32770`. После возврата действия
1С вызывается, и окно ищется ещё раз (вопрос «Сохранить изменения?» после `#Закрыть`). Вызовы
цепочки — номера `шаг + 1000·k`, протоколы `step-<номер>.txt`. Действие и его окна — одна цепочка:
её вызовы, сообщения и ошибки исполнения оцениваются вместе на последнем шаге. Окно без шага
`dialog`, не тот текст, нет кнопки или поля, окно не открылось — провал шага; окно провалившегося
шага закрывается кнопкой «Отмена», иначе «Нет», иначе единственной (до пяти окон), в `steps` —
`dismissed`. В записи шага: `modal` (окно, на которое ответит следующий `dialog`), `unexpected`,
`window`, `answer`, `calls`. `ОткрытьФормуМодально`, выбор ссылочного значения, окно
в `ПриОткрытии` и окна без кнопок не поддержаны.

**Табличная часть в шагах — задача 027.** Для формы документа конфигурации с табличной частью
([задание](tasks/027-table-part-steps.md), [пример](../examples/table-part/README.md)):
`{ add_row = true }` (Insert), `{ row = <номер> }` (курсор клавишами Down/Up), `{ cell = "<колонка>",
text = "…" }` (ячейка в режиме редактирования через `Активизировать(<колонка>, 1)`, замена текста, Enter;
исполняется формула колонки), `{ delete_row = true }` (Delete), `{ rows = <число> }`,
`{ total = "<колонка>", text = "…" }` (`Строка(Итог(…))`), `row = <номер>` у `value` (реквизит строки
из `ВыгрузитьТабличнуюЧасть`, курсор не двигается). `{ key = "<клавиша>" }` — Insert, Delete, Enter,
Escape, Tab, Up, Down, Left, Right, Home, End, PageUp, PageDown, F2–F9 в табличной части или списке;
в форме списка из новых шагов доступен только он, а `value` читает реквизит текущего элемента.
Колонка — идентификатор или заголовок из раздела `Browser` формы; `cell` — только в колонку поля
строкового, числового или датового реквизита, кроме номера строки. Неизвестная или неоднозначная
колонка, ссылочная колонка у `cell`, шаг табличной части на форме без неё, на форме списка или ERT,
номер строки меньше 1 — `blocked` до запуска 1С.

Клавиши — `WM_KEYDOWN`/`WM_KEYUP` через очередь сообщений окну табличной части (ID 4151) или
редактора ячейки, после повторной проверки процесса; пока идут шаги такой формы, главное окно 1С
показано без активации на своём рабочем столе. Перед действием и после него контроллер сообщает число
строк, номер текущей строки и текущую колонку. `add_row` проходит, если строк стало на одну больше,
`delete_row` — на одну меньше, `row` — если текущей стала нужная строка, `cell` — если редактор
колонки открылся, принял текст и закрылся по Enter. Если открыт редактор ввода новой строки,
`add_row`, `delete_row` и `row` сначала заканчивают ввод клавишей Enter (не больше числа колонок).
`add_row`, `cell`, `delete_row`, `key` — действия: за ними идут шаги `dialog` задачи 026. В записи шага:
`before` (состояние до действия), `round_trip` (после), у `cell` — редактор, текст до и после ввода;
`table` — окна табличной части и фокус. Выбор ссылочного значения, подбор и формы, открытые
из табличной части, табличная часть ERT не поддержаны.

Статусы этапа: `passed`/`failed`/`blocked`/`skipped`. Коды выхода: `0` — все
обязательные этапы прошли (включая проверенный ожидаемый отрицательный тест);
`1` — дефект проверяемого кода или провал теста (ошибка компиляции/исполнения,
несовпадение ожидания); `2` — ошибка входа/инфраструктуры или неполный
обязательный результат (недоступная база, тайм-аут, отмена `cancelled`,
`artifact_write_error`, `shutdown_error`, старый/частичный/чужой результат).
При совпадении дефекта и инфраструктуры приоритет у `2`. Пользовательская отмена
(Ctrl+C, а в Windows и Ctrl+Break) запускает ограниченное ожидание возврата и
завершения своего сеанса; принудительное завершение допускается только для
доказанно собственного сеанса и явно отражается в результате. Нативный launcher
работает в своей группе процессов и узнаёт об отмене по файлу `cancel` каталога
запуска; если за сроки `cancel` + `shutdown` и 10 с запаса он не вернулся, его
процесс снимается и результат помечается принудительным. Этап ниже по конвейеру, не выполненный
из-за отказа выше, помечается `skipped` и итог не повышает.

Backends: `simulation` и `import` всегда `platform_checked=false` и автоматической
проверкой платформы не являются. `native` вызывает launcher стенда (принятый
`research/platform77/stage4_launcher77.py`), доказывает владение процессом до
Initialize, работает на отдельном desktop, проверяет завершение и не выводит
успех из исчезновения процесса. Нативная приёмка короткого цикла выполнена;
реальный долгий прикладной отчёт — отдельный прогон (см.
[приёмку](tasks/004-full-cycle-acceptance.md)). Подробные критерия долгих
расчётов — [раздел 8.5 ТЗ](restructuring-spec.md#85-долгие-расчёты-и-большие-отчёты).

## Визуальные тесты формы — `[visual]` и команда `visual` ([задача 010](tasks/010-visual-form-tests.md))

Профиль проекта может объявить сравнение снимков формы с утверждёнными эталонами:

```toml
[visual]
baselines = "baselines"          # каталог эталонов, от каталога профиля

[[visual.checks]]
name = "form-open"               # латиница, цифры, . _ -; имя файлов эталона
state = "open"                   # open — сразу после открытия; clicked — после нажатия click_id
window = "form"                  # form — окно с заголовком; dialog — внутренняя часть
channel_tolerance = 0            # допустимая разница канала 0…255
max_diff_pixels = 0              # сколько пикселей может отличаться
mask_caret = true                # маскировать мигающий курсор ввода
masks = [{x = 0, y = 0, width = 10, height = 10, reason = "часы"}]
```

Неизвестные ключи, повтор имени, маска без причины — ошибка профиля. С `[visual]`
`run` запрашивает у стенда снимки (`--captures-json` launcher, список
`{state, window}`) и после `tests` выполняет обязательный этап `visual`. Этап
`platform_check` получает `captures`: состояние, окно, файл (путь, SHA-256,
`complete`; нативно перепроверяется с диска), размер, среда, курсор, устойчивость,
число попыток или `error`. Каждая проверка сравнивает снимок с эталоном по пикселям
вне масок профиля и курсора (его прямоугольник из снимка и из записи эталона);
провал — разный размер или больше `max_diff_pixels` пикселей с разницей канала
больше `channel_tolerance`. Строка проверки: `status`, `reason`, `size`,
`diff_pixels`, `masked_pixels`, `max_channel_delta`, `diff_box`, `masks`,
`baseline`, `capture`, `files`; в каталоге запуска `visual/<name>/` — `baseline.png`,
`actual.png`, `diff.png` (снимок светло-серым, различия красным, маски синим),
`result.json`.

`blocked` вместо сравнения: нет снимка, ошибка или неустойчивость снимка, нет
эталона, изображение эталона не совпадает с записью, запись для другого состояния
или окна, среда снимка не совпадает со средой эталона или не записана
(`environment_issues`). Среда — `platform_version`, `configuration` (SHA-256
`1Cv7.MD`), `windows_build`, `system_dpi`, `window_dpi`, `theme`, `font`, `locale`,
`capture`. Если платформа не прошла, этап `skipped`. Коды выхода общие: провал
сравнения — `1`, блокировка — `2`.

Эталоны пишет только явное утверждение; `run` их не создаёт и не меняет:

```text
harness77 visual approve --project PROJECT.toml --run RUN_DIR --by WHO [--check NAME ...] [--replace]
harness77 visual compare BASELINE.png ACTUAL.png --output NEW_DIR [--mask x,y,w,h ...]
                         [--channel-tolerance N] [--max-diff-pixels N]
```

`approve` берёт снимки запуска, прошедшего `platform_check`, и пишет
`<name>.png` и `<name>.json` (`harness77-visual-baseline` 1: изображение, среда,
курсор, кто и когда, `run_id`, хеши ERT и описания формы, статус тестов, маски
профиля, хеш заменённого эталона). Отказ без записи: запуск не прошёл платформу,
снимок отсутствует, неустойчив, изменён после запуска или без среды, имя проверки
неизвестно, эталон уже есть без `--replace`. Код `0` — утверждено, `2` — отказ.
`compare` сравнивает два PNG вне запуска: `0` совпали, `1` различаются, `2`
нечитаемый вход. Читаются PNG 8 бит без чересстрочности (серый, RGB, RGBA —
альфа-канал отбрасывается);
пишется RGB без служебных блоков, одинаковые пиксели дают одинаковые байты.

Нативные снимки делает `research/forms/form_launcher77.py`: показывает скрытое
главное окно своей 1С на своём desktop без активации, снимает `PrintWindow`
(`PW_RENDERFULLCONTENT`) серией до двух совпадающих вне курсора (до 6 попыток),
затем скрывает окно. Другой launcher на запрос снимков отвечает отказом.

## MCP-сервер — команда `mcp` ([задача 014](tasks/014-mcp-server.md))

`harness77 mcp` — сервер Model Context Protocol на stdio: JSON-RPC 2.0, одно
сообщение на строку UTF-8. Рукопожатие `initialize`, версии `2025-11-25`,
`2025-06-18`, `2025-03-26`, `2024-11-05`: сервер отвечает версией клиента, если
знает её, иначе `2025-11-25`. Клиент ревизии `2026-07-28` (без рукопожатия)
получает на `server/discover` ошибку `-32601` и переходит к `initialize`.
Возможности — только `tools`. Методы: `initialize`, `ping`, `tools/list`,
`tools/call`; уведомления `notifications/initialized`, `notifications/cancelled`.
Пакет JSON-RPC (массив) — `-32600`, неразборчивая строка — `-32700`, неизвестный
метод — `-32601`, неизвестный инструмент — `-32602`. В stdout — только сообщения
протокола; журнал сервера — в stderr. Код выхода `0` после закрытия stdin.

Инструменты — команды CLI с теми же ключами (`-` в имени ключа становится `_`):

| Инструмент | Команда | Аргументы |
|---|---|---|
| `lint` | `lint --format=json` | `paths`*, `globals`, `allow`, `dialog`, `metadata`, `strict` |
| `compiler-protocol` | `compiler-protocol` | `input`*, `encoding` |
| `triage` | `triage` | `protocol`*, `source`, `ert`, `encoding` |
| `extract` | `extract` | `input`*, `output`* |
| `form-extract` | `form-extract` | `input`*, `output`*, `metadata` |
| `md-extract` | `md-extract` | `input`*, `output`* |
| `md-build` | `md-build` | `template`*, `modules`*, `output`* |
| `build` | `build` | `template`*, `source`*, `output`*, `encoding`, `legacy_normalize`, `form`, `metadata` |
| `run` | `run` | `project`*, `stand`*, `output_root`, `run_id`, `open_timeout_s`, `calculation_timeout_s`, `cancel_timeout_s`, `shutdown_timeout_s`, `total_timeout_s`, `reindex_timeout_s` |
| `visual-compare` | `visual compare` | `baseline`*, `actual`*, `output`*, `masks`, `channel_tolerance`, `max_diff_pixels` |

`*` — обязательный. Нет в MCP: `catalog`, `visual approve` (эталон утверждает
человек в CLI), `--output` у `lint`, `compiler-protocol`, `triage` (отчёт — в ответе).
Подсказки: `lint`, `compiler-protocol`, `triage` — `readOnlyHint`; `run` —
`destructiveHint` (исполняет модуль на базе стенда); остальные пишут только новые файлы.

Вызов — дочерний процесс `python -m harness77 <команда>` тем же интерпретатором,
в рабочем каталоге сервера (относительные пути — от него) и с окружением сервера.
Ключи передаются как `--ключ=значение`, позиционные — после `--` (пути, начинающиеся
с `-`); `encoding` у `compiler-protocol`, `triage`, `build` всегда передаётся
(по умолчанию `auto`). Неверные аргументы — лишний или пропущенный, не того типа,
вне перечня, с NUL — результат `isError` с текстом без запуска процесса.

Результат: `structuredContent` (схема — `outputSchema` каждого инструмента) —
`tool`, `argv` (аргументы после `harness77`), `cwd`, `exit_code`, `stdout`,
`stderr` (разобранный JSON, если операция вывела JSON, иначе текст, пустой — `null`),
`duration_s`; тот же JSON — текстом в `content`. `isError` — при коде вне `0` и `1`:
`1` — найденный дефект или провал теста, это результат проверки.

Вызовы идут параллельно. С `_meta.progressToken` запроса сервер каждые 10 с шлёт
`notifications/progress` (секунды от начала, растут). `notifications/cancelled`:
`run` получает файл отмены (`--cancel-file`) и отменяется как по Ctrl+C;
остальные операции доходят до конца (новые файлы не остаются недописанными); ответ
на отменённый запрос не отправляется. Закрытый stdin отменяет активные `run` так же,
остальные вызовы завершаются; ответы отправляются, пока клиент читает; затем сервер
выходит. Клиент, снимающий дерево процессов сервера (официальный Python SDK на
Windows — через 2 с после закрытия stdin), снимает и `run` со своей 1С (она дочерний
процесс отладчика launcher): 1С останавливается принудительно, `run.json` нет,
временная регистрация COM launcher остаётся, и следующий запуск снимает её, доказав
завершение её процессов (задача 015). `run` намеренно не выносится из дерева сервера,
чтобы дойти до конца без клиента (задача 017): отмена тоже останавливает 1С принудительно,
а `run` без клиента держал бы стенд до срока профиля незаметно для следующей сессии.

`harness77 run --cancel-file PATH`: запуск отменяется, когда файл появится
(проверка каждые 0,2 с), как по Ctrl+C; файл, существующий до старта, — `blocked`,
код 2, ничего не запускается.
