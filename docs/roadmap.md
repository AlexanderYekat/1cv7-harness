# Дорожная карта harness77

Обновлено 10 октября 2026 года. Цель — постепенно получить полный цикл проверки разработки для 1С 7.7: исходники → статический анализ → сборка ERT → проверка платформой → тесты на копии базы → отчёт для разработчика или агента.

Это действующий порядок развития проекта. [Архитектура](architecture.md) задаёт границы компонентов, [большое ТЗ](restructuring-spec.md) сохраняет подробные требования. Начать ближайшую фичу можно уже сейчас.

## 0 Подготовка завершена

Папки упорядочены, назначение компонентов описано, исходное состояние сохранено в Git, локальные данные исключены из истории. Линтер и инструменты чтения/записи уже существуют; общий запуск всего цикла ещё предстоит сделать. Проверенные версии и ограничения — в [манифесте](baseline.json).

## 1 Разбирать ошибки платформы в JSON

**Следующая задача.** Преобразовать сохранённый текстовый протокол ошибок Конфигуратора в диагностики с путём, строкой, колонкой и сообщением.

**Готово, когда:** P2 даёт 7 диагностик, P1 — 60, неполный или неизвестный протокол явно отклоняется; есть переносимые тестовые примеры. Подготовлены [методологическое ТЗ](tasks/001-compiler-protocol.md) и [техническое ТЗ на реализацию](tasks/001-compiler-protocol-technical.md): определены контракт JSON, алгоритм, файловые операции, тестовые сценарии и приёмка. Реализация не начата.

Результат полезен сразу: агент получает ошибки в машинном формате. Импорт протокола пока не связывает его с текущей версией ERT и не подтверждает успешную компиляцию.

## 2 Проверить способ управления настоящей 1С 7.7

**После задачи 1.** На выбранной установке и рабочей копии базы провести небольшой эксперимент: исправная ERT, синтаксическая ошибка, ошибка открытия базы, зависание и повторный запуск. Установить, какие модули реально проверяются и как получать достоверный результат.

**Готово, когда:** зафиксированы воспроизводимый способ запуска, протокол и ограничения; успех проверки, ошибка кода и сбой среды различимы. Для этого эксперимента общий пакет не требуется.

Если автоматический способ не подтверждается, сохраняем ручной импорт как отдельную возможность и уточняем способ автоматизации. Полный автоматический цикл остаётся незавершённым.

## 3 Сделать воспроизводимую сборку и запуск инструментов

**Далее, двумя небольшими задачами.** Сначала подготовить устанавливаемый пакет и общий CLI над нужными существующими операциями, с явными путями и зависимостями. Затем закрепить сборку «текст + шаблон → новая ERT» с проверкой сохранности контейнера. Место переноса кода и использование 77MCP определить в задании на пакет, сохранив исходные истории Git.

**Готово, когда:** инструменты устанавливаются по инструкции и работают из другого каталога; исходники и шаблон не изменяются; текст собранной ERT проверяется обратным чтением, остальные потоки сохраняются. Результат содержит хеши входов и собранного файла, существующие тесты проходят.

## 4 Собрать первый полный сценарий

**После подтверждения этапов 2 и 3.** Связать статический анализ, сборку, проверку платформой и минимальный исполнитель тестов. Для каждого запуска использовать подготовленную рабочую копию базы и сохранять результаты отдельно.

**Готово, когда:** одна команда проходит весь цикл для внешней обработки; есть проходящий и намеренно падающий тест; повторный запуск даёт тот же существенный результат. Общий отчёт указывает проверенный артефакт, выполненные этапы и причины отказа. Тайм-аут или недоступная платформа не выглядят успехом, эталон базы сохраняется.

**Это первая рабочая версия harness для внешних обработок.** Она ещё не означает поддержку всех режимов и объектов 1С 7.7.

## 5 Расширять по реальным задачам

Подключить первый прикладной проект с согласованными ожидаемыми результатами; кандидаты — КУДиР и 76.АВ. Из подтверждённых случаев добавлять регрессии и правила анализа. После устойчивого CLI подключать CI на подходящем стенде и MCP над теми же операциями.

**Готовность каждой такой задачи:** новый случай воспроизводится тестом, результат объясним, прежние проверки проходят. Полная пересборка MD, SQL-стенды и автоматизация форм получают отдельные задания по потребности.

## Как двигаться по карте

Подробно расписываем только ближайшую задачу: вход, результат и проверка готовности. После её завершения обновляем статус здесь и выбираем следующий небольшой шаг. Этапы 2–5 пока являются направлениями; сроки и объём уточняем перед реализацией, особенно после эксперимента с платформой.
