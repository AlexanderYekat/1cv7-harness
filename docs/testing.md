# Проверки без 1С

Задача 034: `research/forms/tests/test_journal77.py` проверяет обязательность
копии и режима журнала, порядок создания/захвата ссылки, отсутствие
программной записи/проведения в генерируемом контроллере, отказ при
неоднозначном ответе, старом/чужом HWND и неполном свидетельстве UI-перехода.
[Нативный пример](../examples/journal-document/README.md) проверяет создание,
повтор, отмену без новой записи и продолжение после намеренного failure.
`scripts/verify_journal_document77.py` независимо перечитывает протоколы,
данные/проводки, JSON/JUnit, хеши и очистку; использует общую сверку
повторного открытия из `verify_document_form77.py`.

После установки пакета: `python -B -m unittest discover -s tests -v`.
Набор содержит прежние тесты линтера, протокола, диалога и безопасной
сборки/извлечения, а также 58 тестов этапа 4 (`test_deadlines77`,
`test_config77`, `test_backends77`, `test_run77`, `test_native77`,
`test_screenshots77`): сроки раздела 8.5, профили, полный цикл через
симуляционный бэкенд, контракт нативного launcher (поддельный launcher),
скриншоты. Тесты используют синтетические CFB, переносимые протоколы и
управляемые часы; 1С, база и прикладной корпус не нужны.

Полная проверка установки и поставки одной командой (setuptools из
`requirements-build.txt` и pip должны быть установлены):

```powershell
python scripts/verify_package77.py
```

Скрипт копирует только исходники поставки в новый каталог `.artifacts/package77`,
строит sdist, из него wheel, создаёт чистое venv без системных пакетов,
устанавливает wheel без сети и запускает тесты из другого каталога без
PYTHONPATH. Проверяет консольную команду, `python -m`, наличие словаря,
единственную установленную дистрибуцию и P1/P2. Логи и summary.json сохраняются
также при отказе. Каталог каждого запуска новый; скрипт не удаляет деревья.
`--output` выбирает отсутствующий каталог, `--build-python` и `--runtime-python`
позволяют отдельно выбрать интерпретаторы сборки и проверки, `--command-timeout-s` —
срок каждой команды (по умолчанию 300 с; на нагруженной машине тесты установленного
пакета, запускающие много процессов, могут его превысить).

`test_mcp77` (задача 014) запускает настоящий сервер `python -m harness77 mcp` и
сравнивает ответ каждого инструмента с той же командой CLI; прогресс, отмена и
закрытый stdin проверяются сервером в процессе теста с поддельной операцией. Тесты
запускают много процессов Python: на нагруженной машине набор идёт 10–15 минут,
а проверки с порогом времени (`test_native77_long`) могут его превысить.

Отрицательные проверки включают повреждённую/неоднозначную ERT, NUL,
неверную кодировку, символ вне CP1251, существующий выход и hardlink на вход,
гонку создания результата, изменение входа, порчу временного файла,
ошибки синхронизации/публикации/очистки и изменение постороннего потока/каталога.
Сборка проверяется при переходах между обычным и mini-потоком.

Три проверки symlink могут быть пропущены, если Windows не разрешает их создание;
это явно отражается в итогах. В sandbox Windows вызов `resolve(strict=True)`
может получать отказ доступа даже при доступном чтении. Такой запуск не считается
успехом: для приёмки требуется среда с доступной проверкой файловой идентичности.
При ограниченном TEMP задайте TEMP/TMP в доступный каталог до запуска Python.

`test_suite77` (задача 029) выполняет несколько полных циклов через simulation:
раздельные артефакты и run_id, продолжение после провала, ожидаемый отрицательный тест,
ошибки профилей, отмена, отказ продолжать после непроверенной очистки и чужого/пропавшего
отчёта, счётчики и Unicode JUnit. `test_mcp77` проверяет запуск набора через настоящий
MCP-сервер. Нативный пример 025–028 и его команды — в
[examples/scenario-suite](../examples/scenario-suite/README.md).

Исследовательские тесты запускаются отдельно, по набору на каталог:
`python -B -m unittest discover -s research/platform77/tests -p "test_*.py" -v`, так же
`research/forms/tests` и `research/kudir/tests`. Им достаточно checkout: `ert_module`
и `compiler_protocol77` берутся из `src` этого репозитория, соседний `1cv77-devtools`
не нужен. Они не доказывают работу с настоящей 1С: это делает нативная приёмка.

Задача 030 расширяет `research/forms/tests/test_fixture77.py`: обязательная копия,
документ и явные тесты `post`/`verify`, несовпадение возврата со свежим состоянием,
отказ/исключение и блокировка отсутствующего или неоднозначного результата.
Нативные ожидания — [в задании](tasks/030-document-posting.md), запускаемые наборы
с проверкой проводок — [в примере](../examples/document-posting/README.md).
`scripts/verify_posting77.py` перечитывает протоколы, ответы контроллера, результаты,
очистку и JUnit; отсутствие проводок после ожидаемого отказа проверяется отдельно
от возврата `Провести`.

Задача 032 использует прежний контракт `fixture_operations` без новых команд.
`research/forms/tests/test_rollback77.py` проверяет, что свидетельство отката
отклоняется без точного одиночного маркера чтения частичной проводки перед
ошибкой/отказом, при неправильной сумме, количестве проводок или другом модуле.
Генератор также отказывает при неизвестной структуре модуля проведения.
Нативные ожидания — [в задании 032](tasks/032-posting-rollback.md), команды —
[в примере](../examples/posting-rollback/README.md). `scripts/verify_rollback77.py`
независимо сверяет частичную запись, последующий откат, восстановление,
сохранённые поля документа, JSON/JUnit и очистку; `--test-log` дополнительно
требует успешное завершение переданных журналов unittest.

Задача 033 добавляет `research/forms/tests/test_reopen77.py`: нельзя повторно
открыть чужую ссылку, принять отсутствующий/неоднозначный ответ, использовать
окна закрытой формы или считать старое закрытие доказательством закрытия новой.
Проверяется отказ продолжать, если контроллер сообщил успех, но HWND остались.
Нативный [пример](../examples/document-form-cycle/README.md) сохраняет и проводит
документ через штатную форму, закрывает его через 1С++ System.CloseForm и заново
проверяет поля той же ссылки. `verify_document_form77.py` независимо читает
протоколы/ответы шагов, уничтожение окон, поля/проводки, JSON/JUnit и очистку.
`--excluded-run` сохраняет хеши и проверяет очистку исследовательских попыток,
`--regression-report` связывает итог с отдельными отчётами регрессии.

## CI

`.github/workflows/ci.yml` (задача 016) запускается на GitHub при push в любую ветку,
при pull request и вручную:

- `windows` — Windows Server 2025, Python 3.11, 3.13 и 3.15: установка, как в
  [development.md](development.md), тесты продукта и три набора исследования;
- `package` — Windows, Python 3.13: `scripts/verify_package77.py`; `summary.json`,
  журналы команд и дистрибутивы — артефакт `package77` запуска;
- `linux` — Ubuntu 24.04, Python 3.13: тесты продукта; тесты, которым нужна Windows,
  пропускаются с причиной.

Итоговое задание `ci` зелёное, только если прошли все три; оно — единственная обязательная
проверка ветки `master`, поэтому смена версий Python в матрице не требует перенастройки
защиты. Сводка каждого задания (`scripts/ci_summary77.py`) перечисляет пропущенные тесты
с причинами и упавшие тесты. Dependabot (`.github/dependabot.yml`) раз в месяц предлагает
одним pull request обновление закреплённых действий; `setuptools` закреплён вручную —
`verify_package77` сверяет его версию. На runner нет 1С, поэтому сверка каталога с установленной
платформой пропускается.

CI не запускает настоящую 1С 7.7: платформа, базы и лицензия есть только на стенде
владельца, а собственный runner в публичном репозитории выполнял бы на этом стенде код
из чужих pull request. Нативная приёмка остаётся локальной. Повторить CI локально —
те же команды в чистом клоне и новом venv:

```powershell
git clone . $env:TEMP\harness77-ci; cd $env:TEMP\harness77-ci
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements-build.txt
.\.venv\Scripts\python -m pip install --no-build-isolation -e .
.\.venv\Scripts\python -B -m unittest discover -s tests -v
.\.venv\Scripts\python -B -m unittest discover -s research/platform77/tests -p "test_*.py" -v
.\.venv\Scripts\python scripts/verify_package77.py
```

Рабочий каталог владельца может скрыть зависимость от неотслеживаемых файлов
(`1cv77-devtools`, `.local`); чистый клон её покажет.
Локальный корпус проверяется отдельно по хешам, без изменения оригиналов;
не включайте базу и прикладные ERT в переносимый набор.
