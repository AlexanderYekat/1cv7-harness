# 110. Упростить fixture и reader для «Оказания услуг»

Задача поставлена после приёмки 0.15.0 и принята владельцем 18 ноября 2026 года.
В примере 104 автор вручную создаёт семь справочных записей в fixture и собирает JSON
в reader. Теперь автор задаёт данные и сопоставление полей в одном TOML,
а ожидаемые сохранённые значения по-прежнему задаёт отдельно.
[Пример и команды](../../examples/services-fixture/README.md).

На подготовке Python формирует два обычных тела функций 1С 7.7 для уже
существующих `fixture_setup_file` и `fixture_verify_file`. Создание ссылок,
нулевые налоги и обход строк переиспользуются при изменении входных данных.
Reader создаёт новый объект `Документ.ОказаниеУслуг`, открывает точную
ссылку fixture и читает строки, итоги и реквизиты после записи из формы.
Проверки из 104 сохранены, добавлен числовой `/service_type`.

Это рецепт для одного прикладного сценария. Профиль, файловые входы и API
продукта используют прежний контракт. Поля и правила других конфигураций
потребуют своих рецептов.

## Критерий нативной проверки

Использовать неизменные шаги 104, подготовленный fixture/reader и один
`expected.json` на трёх фазах. После исходного успешного запуска вставить
`ТипУслуги = 2` в обработчик `ПриЗаписи` только в копии конфигурации.
При успешных UI-записи и переоткрытии независимая проверка должна дать одно
расхождение `/service_type`, ожидаемое `1`, фактическое `2`. После
восстановления оригинального модуля то же ожидание должно пройти.
Сверить содержимое fixture/reader/steps/expected, остальные потоки MD,
исходную базу, реестр, процессы, удаление копии и блокировки.

## Результат

Нативная проверка завершена 18 ноября 2026 года на Windows / 1С 7.70.027 /
DBF с установленным опубликованным wheel 0.15.0. Исходный, испорченный и
исправленный варианты дали `passed → failed → passed` через `run`.
Во всех трёх фазах прошли 19 UI-шагов, в том числе запись и переоткрытие
той же ссылки. При ошибке reader успешно прочитал JSON, а структурированное
сравнение обнаружило только `/service_type`, ожидаемое `1`, фактическое `2`.
После исправления сохранённое значение снова `1`. Остальные значения, включая
суммы строк `50` и `90` и итог `140`, совпали во всех прогонах.

Входы fixture, reader, шагов и ожиданий во всех отчётах сверены по SHA-256.
Из 3598 потоков MD в отрицательном контроле изменён один поток модуля формы.
После исправления модуль совпал с исходным побайтно. База, реестр и чужие
процессы сохранены. Все сеансы завершены штатно, копия и lock удалены.
[Отчёт трёх запусков](../../.artifacts/s110-services-cycle/verified.json),
[контролируемая правка](../../.artifacts/s110-services-cycle/regression.diff).

Автор редактирует 13 содержательных строк TOML вместо 54 строк тел fixture
и reader из 104. `expected.json` остаётся самостоятельным входом. Дополнительно
проверены детерминированная генерация, имена с кавычками, изменение количества
строки и отклонение дублирующих ключей и неверного типа количества.
