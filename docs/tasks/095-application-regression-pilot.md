# Задача 095. Пилот прикладной доработки с регрессионным тестом

Дата — 13 ноября 2026 года. Продолжение [094](094-project-init.md),
принятой владельцем 13 ноября. Реализация и нативная проверка 095 завершены;
результат принят владельцем 13 ноября 2026 года.

## Охват и ожидания до запуска

Выбран настоящий модуль `Документ/ГотоваяПродукция/МодульДокумента.1s`
на квалифицированной DBF-базе 7.70.027. Пилот использует контролируемую
регрессию: исходный модуль корректен, новый дефект исходной базы не заявляется.
В копии одна строка `Операция.Сумма = Сумма;` заменяется на
`Операция.Сумма = Стоимость;`. Цена теряет множитель количества.
Исправление возвращает перенос полной суммы строки.

Один неизменный регрессионный тест:

1. Создать товар и документ с двумя строками; штатной формой изменить
   количество первой на 3. Строки — 3 × 10 = 30 и 2 × 20 = 40, итог 70.
2. Записать и провести через UI, повторно открыть ту же ссылку.
3. Независимым объектом прочитать поля, ссылки товара и все проводки
   Дт 43 Кт 40. Ожидаются две проводки с количествами 3/2 и суммами 30/40.

Baseline должен пройти. Регрессия должна сохранить правильные поля/UI,
но записать в проводки суммы 10/20 и провалить ровно
`persisted-document-and-entries`. Исправление и повтор на новой копии
должны пройти с прежними ожиданиями. Тест, ERT-модуль, шаблон и fixture
между фазами не меняются. Меняется только выбранный прикладной модуль.
Проверка не правит проводки и не вызывает проведение программно.

Этот пилот не добавляет новую бизнес-функцию: он показывает полный цикл
изменения реального BSL-кода, обнаружения регрессии и восстановления
корректного поведения при неизменном тесте.

## Реализация

Используется принятый wheel **0.4.0**, без новой версии или изменений
runtime. В новом venv установлена только дистрибуция harness77.
Stand-init создаёт forms-стенд, project-init — новый каркас. Его обычная
адаптация под приложение заменяет тестовый ERT-модуль на принятый form probe,
подключает сценарий 033 и каталог конфигурации. Это входы прикладного
проекта, не подмена launcher или установленного runtime.

`md-extract` читает исходную MD и извлекает модули/индекс. В проект копируются
только выбранный модуль и modules.json для проверки устаревшего шаблона.
Сохраняются baseline/regression/fixed, прямой и обратный unified diff.
Каждая фаза отдельно собирает плановую MD через md-build. Независимый
аудит сравнивает все потоки и метаданные каталога: при регрессии отличается
только поток выбранного модуля; остальные фазы совпадают с исходной MD.
Результат автоматической сборки run должен иметь тот же SHA-256, что план.

Каждый run получает свежую проверенную копию. Doctor перед каждой фазой
проверяет предпосылки. Хеши project.toml, тестового ERT-модуля, шаблона и
scenario.json сохраняются до первого запуска и сверяются после всех фаз.
Общий verifier 033 получил только явный expected_md_hash: прежнее значение
по умолчанию сохранено, проверка хеша не отключается.

Входной kit не содержит MD, готового модуля базы, runtime-копии или launcher.
Извлечение и исполнение выполняются установленными командами из другого CWD,
без PYTHONPATH/PYTHONHOME и checkout-импортов. База и DLL остаются явными
квалифицированными зависимостями стенда.

## Воспроизведение

[Самостоятельный пример](../../examples/application-pilot/README.md).

```powershell
python -B examples/application-pilot/prepare.py --application .artifacts/s92-kit-final --stand-inputs .artifacts/s94-kit --output .artifacts/s95-kit-final
.artifacts/s95-kit-final/venv/Scripts/python.exe -B .artifacts/s95-kit-final/run.py --output .artifacts/s95-final2
```

Установка нового venv из wheel описана в примере. Для повторного прогона
нужны новые kit/output. Ожидаются фазы baseline/regression/fixed/repeat-fixed
с исходами passed/failed/passed/passed, коды CLI 0/1/0/0. Полная сверка
проверяет UI, raw-протоколы, сохранённые данные/проводки, SHA-256 и очистку.
Нормальный существующий внешний сеанс разрешён как неизменный baseline;
контроллер проверяет его идентичность и сохраняет, а появление нового
процесса во время запуска останавливает собственный сеанс.

## Полученный результат

Серия `.artifacts/s95-final2` выполнена из чистого установленного venv:

- **baseline — passed/0**, `380b74af-2cf2-4bd3-976f-d884f46227bb`.
- **regression — failed/1**, `bb4341de-593c-406c-8c96-fb68f9d1aeee`.
  Поля документа, суммы 30/40, итог 70, запись/проведение и повторное открытие

- **fixed — passed/0**, `670b2adc-08d4-4557-8f09-bbcea298bb3f`.
  Проводки вернули 30/40 с количествами 3/2.

  Тот же результат на ещё одной свежей копии.

Извлечены 494 модуля. Каждая из четырёх сборок независимо сверена по **3598
потокам** и метаданным каталога MD. При регрессии изменён только
`TypedText/Transact_Number13062/MD Programm text`; другие потоки и формы
сохранены. SHA-256 регрессионной MD:
`c75e359a6ef20e04627d0225a620ac6657dd660bbc789782ab96198066181f6e`.

`931b26eb2e388ba3000196ab024351e65cb324e02e885dc4cef5be68059ecfa1`.
MD внутри каждого run совпала с соответствующей плановой сборкой.

Хеши project.toml, тестового ERT-модуля, шаблона и сценария не изменились.
Независимая повторная сверка подтвердила raw-протоколы UI, сохранённые данные,

## Сохранённая первая попытка

`.artifacts/s95-final`: во время baseline появился новый внешний процесс
1С, которого не было в исходном инвентаре. Контроллер остановил только
свой сеанс с `concurrent process inventory changed`. До отказа UI и чтение
данных вернули правильные 30/40, но запуск blocked/2 не считается
успешным прикладным результатом. Own server PID 11124 завершился с 0;
очистка в целом не подтверждена (`cleanup_verified=false`, в том числе
из-за смены инвентаря), чужие процессы сохранены. Копия удалена, замок
освобождён, источник, реестр, guard и входы не изменились. Поле processes
в общей сверке закономерно false.

Последующее чтение CIM с обычными правами установило внешний PID 18812,
parent 7676, время создания 13 ноября 09:46:38. Он не завершается и не
перезапускается. Полный doctor подтвердил доступность исходной базы и ready/0
с предупреждением о внешнем процессе. Новой серией этот стабильный процесс
учтён в baseline, проверка внутри штатного контроллера не ослаблялась.
Первый комплект и отказ сохранены отдельно; автоматических повторов нет.
