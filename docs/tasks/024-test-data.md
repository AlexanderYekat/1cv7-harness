# Этап 5, задача 024: тестовые данные на копии базы и существующие объекты

Дата: 23 октября 2026 года. Предшествующая задача — [023](023-catalog-journal-forms.md).
Статус: **принято** владельцем 23 октября 2026 года.
Владелец поручил выполнить задачу и дополнить её запускаемым примером.
[Отчёт проверки](024-test-data-acceptance.md).

## Зачем

После 023 launcher открывает новые формы объектов. Теперь тест должен заранее подготовить
известные ему записи на свежей копии базы, открыть конкретную запись, проверить её поля и
обработчики. Для подчинённого справочника тест готовит также владельца.

## Охват

1. Код подготовки данных на языке 1С 7.7 в профиле запуска: выполняется один раз перед
   проверкой и открытием формы, возвращает ссылку на записанный объект. Данные создаются
   только на копии, которую `run` сделал для этого запуска с `[configuration]`. На исходной
   базе такой профиль отвергается до запуска 1С. Можно использовать неизменённую конфигурацию.
2. Открытие существующего элемента, группы справочника и документа по полученной ссылке.
   Тип, вид и признак группы должны соответствовать `form_object`. Пустая ссылка или другой
   объект — явный отказ; произвольный первый объект базы не выбирается.
3. Открытие нового элемента подчинённого справочника с подготовленным владельцем.
   Владелец должен иметь нужный вид и быть записанным элементом. Его передача проверяется
   внутри открытой формы. Существующий подчинённый элемент также открывается по своей ссылке.
4. Проверка начальных значений формы, нажатия кнопки и результата обработчика прежними
   средствами launcher. Дополнительный код проверки после закрытия формы может повторно
   прочитать запись из базы; его результат сравнивается с `expect_value` обычного теста.
5. Сквозной запускаемый пример: создать запись с известным значением, открыть её форму,
   изменить значение, нажать тестовую кнопку записи, прочитать запись заново и сравнить
   результат. Повторить сценарий на новой копии с тем же результатом.

Новый язык сценариев, Gherkin, запись действий пользователя, универсальная модель фикстур,
изменение структуры метаданных и работа с производственной базой в задачу не входят.
Пример использует код 1С, профиль TOML и существующие команды `harness77 run`.

## Приёмка

Ожидания нативных случаев записываются до запусков. Проверить элемент, группу, документ,
существующий подчинённый элемент и нового с владельцем; проверить отказ при неверной ссылке,
ошибке подготовки и запуске без копии. Повторить пример дважды; намеренно неверное ожидание
должно провалить тест. Во всех случаях копия удалена, исходная база и список баз прежние.
Переносимые тесты проверяют контракт, отказ до запуска без копии и распространение ошибок;
прежние проверки форм и поставки проходят. Работа в настоящей 1С подтверждается отдельно.

Серия 0, ожидания до прогона (`research/forms/probe_test_data77.py`):

- `element`, `group`, `document`: форма записанного объекта показывает подготовленное наименование
  или комментарий; `result` содержит то же начальное значение, `run` — `passed`.
- `child`, `owner`: существующий договор и новый договор с владельцем показывают внутри формы
  владельца «Harness77 владелец 024»; существующий — также своё наименование. `run` — `passed`.
- `example`, `example-repeat`: поле нового имени получает ввод, тестовая кнопка присваивает его
  наименованию и записывает объект; новая выборка по ссылке после закрытия возвращает
  «Harness77 изменено 024». Оба запуска — `passed`, исходное значение в каждом — «Harness77 банк 024».
- `wrong-kind`, `wrong-group`, `empty`, `setup-error`: `blocked` с причиной подготовки данных,
  форма не открывается. `wrong-expectation`: `failed` только на сравнении результата чтения из базы.

Серия 0b/0c: элемент, группа, существующий договор и новый с владельцем прошли; пример ввёл
новое имя и прочитал его после записи. У исходного диалога документа «Доверенность» 1С растянула
табличную часть и сдвинула нижние поля на 33 px: значение комментария верное, проверка геометрии
дала отказ (12,34 px). В 022 проверялась изменённая форма высотой 240, а исходная — 220.
Серия 1 проверит документ с тестовой кнопкой ниже прежних элементов и высотой 240: ожидаются
соответствие описанию, начальный комментарий и тот же комментарий из обработчика кнопки.
Порог сравнения геометрии остаётся прежним. Исходная форма с восстановленным размером пока
не считается прошедшей проверку геометрии.

Серия 2, ожидания до прогона: `unwritten` — отказ по незаписанной ссылке;
`wrong-owner` — отказ по виду владельца; `verify-error` — ошибка дополнительной проверки
после успешных действий формы даёт `failed`; `setup-once` — повторное чтение и подсчёт
записей по обоим тестовым именам возвращают новое имя и `count:1` (подготовка не повторилась
между `check` и `open`). Запуск примера из `examples/test-data` проверяется отдельной командой.

Серия 3: результат `verify` должен оцениваться объявленным тестом, как и остальные операции:
повтор `verify-error` с `expect = "passed"` — провал теста; новый `verify-negative` с явным
`expect = "failed"` — ожидаемая отрицательная проверка, итог `passed`. Инфраструктурного отказа
при пойманной ошибке исполнения проверки нет; она остаётся в диагностике операции.

## Пример для пользователя

Сценарий в обычных словах: «Подготовить тестовую запись; открыть её форму; убедиться, что
видно начальное значение; изменить его; нажать кнопку записи; проверить сохранённое значение».
Исходники, профиль и команда воспроизведения — в
[examples/test-data](../../examples/test-data/README.md). Это пример использования задачи 024,
а не новый язык тестов. Он создаёт банк,
открывает его форму, вводит новое имя в дополнительное тестовое поле, записывает его кнопкой
и читает запись заново по ссылке. Подготовленный профиль находится локально в
`.local/stage24-example`; оба запуска примера прошли с одинаковыми значениями.
