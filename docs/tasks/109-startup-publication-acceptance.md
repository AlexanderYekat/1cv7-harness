# 109 — проверка устойчивой публикации startup.json

Техническая проверка завершена 16 ноября 2026 года. Задача принята владельцем
18 ноября 2026 года. Локальная версия — 0.15.0 (принятые 108 + 109);
публикация ещё не выполнялась.
[Контракт](109-startup-publication.md), [воспроизводимая проверка](../../examples/startup-publication/README.md).

## Причина и изменение

В сохранённых отказах 108 и проверки релиза 0.14.0 единственная замена
startup.json.tmp → startup.json завершилась WinError 5. На том же Windows
открытый reader без FILE_SHARE_DELETE воспроизводит точный WinError 5;
после закрытия операция проходит. Прежний JSON остаётся целым. Это доказательство
механизма отказа, а не установление процесса, который держал исторические файлы.
[Microsoft: совместный доступ и удаление](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew),
[замена файлов](https://learn.microsoft.com/en-us/windows/win32/fileio/moving-and-replacing-files).
Пробы: [.artifacts/s109-probe/result.json](../../.artifacts/s109-probe/result.json).

StartupTrace публикует полностью сериализованный JSON через уникальный временный
файл в том же каталоге. На Windows перед заменой проверяется DELETE-доступ
к существующей цели; проверочный handle закрывается до замены. Ошибки Windows
5/32/33 на этом этапе или при замене допускают до 26 попыток в пределах секунды,
с паузами до 40 мс и проверкой оставшихся сроков/отмены. Ошибки создания/записи
и другие коды не повторяются. ACL/readonly автоматически не снимаются.

Первая публикация входит в защищённую область сеанса. Финальная диагностика
выполняется после независимой очистки собственных ресурсов; её отказ сохраняется
в итоговом отчёте рядом с первичной ошибкой. При удерживаемом файле сведения
startup доступны в памяти итогового platform-result.json, старый startup.json
не выдаётся за свежий. Временные файлы своей публикации удаляются.

Baseline чужих процессов и удерживаемые handles фиксируются до диагностической
публикации registration_acquired. Поэтому её отказ до создания отладчика имеет
доказательства сохранности процессов; suite может продолжиться с прежней строгой
проверкой очистки. Условие продолжения suite не ослаблено. Если baseline ещё
не получен, сохранность чужих процессов не выдумывается.

## Что выявили предварительные серии

- `.artifacts/s109-native`: повторов недостаточно без предварительной проверки.
  В опыте короткого open deadline сам Path.replace вернулся с отказом через
  36,85 секунды. Добавлены DELETE-preflight и проверка срока после операции.
- `.artifacts/s109-native-r2`: единственная замена старого runtime иногда ждёт
  дольше 200 мс и успевает пройти после снятия reader. Старые отрицательные
  контроли теперь удерживают reader до записи отказа.
- `.artifacts/s109-native-r3`: семь отдельных run совпали с ожиданиями, но CLI
  suite правильно остановился после persistent-pre: baseline ещё не был снят
  к моменту отказа trace. Исправлен порядок получения свидетельств; добавлена
  регрессионная проверка с чужим процессом и очисткой временной регистрации.

Эти попытки сохранены отдельно и не включаются в окончательную квалификацию.
Синхронный вызов Windows нельзя прервать лимитом повторов; preflight не устраняет
гонку между проверкой и заменой. Лимит ограничивает повторы/ожидания, а проверка
после вызова сохраняет классификацию timeout/cancel. Конкретный держатель старых
блокировок остаётся неизвестным.

## Нативный стенд

Windows / 1С 7.70.027 / DBF, исходная база base-for-test, изолированная копия
harness77-copy. Проверяется установленный окончательный wheel без PYTHONPATH;
исходники runtime и файлы пакета сверяются с wheel. Прежний контроль — принятый
wheel 108. Диагностический launcher удерживает настоящий reader и наблюдает
реальные ошибки ядра; файлы установленного пакета и бизнес-модуль не меняются.
На новом runtime конфликт обычно обнаруживается preflight как WinError 32,
до медленной замены, которая на старом runtime даёт WinError 5.

Используется неизменённый сценарий 108: восемь шагов, точный check_combo,
пустые строки/дубликаты/пробелы, select и подтверждение обработчика.
Отдельные обычные run baseline/after-failure/after-cancel используют исходный
bundled runtime без диагностического перехвата. Семь основных случаев повторяются
через CLI suite и MCP; отдельно проверяются отмена и следующий обычный run.

Окончательная серия: **25 попыток — 23 на исправленном runtime и два старых
отрицательных контроля**. Оба старых контроля воспроизвели WinError 5 до старта
отладчика и после ownership. На исправленном runtime **13 passed и 10 ожидаемых
blocked**, все исходы совпали с ожиданиями.

Шесть временных блокировок восстановились за 211,637–229,363 мс с recovered=true,
затем все восемь UI-шагов прошли. Шесть постоянных блокировок остановили повторение
за 1000,07–1003,13 мс; число попыток не превысило 26. Прежний JSON при отказе
сохранил SHA-256, собственных временных файлов не осталось. Ошибка финальной
публикации видна в итоговом отчёте и не пропустила очистку. Три уже запущенных
сервера в persistent-owned очищены по проверенному ownership; успешные сценарии
завершились штатно, без forced cleanup.

Три коротких срока дали timeout_phase=open, отмена дала cancelled=true и сохранила
первичную причину; reader освобождён через 0,176 с. Следующий обычный запуск прошёл.
Оба suite завершили все семь сценариев (4 passed, 3 ожидаемых blocked), включая
успешный after-failure. JSON/JUnit и SHA-256 ссылок согласованы. MCP отвечает на
ping во время и после suite, сервер завершился с кодом 0.

[Основная сверка](../../.artifacts/s109-native-final/verified.json),
[независимое перечитывание](../../.artifacts/s109-native-final/independent.json).
Независимый аудитор сверил исходы всех 25 попыток, байты входов с неизменённым
примером 108, хэши содержимого build/steps, 73 установленных файла с wheel и
33 native-исходника с manifest. При написании аудитора исправлена его проверка:
inputs.source.sha256 — хэш пути, а хэш содержимого находится в build.source_sha256.
Нативные результаты и входные ожидания при этом не менялись.

До/после каждого квалификационного запуска совпали листинг исходной базы,
MD/DD/DLL-хэши, снимки реестра и чужих процессов; копия и lock отсутствуют.
Начальный снимок окончательной серии также совпал с тремя предварительными.

Квалификация ограничена прежним Windows/1С 7.70.027/DBF-стендом. Постоянный запрет
записи должен завершаться blocked с доказанной очисткой, а не обходом прав.
