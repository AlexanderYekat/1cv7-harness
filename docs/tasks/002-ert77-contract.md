# Пробы синтетических ERT на текущем стенде

Обновлено 12 октября 2026 года. Минимум синтетических ERT проверен нативно:
`ok → syntax → ok`, `unused-syntax`, `unused-name`, `runtime`. Подтверждены
сообщения компилятора, разделение check/execute, UUID, 42 и штатное завершение
рядом с открытыми сеансами. [Свидетельства и команды](../../research/platform77/README.md).
Модальный wait также воспроизведён нативно: внешний тайм-аут 30 с, закрытие
точного предупреждения с UUID, возврат из COM и корректная очистка. Сам wait
остаётся blocked; история отказов и повторов приведена в журнале.
После `507d2dd` профиль `challenge-only-v2` прошёл три заранее заданных цикла
`ok → wait → ok`; завершение 2,444–7,357 с при прежнем пределе 10 с.
Два прежних превышения (последний `server_released` на 10,238 с) и старые
серии остаются blocked. Проверена повторяемость этого синтетического сценария
на текущем стенде, а не произвольная нагрузка или зависание COM.

Используется прежняя существующая база и точные хеши стенда. Разметка берётся
из локальной `ExtForms/rp14q1.GRP/FIO.ERT` с SHA-256
`096e1a05f871158b9ec5adaafa397adca87cee4aae8cd6f28f130080ac318b4a`.
Исходная обработка не запускается: весь модуль заменяется безопасным
синтетическим кодом; все остальные потоки остаются побайтно прежними.
Модуль после сборки извлекается обратно и сравнивается с исходником.

Каждый прогон получает новый UUID, отдельную ERT с UUID в коде и каталог.
Платформа получает полный путь именно к этому файлу. `ОткрытьФорму` выполняется
дважды: команда `check` разрешает загрузку/компиляцию, но не вызывает контрольную
функцию; `execute` вызывает её явно. `ПриОткрытии` возвращает маркеры через
переданный список значений и использует `СтатусВозврата(0)`, чтобы не показывать
форму. Нулевой результат открытия сам по себе не доказывает успех: нужны
точные маркеры UUID из загруженного кода и завершённый протокол MessageView.
Это проверка загрузчиком Предприятия, не команда проверки Конфигуратора.

Варианты: `ok` (42), `syntax` (ошибка в строке 2), `unused-syntax` (ошибка
в невызванной процедуре, строка 6), `unused-name` (неизвестная процедура,
строка 6), `runtime` (параметр-делитель 0 при исполнении). Для `unused-name`
фактическое поведение определяет охват; неожиданное поведение сохраняется
как несоответствие, а не замена ожидания. Отдельный `wait` предназначен для
контролируемого модального ожидания внутри самой 1С; его результат всегда
требует разбора тайм-аута, не принимается как обычный успех.

### Модальный тайм-аут и восстановление

Для `wait` обязателен `--identity-dll`. Контроллер запускает последовательно
`ok → wait → ok` командой `qualify_wait77.py`, каждый раз с новым UUID и
отдельным собственным сеансом на прежней базе. Чужие сеансы сохраняются.
Серия останавливается при первом несоответствии, AV или непроверенной очистке.
`--cycles 3` заранее записывает план из девяти запусков и требует три подряд
полных цикла; повторов после отказа нет. Повторный UUID блокирует серию даже
при успешных отдельных отчётах. Временные пределы проверяются как часть профиля.

Таймер 30 с начинается отдельно для каждого вызова ERT по атомарному маркеру
клиента. При истечении `wait` сохраняются исходные события, отсутствие возврата
из COM и завершённого протокола, окна только собственного private desktop.
Разрешено закрыть ровно один видимый стандартный диалог `#32770` собственного
PID/TID с точным UUID в Static, единственной доступной кнопкой `OK` с ID 2
и отключённым окном-владельцем того же потока. Этот ID установлен по нативному
снимку: первая проба с предположением IDOK=1 отказала и применила принудительную
очистку собственных процессов, её отчёт остаётся blocked.
Перед `WM_COMMAND/BN_CLICKED` заново проверяются
удерживаемый HANDLE, время создания, desktop и весь снимок диалога. Поиск на
Default desktop, переключение desktop, мышь и клавиатура не используются.
Неизвестные или неоднозначные окна не закрываются.

После сообщения даётся 10 с на возврат вызова; затем действует прежний предел
завершения. Нужны окончательные UUID-маркеры, полный протокол и все 16 шагов
выгрузки, нулевые exit code, отсутствие AV/принудительной остановки, проверенная
очистка и сохранение исходных сеансов. Непредвиденный отказ оставляет прежнюю
аварийную очистку только процессов с доказанным владением.

Исходный `run.json` для `wait` всегда остаётся `blocked`, CLI 2, операция —
`blocked/outcome=timeout`. `timeout_verified=true` означает доказанный ожидаемый
тайм-аут и корректное завершение после закрытия синтетического диалога.
`shutdown_assessment` также остаётся blocked из-за `timeout_phase`; любые
дополнительные нарушения запрещают подтверждать этот сценарий. Отдельный
`qualification.json` может стать passed только после нового `ok` с результатом
42. Это проверка восстановления следующим сеансом, не произвольного зависания
и не зависшего вызова внутри выгрузки 1CPP.

Для защиты рабочего стола пробы запускают CDB и 32-битный клиент на отдельном
Windows desktop, без переключения пользователя, мыши и клавиатуры. Используются
документированные [CreateDesktopW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-createdesktopw)
и [STARTUPINFO.lpDesktop](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow).
Дескриптор desktop закрывается после остановки процессов. Общий предел 145 с,
операции ERT — 30 с, завершения — 10 с; остановка на первом AV сохранена.

Перед отключением 1CPP функция управления освобождает параметры и контекст
ERT, затем клиент освобождает контроллер. Применяется прежняя последовательность
выгрузки, но её пригодность после загрузки ERT должна подтверждаться новыми
прогонами. Проверяются протоколы, UUID, путь, исходные байты, все коды выхода,
отсутствие AV, принудительной остановки, оставшихся процессов и COM-ключей.
В режиме `--identity-dll` это означает отсутствие оставшихся собственных
процессов при сохранении исходных пользовательских сеансов. До Initialize
уникальный GetIDsOfNames-запрос должен быть наблюдён CDB в собственном PID;
проверяются TID и private desktop. Без этого разрешение на открытие базы
не выдаётся. Исходные процессы удерживаются через HANDLE только для чтения
и ожидания; PID без времени создания не считается идентичностью.
Профиль наблюдателя `challenge-only-v2` снимает точки CDB сразу после первого
GetIDsOfNames и печатает пустой `bl` между UUID-маркерами. Разрешение Initialize
требует и точного nonce, и свидетельства снятия точек; посторонний первый запрос
блокирует запуск. После завершения отсутствие дальнейших lookup проверяется
повторно по журналу. `bc *` относится только к точкам этого собственного CDB;
фильтр остановки на первом AV не меняется. `continuous-v1` сохранён только
для сравнения задержек через `run_ert77.py --observer-profile continuous-v1`;
новая серия восстановления требует `challenge-only-v2`.
Диагностика `shutdown_observations` фиксирует замеченный шаг, внешнее время,
накопленное CPU-время собственных сервера/клиента/CDB по удерживаемым HANDLE
и размер журнала; `shutdown_elapsed_seconds` включает ожидание выхода клиента
и CDB. Это выборки контроллера, а не точный профилировщик каждого вызова.
Результат отрицательной проверки остаётся `failed`; итог пробы `passed` означает,
что этот ожидаемый отказ воспроизведён и сеанс корректно завершён.

Обязательный минимум этого этапа: `ok`, `syntax`, восстановление `ok`, затем
отдельные пробы невызванного кода и ошибки исполнения. P05/P06/P07, полный P08,
Конфигуратор и видимая форма учитываются отдельно; не объявлять всю P00–P08
принятой по этому минимуму. Прикладные ERT КУДиР/ККТ не исполняются.
