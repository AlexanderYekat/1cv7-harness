# Этап 5, задача 016: CI на GitHub

Дата: 21 октября 2026 года. Статус: **в работе**. Предшествующая задача —
[015](015-launcher-robustness-acceptance.md). 21 октября владелец закоммитил 015 и выбрал
следующим этапом CI на GitHub.

## Зачем

Большое ТЗ (Р4): «После устойчивого CLI добавить CI, затем MCP». MCP сделан в задаче 014,
а переносимые проверки — тесты продукта (366), тесты исследования (136) и проверка поставки
`scripts/verify_package77.py` — запускаются только вручную на машине владельца. Там внешняя
нагрузка уже давала отказы по времени, не связанные с правкой (`test_d05` в 015). Кроме того,
два заявления пакета ни разу не проверялись: минимальный Python 3.11 (`requires-python`;
у владельца 3.13) и установка на Linux ([development.md](../development.md)).

Репозиторий публичный — `github.com/AlexanderYekat/1cv7-harness`; workflow в нём нет.

## Что делается

- **`.github/workflows/ci.yml`.** Запуск при push в любую ветку, при pull request
  и вручную (`workflow_dispatch`). Три задания:
  1. `windows` — `windows-2025`, Python 3.11 (заявленный минимум), 3.13 (у владельца)
     и 3.15 (новейший): установка по [development.md](../development.md)
     (`requirements-build.txt`, `pip install --no-build-isolation -e .`), тесты продукта
     `tests`, тесты исследования `research/platform77/tests` (после C0 — и `research/forms/tests`,
     `research/kudir/tests`). Пропущенные тесты
     с причинами — в сводке задания.
  2. `package` — `windows-2025`, Python 3.13: `scripts/verify_package77.py` (sdist → wheel →
     чистое venv без сети и без PYTHONPATH → тесты установленного пакета → консольная команда,
     P1/P2). Каталог свидетельств (`summary.json`, журналы команд) — артефакт запуска,
     и при отказе тоже.
  3. `linux` — `ubuntu-24.04`, Python 3.13: тесты продукта. Тесты, которым нужна Windows
     (нативный launcher, WinAPI), пропускаются с причиной; остальное должно пройти без правок
     ожиданий.
- **Безопасность.** `permissions: contents: read`; сторонние действия (`actions/checkout`,
  `actions/setup-python`, `actions/upload-artifact`) закреплены SHA коммита с версией
  в комментарии; секретов нет; событие `pull_request`, не `pull_request_target`; у каждого
  задания срок; новый push в ту же ветку отменяет устаревший запуск.
- **Документы.** [testing.md](../testing.md): что проверяет CI, чего не проверяет и как
  повторить его локально; дорожная карта.

**Не входит.** Настоящая 1С 7.7 в CI: платформа, базы и лицензия есть только на машине
владельца, а собственный runner в публичном репозитории выполняет на этой машине код
из чужих pull request (GitHub не рекомендует self-hosted runner для публичных репозиториев);
там же идут задания `kudir` с общим gate. Нативная приёмка остаётся локальной, как в задачах
004–015. Также не входят публикация пакета, Dependabot и защита ветки `master`
(настройка репозитория — решение владельца).

## Порядок работы

По решению владельца коммиты задачи идут сразу в `master` и отправляются на GitHub (вместе

## Исходы и изменённые правила (до приёмки)

- **C0 опроверг ожидание.** Тесты продукта в чистом клоне прошли (366, 3 пропуска symlink,
  53 с), а тесты исследования — нет: 83 вместо 136 и 8 ошибок `No module named 'ert_module'`.
  `ert_probe77.py` и `build_formex_fixture.py` брали `ert_module` из соседнего
  `1cv77-devtools` (не в Git; по [development.md](../development.md) больше не нужен),
  а `reference77.py` получал оттуда же `compiler_protocol77` побочно. Модули в `src/harness77`
  совпадают с ними байт в байт (без учёта концов строк) — исследование теперь берёт их из
  `src` этого репозитория. После правки в чистом клоне: исследование 136, а также
  `research/forms/tests` (25) и `research/kudir/tests` (17) — они тоже вошли в CI. `kudir`
  берёт свой `ert_module` из своей синхронизации, правка его не касается.
- **Первый запуск** (`dbad156`, [39585013383](https://github.com/AlexanderYekat/1cv7-harness/actions/runs/39585013383)),
  каждое задание — 25–81 с:
  - **C1 опроверг ожидание.** На Windows при всех трёх версиях Python упали 4 теста продукта
    (`test_config77`, `test_form77`, два в `test_mcp77`): `TEMP` runner — короткое имя 8.3
    (`C:\Users\RUNNER~1\...`), продукт приводит пути профиля и отчётов к полному виду
    (`runneradmin`), а тесты сравнивали с непреобразованным временным каталогом. Воспроизведено
    локально с коротким `TEMP`. Дефект тестов: их корень теперь `Path(...).resolve()`; весь набор
    при коротком `TEMP` — 366, как и с длинным. Symlink на runner работают; единственный
    пропуск — сверка каталога с установленной 1С.
  - **C2:** на 3.11 вдобавок упал `test_session77` (нет `timeout_phase`): тест давал сроку
    открытия 0,001 с и ждал, что настоящие `time.monotonic` сдвинутся, а на Windows до 3.13
    они идут шагами ~16 мс. Дефект теста: управляемые часы, как в соседних тестах этого файла.
  - **C3:** 3.15 — те же 4 отказа, что у 3.13, других нет.
  - **C4 как ожидалось:** `package` — `passed`, 366 тестов установленного пакета, 1 пропуск
    (каталог); `verify_package77` задаёт свой длинный `TEMP`, поэтому C1 его не затронул.
  - **C5 как ожидалось:** на Linux 11 отказов, и все — тесты нативного backend
    (`native_preflight: 1C 7.7 requires Windows; this is posix` и его следствия): три
    в `NativeBackendTests`, класс `LongNativeTests`, класс `NativeContractTests`. Они помечены
    `windows_only` (`tests/stage4_fixtures.py`); проверка отказа вне стенда осталась
    на Linux. Остальные 355 тестов прошли на Linux без правок.

Проверки со временем (`test_native77_long`, `test_mcp77`, `test_d05`) на runner могут
оказаться нестабильными: нестабильность исправляется в тесте без ослабления самой проверки
и записывается в приёмку.

## Приёмка

Запуск CI на коммите задачи зелёный во всех заданиях; C2–C6 дали записанные исходы или
исправлены до приёмки; разметка Windows-тестов не скрывает ни одного теста на Windows
(число тестов `windows` не меньше прежнего, пропуски — с причиной). Все прежние тесты
продукта и исследования проходят локально.
