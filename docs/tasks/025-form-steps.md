# Этап 5, задача 025: сценарии шагов на форме

Дата: 25 октября 2026 года. Предшествующая задача — [024](024-test-data.md).
Статус: **принято** владельцем 25 октября 2026 года. Владелец выбрал направление 25 октября 2026 года
из четырёх предложенных. [Отчёт проверки](025-form-steps-acceptance.md).

## Зачем

После 024 тест готовит данные и открывает нужную запись. Действия на форме пока задаются
строкой `actions` с ID окон (`type:4168=…,click:4167`). Проверки возможны в двух местах:
итог обработчиков, записанный протоколом harness77 в модуль формы, и чтение базы после
закрытия формы. Неизменённую форму конфигурации или ERT так проверить нельзя.

Нужен читаемый сценарий в профиле. Шаги называют элементы так, как их видит разработчик:
по идентификатору или подписи. После каждого шага сценарий проверяет, что показывает
форма, что сообщила 1С и какое значение у реквизита. Это шаг к тестам наподобие Vanessa
без своего языка: шаги записываются массивом таблиц стандартного TOML.

## Охват

1. `[platform.parameters] steps` — массив таблиц. Продукт разрешает в `[platform.parameters]`
   массивы строк, чисел, логических значений и таблиц из них; прежние плоские значения
   не меняются. Смысл шагов определяет launcher форм.
2. Виды шагов (в таблице ровно один ключ вида):
   - `{ click = "<элемент>" }` — нажать кнопку или флажок; `closes = true` — нажатие
     закрывает форму;
   - `{ input = "<элемент>", text = "<текст>" }` — перейти в поле, заменить его текст,
     выйти из поля;
   - `{ check = "<элемент>", text = "…" }`, `checked = true|false`, `enabled = …`,
     `visible = …` — что показывает окно элемента;
   - `{ value = "<реквизит>", text = "…" }` — `Строка()` реквизита в контексте открытой формы;
   - `{ message = "…" }`, `{ no_message = "…" }` — есть или нет такая строка среди сообщений
     1С после последнего действия.
3. Элемент ищется в описании формы (ERT или `1Cv7.MD`): сначала по идентификатору, затем
   по подписи без `&`, без учёта регистра. Должен найтись ровно один элемент подходящего
   класса. Иначе, а также для шагов после закрытия формы, кроме `message`/`no_message`,
   — отказ до открытия формы.
4. Шаги выполняются после осмотра открытой формы, по порядку. Действие — сообщение окну
   (прежние правила `OwnedModal`). Затем клиент один раз вызывает 1С: контроллер сохраняет
   сообщения шага и читает запрошенный реквизит. Затем читается состояние окон и
   проверяется ожидание. Первый неуспешный шаг останавливает сценарий. Ошибка исполнения
   1С в сообщениях шага — провал этого шага с текстом и строкой модуля.
5. В режиме шагов форме не нужен протокол harness77: открытие подтверждают
   `ОткрытьФорму() = 1` и найденное окно. Тест `result` проходит, если прошли все шаги
   и форма закрыта контроллером или объявленным шагом. Подготовка и `verify` задачи 024
   работают как раньше.
6. Запускаемый пример на неизменённой форме элемента справочника «Банки»: неверный БИК —
   предупреждение формы при записи; верный БИК и новое имя — «ОК» закрывает форму;
   `verify` читает запись заново.

Gherkin, свой синтаксис, запись действий пользователя, модальные окна, вызванные
обработчиком (`Предупреждение`, `Вопрос`), табличная часть и список, клавиатурный ввод
через систему, снимок `clicked` после шагов не входят в задачу. Отказ должен быть явным.

## Приёмка

Ожидания нативных случаев записываются здесь до запусков. Проверяются сценарии на
неизменённой форме конфигурации и на ERT. Также проверяются: провал ожидания каждого
вида, ошибка исполнения обработчика, недоступный элемент, закрытие формы (объявленное
и необъявленное), отказы до запуска. Регрессия — пример 024 и прежние случаи 022/023.
Переносимые тесты покрывают разбор и разрешение шагов, сгенерированный код 1С и клиента,
а также оценку шагов. Копии удаляются, исходная база и список баз не меняются.

Серия 0 (исследование механизма, форма элемента «Банки» без изменений, банк из `fixture_setup`).
Ожидания до прогона:

- `s-input`: `input` в «Код» заменяет показанный текст на введённый. После выхода
  из поля `value = "Код"` возвращает введённое значение, окно поля показывает его же.
- `s-message`: неверный БИК, нажатие «Записать» — среди сообщений шага есть
  «Возможно, БИК указан неверно.»; при верном БИК (9 цифр, без корр. счёта) такого нет.
- `s-ok`: «ОК» (`#Записать Закрыть`) закрывает форму: окно исчезает, `result` не провален
  закрытием; `verify` читает новое имя.
- `s-error`: кнопка добавлена в форму, её формула делит на ноль. Сообщения шага содержат
  ошибку исполнения со строкой модуля — шаг провален.
- `s-ert`: FIO.ERT с модулем визуальных проб; «Проверка» пишет «Нажато: 1» в «Фамилия».
  `check` показывает новый текст сразу после шага, протокол формы не нужен.

Наблюдать: формат строк сообщений с важностью «!»; поведение `Закрыть(0)` закрытой формы;
нужен ли выход из поля, чтобы значение дошло до реквизита.

Серия 0, итог: `s-message`, `s-ok`, `s-error` совпали с ожиданиями. `s-input` и `s-ert`
провалились на шаге `value`: окно поля показывало введённый текст, а реквизит оставался
пустым. Переход в поле через `WM_NEXTDLGCTL` работает: фокус получает вложенное окно редактора.
`WM_NEXTDLGCTL(0, 0)` фокус не сдвигает: редактор — внук диалога, не его элемент.
В `s-message` и `s-ok` значение до модуля дошло: следующее нажатие перевело фокус на кнопку.
`s-ert` шёл на базе стенда без копии. Сеанс изменил `1SUSERS.DBF`, `SYSLOG/1cv7.mlg`,
`Вера/1Cv7.CFG` и `Вера/1cv7flt.lst`; `1Cv7.MD` и `DD` закреплены хешами стенда и не менялись.
Прежних копий этих файлов нет: изменения остаются в базе стенда.

Серия 0b, ожидания до прогона: выход из поля переводит фокус на следующий элемент
порядка обхода диалога (`GetNextDlgTabItem`); если фокус остался в поле, шаг проваливается.
`s-input` и `s-ert` проходят: `value` возвращает введённое значение. ERT открывается на копии
с пустым `[configuration]`, база стенда после серии не меняется. Остальные три случая —
как в серии 0.

Серия 0b, итог: база стенда и список баз не изменились. `s-error` совпал с ожиданием:
«line 18: Деление на 0», та же строка изменённого модуля. Остальные четыре случая провалились
на первом вводе. `GetNextDlgTabItem` вернул само поле: обход диалога 1С этим вызовом не находится,
шаг честно отказал по причине «leave failed».

Серия 0c, ожидания до прогона: фокус после ввода получает следующий элемент описания,
по кругу, — поле, кнопка или флажок, доступный и видимый. Ожидания пяти случаев —
как в серии 0, база стенда не меняется.

Серия 0c, итог: пять из пяти совпали, база стенда и список баз прежние. Сообщения сохраняются
текстом без пометки важности. Ошибка исполнения — строка исходника и
`{Справочник.Банки.Форма.Модуль(18)}: Деление на 0`. `Закрыть(0)` закрытой формы —
`close-error: Значение не представляет агрегатный объект (Форма)`. Один круг через 1С
занимает 0,08–0,35 с.

Серия 1 (итоговая), ожидания до прогона. Повторяются пять случаев серии 0. Новые случаи:

- `s-states`: `ПриОткрытии` выключает «Записать» и скрывает поле «Телефоны»; в диалог
  добавлен флажок без формулы. `enabled = false`, `visible = false` и `true`, флажок снят;
  после нажатия по подписи — установлен, реквизит `Флажок77` — «1». `result` — `passed`.
- Провал шага, сценарий остановлен на нём, тест `result` с `expect = "failed"`:
  `s-disabled` (нажатие выключенной кнопки, «the element is disabled»), `s-wrong-check`,
  `s-wrong-value`, `s-wrong-message` (предупреждения нет), `s-unexpected-message`
  (предупреждение есть), `s-not-closed` (объявлено закрытие, форма открыта), `s-closed`
  (форма закрылась без объявления), `s-wrong-attribute` (реквизита нет —
  «1C did not read the attribute», ошибка перехвачена в контроллере).
- Отказ до открытия формы, `blocked`: `s-unknown` (элемента нет), `s-wrong-class`
  (ввод в кнопку), `s-ambiguous` (подпись «Кем» у трёх полей FIO.ERT), `s-after-close`
  (проверка окна после закрытия).

Затем пример `examples/form-steps` — два запуска, оба `passed`, и регрессия: пример 024,
`f-elements` задачи 022 (`actions`) и `e-button` задачи 023 — результаты прежние.
После каждой серии база стенда и список баз не меняются.

Серия 1, итог: 16 из 18 совпали с первого прогона. `s-wrong-value` и `s-wrong-message` получили
`blocked` до OLE-активации. Сработала прежняя проверка владения: менялся состав процессов `1cv7*`,
так как параллельный сеанс владельца запускал свою 1С. Повтор (1b) в то же время дал тот же отказ.
Повтор (1c), когда чужой процесс работал непрерывно, — оба совпали. Пример прошёл дважды.
Отрицательный вариант примера (другой текст в `message`) — `failed`, код 1, причина — шаг 4
с перечнем полученных сообщений. Регрессия 022–024 — без изменений.

Серия 2, ожидания до прогона: `s-masked` — в форму банка добавлены поля `BMASKED` числа
(10.2) и даты. Ввод `12.5` даёт реквизит «12.5». Ввод цифр `251026` в маску даты даёт
«25.10.26». Сценарий проходит.

Серия 2, итог: совпало. Окно числа показывает « 12.50» с ведущим пробелом, окно даты —
«25.10.26». Поэтому текст окна и значение реквизита теперь сравниваются без крайних пробелов,
а не только без конечных. В `s-masked` добавлены проверки окон «12.50» и «25.10.26».

Серия 3 (итоговая, окончательный код), ожидания до прогона: все 19 случаев — как в сериях 1
и 2. Пример — два запуска `passed`. Регрессия 022–024 — прежние результаты.
База стенда и список баз не меняются.

Серия 3, итог: 18 из 19 совпали с первого прогона. `s-message` снова получил `blocked` из-за
чужой 1С; повтор (3b) совпал. Пример прошёл дважды, регрессия 022–024 — без изменений.

## Пример для пользователя

Сценарий обычными словами: «Открыть подготовленный банк; убедиться, что видно его имя; ввести
неверный БИК и записать — форма должна предупредить; ввести верный БИК и новое имя, нажать
„ОК“ — форма закрывается без предупреждения; прочитать запись заново». Весь тест — в
[examples/form-steps/scenario.toml](../../examples/form-steps/scenario.toml), форма базы не
меняется. Подготовка и запуск — в [README примера](../../examples/form-steps/README.md).

## Итог

19 итоговых случаев на окончательном коде совпали с ожиданиями, пример прошёл дважды,
регрессия 022–024 — без изменений. Копии удалены, исходная база и список баз после серий
на копиях сохранены. Сеанс `s-ert` серии 0 на базе стенда оставил журнал и настройки
пользователя: подробности и остальные границы — в отчёте. 475 тестов продукта (3 пропуска
symlink), 53 — форм, 143 — платформы, 17 — КУДиР, без ошибок; поставка проверена в чистом окружении.
