# 111. Fixture и reader «Счёта-фактуры» по TOML

Задача принята владельцем 19 ноября 2026 года.

Прямой сценарий счёта-фактуры из 103 получает рецепт `invoice.toml` с данными
fixture и полями reader. Генерация на этапе подготовки выдаёт `fixture.1s`
и `reader.1s` для прежнего контракта harness77. Входные UI-шаги и ожидания
взяты из 103. [Пример и команды](../../examples/invoice-fixture/README.md).

Оба рецепта используют общий код создания связанных справочников, заполнения
шапки и строк, повторного открытия документа по точной ссылке и проекции
числовых полей в JSON. Счёт-фактура назначает поддерживаемый тип ссылки
для строки `Товар`. В услугах остаются тип номенклатуры, тип услуги и нулевые
ставки. Рабочий код продукта и форматы профилей прежние.

## Критерий проверки

Прогнать `baseline → regression → fixed` для обоих документов. Для
счёта-фактуры контроль добавляет присваивание неверного значения реквизиту `Комментарий` в
`ПриЗаписи` модуля формы только в копии конфигурации. UI должен успешно
записать и переоткрыть ту же ссылку. Независимый reader должен дать одно
расхождение `/comment_ok` с ожидаемым `1` и фактическим `0`. После
восстановления исходного модуля тот же `expected.json` должен пройти.

Для услуг повторяется принятая проверка `/service_type` с `1` и `2`.
Сгенерированные входы услуг должны побайтно совпасть с задачей 110. Проверка
сверяет отпечатки входов и потоков MD, исходную базу, реестр, процессы и
удаление копии и блокировки.

## Нативная проверка

Использован опубликованный wheel 0.15.0 на Windows / 1С 7.70.027 / DBF.
Сборочные входы счёта-фактуры извлечены из сохранённого проекта 103. Шаги
и `expected.json` сверены с архивом 103 после нормализации переводов строк.

На «Счёте-фактуре» через `run` получено `passed → failed → passed`.
Каждый запуск выполнил все 25 UI-шагов, включая запись и переоткрытие той же
ссылки. В контрольной фазе reader прочитал документ и вернул `comment_ok = 0`.
Единственное расхождение сравнения — `/comment_ok` с ожидаемым `1`. После
возврата исходного модуля reader вернул `1` с тем же `expected.json`.
[Отчёты счёта-фактуры](../../.artifacts/s111-invoice-cycle/verified.json),
[контрольная правка](../../.artifacts/s111-invoice-cycle/regression.diff).

«Оказание услуг» тоже дало `passed → failed → passed` и прошло все 19 UI-шагов
в каждом запуске. Единственное расхождение контрольной фазы — `/service_type`
с ожидаемым `1` и фактическим `2`. Сгенерированные fixture и reader, шаги и ожидания
побайтно совпали с принятыми входами 110.
[Отчёты услуг](../../.artifacts/s111-services-cycle/verified.json).

Во всех шести запусках входные снимки сверены по SHA-256. В каждой
контрольной фазе из 3598 потоков MD изменён только поток модуля формы.
Исправленные модули побайтно совпали с исходными. Реестр, исходная база
и чужие процессы сохранены, сеансы закрылись штатно, копии и lock убраны.
[Итоговая сверка](../../.artifacts/s111-native-audit.json).

Автор задаёт 12 содержательных строк TOML вместо 51 строки ручных fixture
и reader прямого сценария. Дополнительно проверены повторяемость генерации,
имя товара с кавычками, назначение типа ссылки и отклонение выражения вместо
имени поля reader.
