# 112. Генерация fixture и reader из установленного harness77

Задача принята владельцем 19 ноября 2026 года.

`fixture-render` переносит генератор из примеров 110–111 в установленный
пакет. Команда готовит `fixture.1s` и `reader.1s` для «Оказания услуг» и
«Счёта-фактуры» на этапе подготовки проекта. Новый интерфейс доступен в
локальной сборке 0.16.0.

```powershell
harness77 fixture-render --kind services --output generated
harness77 fixture-render --kind invoice --recipe my-invoice.toml --output invoice --format json
```

При отсутствии `--recipe` берётся TOML-образец соответствующего вида из wheel.
Пользовательский рецепт читается в UTF-8, допускается BOM. В секции `fixture`
указываются дата, имена связанных записей, комментарий и строки документа.
Для услуг также указывается `service_type`. Секция `reader` задаёт целые
числовые реквизиты, итоги и поля строк. В ней принимаются имена полей 1С,
поэтому переданные выражения отклоняются. Поддерживаемые поля и типы задаёт
конфигурация 1С.
[Образец услуг](../../src/harness77/fixture_recipes/services.toml),
[образец счёта-фактуры](../../src/harness77/fixture_recipes/invoice.toml).

Выходной каталог должен быть новым, его родительский каталог должен
существовать. Перед публикацией оба файла проверяются на представимость в
CP1251, записываются в UTF-8 и перечитываются. Пара публикуется одним
переименованием каталога с отказом при существующем выходе. В JSON-отчёте
указаны SHA-256 рецепта и обоих результатов. Успех даёт `created` и код `0`,
ошибка чтения, проверки или записи даёт `blocked` и код `2`. У подготовки
`platform_checked=false` и `launch_performed=false`.

В рабочем профиле подключите полученные файлы через `fixture_setup_file` и
`fixture_verify_file`. Шаги и `expected.json` задаются отдельно. Для загрузки
сценария, запуска 1С и выполнения reader используются существующие команды
и формат профиля.

## Критерий готовности

Собрать wheel из sdist, установить его без сети и вызвать штатную команду
в проекте вне репозитория. Оба сценария должны дать `passed → failed → passed`
на нативном стенде. Контроль услуг записывает `ТипУслуги = 2` и даёт одно
расхождение `/service_type`. Контроль счёта-фактуры записывает неверный
комментарий и даёт одно расхождение `/comment_ok`. UI проходит в том числе
в отрицательных запусках. Для каждого документа ожидания и остальные входы
побайтно одинаковы на всех трёх фазах. Исходная база, реестр и процессы
сохраняются, копия и lock убираются.

19 ноября 2026 года создан отдельный проект `C:/MyProjects/h77-112-qualify`
вне репозитория. В его окружение установлен именно проверенный wheel.
Все 76 файлов пакета сверены побайтно, включая 33 файла нативного runtime.
Штатная команда создала файлы из встроенного рецепта услуг и из явного TOML
для счёта-фактуры. `project-init` подключил полученные файлы, а `doctor`
подтвердил готовность стенда Windows / 1С 7.70.027 / DBF.

- «Оказание услуг». Во всех трёх прогонах прошли 19 UI-шагов. Reader обнаружил
  только `/service_type` с ожидаемым `1` и сохранённым `2`.

  комментарии reader вернул `/comment_ok` со значением `0` вместо `1`.

После возврата исходных модулей те же `expected.json` прошли. Хэши ожиданий
и сгенерированных входов сверены во всех шести запусках. Все сеансы использовали
Python и нативный runtime из внешнего окружения. Исходная база, реестр и чужие
процессы сохранились, временные копии и lock удалены.
[Итоговый отчёт](../../.artifacts/s112-native-verification.json).

Ранее использованные DLL стенда отсутствовали. Они восстановлены из тех же
