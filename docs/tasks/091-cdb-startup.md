# Задача 091. Устойчивый старт CDB до Initialize

Исправление проверено 12 ноября 2026 года.

Задача принята владельцем 12 ноября 2026 года.
Продолжение [090](090-cell-input-readiness.md).

## Причина

Старый `debugger-ready` объединял выполнение команд CDB и срабатывание
точки регистрации COM. В отказавшем старте команды уже выполнились,
а точка осталась непривязанной. Это происходит до клиента и Initialize.

Естественное воспроизведение сохранено в
`.artifacts/s91-investigate2/runs/0406edce-7aa1-4084-8c9e-6fa174c7b1a5`.
В `native/debugger.log` видны две загрузки combase.dll: временный адрес
00d10000, затем 75f30000. `bl` показывает `10 eu ... (combase!CoRegisterClassObject)`;
`lm m combase` пуст, `x combase!CoRegisterClassObject` не находит модуль.
READY напечатан, FACTORY_WATCH отсутствует.

Второй наблюдатель CDB с `-pvr` прочитал тот же принадлежащий запуску
процесс. Путь образа и время создания проверены через удерживаемый HANDLE
до и после чтения. Он видит combase.dll по реальному адресу и основной
поток в win32u!NtUserGetMessage / цикле сообщений MFC42. Сохранены
noninvasive.txt и stall.json. Чтение окон вернуло отказ доступа и не
считается снимком окон. Наблюдатель отсоединён через qd, основной
контроллер очистил собственный сеанс по тайм-ауту.

Причина пропуска точки — потерянная запись модуля в состоянии основного
CDB при фактически загруженной DLL. Почему данная последовательность
уведомлений Windows приводит DbgEng к такому состоянию, отдельно не
установлено. Диагностическая серия: 13 успешных стартов и этот отказ.
Она не считается успешной приёмочной серией.

## Исправление

`prepare_observer` один раз выполняет `.reload /s /f combase.dll` перед
bp10. Это восстанавливает состояние отладчика, не выгружая DLL из 1С.
Используется экспорт CoRegisterClassObject. Отсутствие PDB допустимо
только при доказанной привязке точки. Microsoft описывает восстановление
удалённого из списка CDB модуля через /s и немедленную загрузку доступных
символов через /f: [.reload](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/-reload--reload-module-).

Контроллер требует ровно одну включённую разрешённую запись bl 10 между
маркерами с UUID запуска. Непривязанная/отключённая точка, нулевой адрес,
другое имя, смещение, дубли, эхо команд, чужая или неполная секция не
дают разрешения на активацию. Маркер выполнения команд также получил UUID.
Затем обязательны фабрика COM, проверка proxy по nonce/PID/потоку/desktop,
снятие наблюдателя и permit перед единственным Initialize.

Атомарный `native/startup.json` хранит этапы: регистрация → CDB → владение
сервером → команды → привязка → фабрика → клиент → proxy → permit →
начало/конец Initialize. observed_s — время наблюдения контроллером, не
время события внутри 1С. Финальная копия передаётся через open.startup
platform-result.json и стадии platform_check общего отчёта. Ожидания
debugger-commands, observer-binding, factory-registration относятся к open;
старое debugger-ready сохранено в отображении фаз для совместимости.
Маркеры вокруг Initialize атомарны и содержат UUID, формат ert-events
сохранён. Сроки, первый AV, владение и очистка не ослаблены; повторов нет.

Первичные источники по диагностике:
[неинвазивное чтение](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/noninvasive-debugging--user-mode-),
[-pvr](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/cdb-command-line-options),
[qd](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/qd--quit-and-detach-),
[bu](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/bp--bu--bm--set-breakpoint-).

строгую привязку и UUID, неполные журналы, трассу и отказ до клиента при
одном лишь старом READY. Платформенные тесты запущены вне файловой песочницы
из-за ограничений атомарной замены временных файлов.

Диагностический startup_probe77.py не входит в комплект. Он воспроизводит
потерю записи через `.reload /u combase.dll` только в отладчике. Контроль
фабрики меняет лишь диагностический маркер callback: точка срабатывает,
но контроллер не получает разрешения запустить клиент. Срок 8 с задан
только отрицательным профилям; обычные старты используют open=120/total=300.
Чистый venv создан с --without-pip: установлен только прежний wheel 089,
новый native runtime экспортирован явно. Рабочий каталог вне комплекта.

Итоговые свидетельства:

- `.artifacts/s91-final/verified.json`: passed, 25 случаев. Старый runtime
  с потерянной записью получает open_timeout; новый при той же потере
  возвращает 42. Принудительно непривязанная bp10 даёт явный отказ.
  Тайм-аут ожидания фабрики и отмена в этом ожидании завершаются до
  создания OLE-клиента, permit и Initialize, с подтверждённой очисткой.

- Для 21 успешного headless-случая сверены порядок всех этапов, UUID,

## Предварительные попытки

- s91-investigate: слишком ранний порог наблюдателя захватил здоровый
  промежуток до фабрики. Один успешный запуск, не сбой. Следующая проба
  ждала устойчивого отсутствия фабрики после READY.
- s91-reload: предварительная контрольная пара — потеря записи дала
  старому наблюдателю open_timeout, восстановление дало 42.
- s91-native: старый контроль дал ожидаемый тайм-аут, новый прошёл с 42.
  Проверяющий скрипт ошибочно сравнивал WriteLine-маркер без удаления
  перевода строки. Его неуспешный отчёт сохранён; источник, реестр,
  процессы, копия/замок/guard и файлы комплекта не изменились.

Артефакты перечисленных попыток сохранены в одноимённых каталогах
.artifacts. Квалификация ограничена данным Windows-стендом, CDB x86 и
1С 7.70.027. Она не доказывает отсутствие других причин задержки старта.
