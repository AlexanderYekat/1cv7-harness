# Задача 032: откат частичных проводок при ошибке проведения

Дата: 7 ноября 2026 года. Предыдущая задача — [031](031-document-lifecycle.md).
Поручение владельца: «Хорошо, реализовывай» после предложения проверить откат
внутри проведения. Статус: **принято владельцем 7 ноября 2026 года в указанном охвате**
([отчёт](032-posting-rollback-acceptance.md)).

## Ожидания до первого запуска 1С

Тот же закреплённый стенд 7.70.027, документ «Готовая продукция», Дт 43 Кт 40.
Каждый `run` получает новую проверенную копию через `[configuration]`.
Исходная база и её модуль не меняются. Используется контракт `fixture_operations`
задачи 031; новых команд или автоматических повторов не требуется.

Исходный модуль записывает операцию только после заполнения всех строк.
В изменённом модуле копии после заполнения первой строки вызывается
`Операция.Записать()`. Новый объект `Операция` читает её внутри проведения:
маркер фиксирует количество проводок, количество и сумму первой проводки.
Только после этой записи и чтения вызывается деление на ноль (`runtime`)
либо `СтатусВозврата(0); Возврат;` (`refusal`). Условие включается комментарием
документа, который операции подготовки явно записывают. Проверяющий код
не удаляет проводки и не вызывает откат сам.

Для каждого из двух вариантов заранее заданы:

1. `post-first`: первая проводка 3/30 записана и прочитана внутри проведения,
   затем ожидаемая ошибка/отказ. Независимое чтение после возврата: признак 0,
   проводок 0, исходные поля строки 3/30.
2. `post-recover`: убрать условие ошибки; успех, признак 1, ровно две проводки
   3/30 и 2/40 с правильными счетами и ссылками товара.
3. `post-repost`: заранее записать строку 5/50 и включить ошибку; внутри
   проведения прочитана одна новая проводка 5/50, после отказа сохранены прежний
   признак 1 и обе прежние проводки 3/30 и 2/40. Поля документа остаются 5/50:
   их отдельная запись выполнена до транзакции проведения.
4. `post-final`: убрать условие ошибки; успешное перепроведение, ровно две
   проводки 5/50 и 2/40, без дублей. Финальная `verify` подтверждает то же.

`suite` включает runtime, refusal и повтор runtime на новой копии.
`suite-failure` содержит намеренно неверное ожидание количества 999 после
отката и следующий успешный сценарий: итог failed/код 1, один JUnit failure.
Ошибка/отказ отдельной операции должны совпасть с явным отрицательным тестом;
отсутствие маркера частичной записи не считается доказательством отката.

Независимый verifier перечитывает протоколы и ответы контроллера, порядок команд,
проводки, признак, поля строки, JSON/JUnit и хеши; проверяет сохранность исходной
базы/списка баз, завершение своего сеанса, удаление копии и освобождение блокировки.
Регрессия — полный набор 031. Переносимые проверки форм, платформы и продукта.
Неподтверждённые ожидания сохраняются как расхождения; менять их под наблюдение
для получения зелёного результата нельзя.

Другие конфигурации, документы, регистры и аварийное завершение процесса внутри
транзакции в охват не входят. Результат — проверка поведения настоящей платформы
и пример регрессии, без собственной реализации транзакций в harness.
