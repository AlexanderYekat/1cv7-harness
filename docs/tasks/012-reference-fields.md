Дата: 19 октября 2026 года. Статус: **принято** — [приёмка](012-reference-fields-acceptance.md).
Предшествующая задача —
[011](011-form-elements-acceptance.md) (надписи, поля, флажки, рамки). Направление —
[раздел 5.1 дорожной карты](../roadmap.md#51-собирать-и-изменять-формы-ert-по-текстовому-описанию)
и [план задачи 012](../roadmap.md) в списке задач. 19 октября владелец решил
добавить поля, привязанные к конфигурации, и дал команду начать.

## Зачем

Поле формы может иметь тип справочника, документа, перечисления, счёта или вида
субконто — конкретного вида (`Справочник.Контрагенты`) или любого (`Справочник`).
Сейчас такие поля шаблона сохраняются байт в байт, но в описании видны только как
`{"kind": "other", "code": "B"}`, без вида, а новые дают отказ. Вид задаётся
номером объекта метаданных, и этот номер принадлежит конфигурации: в другой
базе тот же номер означает другой объект или ничего. Описание должно называть
объект по имени, а сборка — переводить имя в номер по метаданным той базы,
где ERT будет работать.

## Что известно (обследование 19.10, до проб)

- **Тип поля — поля 14–17 записи:** код, длина, точность, номер объекта
  метаданных — как у реквизитов в `1Cv7.MD`. У всех ссылочных полей корпуса
  длина и точность 0.
- **Корпус** (418 уникальных ERT `ExtForms`, 416 читаемых форм) — 150 ссылочных
  полей: `B` (справочник) 117 — 106 с номером, 11 «любой»; `O` (документ) 20 —
  5 с номером, 15 «любой»; `E` (перечисление) 1 с номером; `T` (счёт) 6 «любой»;
  `K` (вид субконто) 6 «любой». 147 из них — `BMASKED`, 3 — `1CEDIT` (`B`).
  Из 112 номеров 111 находятся в `1Cv7.MD` базы `base-for-test`
  (`931b26eb…`, та же конфигурация лежит в `NEW_STRU` и `configurations/reference`);
  номер `25507` (одна форма) — нет: форма сделана для другой конфигурации.
- **Метаданные.** Поток `Main MetaData Stream` в `1Cv7.MD` — тот же скобочный
  текст CP1251 с тем же заголовком длины, что у диалога; читается имеющимся
  разбором. Разделы: `SbCnts` — справочники (58), `Documents` — документы (86),
  `EnumList` — перечисления (87, значения в `EnumVal`), `Buh` → `Plans` — планы
  счетов (`809` «Основной»), `Buh` → `SbKind` — виды субконто (61). Запись
  объекта — `{"<номер>", "<имя>", …}`. Номер счёта у реквизитов — план счетов
  (`T`/`809`, 43 реквизита); у `K` и `P` (план счетов) номер всегда 0.
  `TaskItem` — имя конфигурации («Бухгалтерский учет, редакция 4.2»).
- **Запись по умолчанию.** Самые частые записи `BMASKED` ссылочных полей отличаются
  от записи поля числа только полем 19 (флаги): `B` — 0 (45 из 114), `O` —
  16777248 (9 из 20), `E` — 0 (1 из 1), `T` — 0 (4 из 6), `K` — 32 (4 из 6).
  Значение флагов не установлено.

## Что делается

### Описание формы, схема версии 3 (продукт, переносимо)

`form-extract` пишет `schema_version = 3`. Ссылочный тип —
`{"kind": "reference", "object": "<имя>"}`:

| Код | Имя в описании | «Любой» | Вид | Имена видов из |
|---|---|---|---|---|
| `B` | `Справочник`, `Справочник.<вид>` | да | да | `SbCnts` |
| `O` | `Документ`, `Документ.<вид>` | да | да | `Documents` |
| `E` | `Перечисление.<вид>` | нет (не встречается) | да | `EnumList` |
| `T` | `Счет`, `Счет.<план счетов>` | да | да | `Buh` → `Plans` |
| `K` | `ВидСубконто` | да | нет | — |
| `P` | `ПланСчетов` | да | нет | — |

Имена — как в языке 1С 7.7 (`Счет` без «ё»). «Любой» не зависит от конфигурации
и пишется всегда. Вид с номером пишется именем, если `form-extract` получил
метаданные (`--metadata 1Cv7.MD`) и номер в них есть; иначе — номером:
`{"kind": "reference", "code": "B", "object_id": 133}`. Отчёт `form-extract`
с метаданными содержит их путь, SHA-256, имя конфигурации и список полей, номер
которых в них не найден. Тип с кодом вне таблицы или с ненулевой длиной/точностью
остаётся `other`, как в версии 2. Описания версий 1 и 2 принимаются и собирают
то же, что прежде.

### Сборка

- `build --form … --metadata 1Cv7.MD`: имя вида переводится в номер по метаданным
  (регистр букв не важен, как в 1С); неизвестное имя, неизвестный раздел (`Склад.X`),
  вид у `ВидСубконто`/`ПланСчетов` и «любое» перечисление — отказ. Имя вида без
  метаданных — отказ с подсказкой, откуда их взять. Отчёт сборки фиксирует
  метаданные: путь, SHA-256 файла `1Cv7.MD`, имя конфигурации.
- **Новое поле:** `BMASKED` с ссылочным типом, обязательны идентификатор и тип;
  тип — только по имени (номер в описании новых полей не принимается: он не
  проверяем без метаданных). Запись — самая частая для кода (выше), длина
  и точность 0, поле 17 — номер. `ПланСчетов` как новое поле — отказ (в формах
  корпуса нет образца записи). `1CEDIT` со ссылочным типом — отказ (3 случая
  в корпусе, не исследовано).
- **Существующее поле:** тип по-прежнему не меняется. Описание по имени
  сравнивается с шаблоном через метаданные сборки: если имя в этих метаданных
  означает другой номер, чем в шаблоне, — отказ с обоими номерами (шаблон сделан
  для другой конфигурации или описание — по другим метаданным).
- `run`: `[build] metadata` в профиле проекта; если не задано, а описание
  называет вид по имени, — `1Cv7.MD` базы стенда. Этап `build` записывает SHA-256
  и источник (`project`/`stand`). Если ERT собрана по метаданным, а `1Cv7.MD`
  базы стенда другой, этап `platform_check` — `blocked` (`metadata_mismatch`),
  1С не запускается.

**Не входит:** изменение типа существующих полей; ссылочные `1CEDIT`; календари
и прочие типы; сопоставление метаданных разных баз (перевод номера одной
конфигурации в номер другой); выбор значения пользователем — ручная проверка
владельцем.

Ожидание опровергнуто: сборка по метаданным стенда прошла (номера 133, 0, 0,

**Установлено:** ERT несёт свою копию метаданных — поток `Main MetaData Stream`
(тот же текст, после него байт NUL). Вид поля 1С ищет в ней: у FIO.ERT копия пустая
(конфигурация «Задача», 196 из 416 форм корпуса), поэтому поле вида не создаётся,
а «любой» — создаётся. Статически по корпусу: все 112 полей вида находят свой
номер в копии своей ERT (форма с `25507` — «Справочник.Тарифы» своей копии
другой конфигурации, в базе его нет); у 220 форм копия непустая (149 — «Бухгалтерский
учет, редакция 4.2», остальные — 22 других конфигураций).

**Изменение способа.**
- Номер нового поля вида по-прежнему берётся из метаданных целевой базы. Если копия
  метаданных шаблона уже содержит этот объект с тем же номером и именем, она
  остаётся. Иначе сборка заменяет копию шаблона потоком `Main MetaData Stream`
  метаданных целевой базы (с NUL в конце, как в ERT) — только если прежние поля
  вида шаблона означают в базе те же объекты; иначе отказ. Отчёт сборки — `form.ert_metadata`
  (`kept`/`replaced`, хеши потока до и после); поток не входит в `preserved_streams`.
- `form-extract` без `--metadata` называет виды по копии метаданных самой ERT;
  с `--metadata` — по метаданным базы. Существующее поле, названное по имени,
  сборка сверяет с номером шаблона по метаданным целевой базы, если они даны,
  иначе по копии шаблона. Неизменённые поля шаблона не проверяются, как в 011.
- Повтор R1 — с этим способом на том же FIO.ERT (копия будет заменена); добавлен
  **R5**: шаблон — FIO.ERT с копией ERT корпуса (из R1b), те же шесть полей —
  ожидание: копия остаётся (`kept`), форма открыта, значение `result` как в R1.

## Решения

Владелец дал команду начать 012 по плану дорожной карты, отдельных решений
не задавал. Приняты варианты, повторяющие 008–011: JSON без новых зависимостей;
описание, метаданные и сборка — продукт (`src/harness77`), нативная проверка —
`research/forms/`; исполнитель запускает 1С сам на `base-for-test`; шаблон —
FIO.ERT; эталоны снимков утверждает исполнитель после просмотра; коммит — только
по слову владельца.

## Приёмка

Переносимо: каждый код, «любой» и вид, имя и номер, каждый отказ покрыты тестом;
все 416 форм корпуса проходят `form-extract` (версия 3) и `build --form` без правок
байт в байт — без метаданных и с метаданными `base-for-test` (имена вместо номеров);
описания версий 1 и 2 собирают те же байты; прежние тесты проходят.
Нативно: R1–R4 дали записанные исходы или их отличие записано до изменения
способа; завершение своей 1С подтверждено, чужие сеансы сохранены.
