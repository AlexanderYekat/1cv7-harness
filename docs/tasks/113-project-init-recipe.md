# 113. Fixture и reader из TOML через `project-init`

Задача принята владельцем 19 ноября 2026 года.

В локальном 0.17.0 `project-init --runtime forms` принимает
`--fixture-kind services|invoice` и необязательный `--fixture-recipe <TOML>`.
При отсутствии пути используется соответствующий образец из пакета. Входной
`scenario.json` задаёт `form_object`, шаги и тест `verify` с ожиданиями.

```powershell
harness77 project-init --runtime forms --directory services-test --id services `
  --template template.ert --source module.1s --scenario scenario.json `
  --fixture-kind services `
  --open-timeout-s 240 --calculation-timeout-s 120 --cancel-timeout-s 15 `
  --shutdown-timeout-s 30 --total-timeout-s 600 --format json
harness77 run --project services-test/project.toml --stand stand.toml
```

Команда создаёт `fixture.1s`, `reader.1s` и точный снимок рецепта
`fixture-recipe.toml`. `project.toml` и скопированный `scenario.json` получают
относительные ссылки на `.1s`. Скопированные шаги и JSON-ожидания доступны
без исходного каталога. TOML используется при подготовке, дальнейший запуск
читает обычные файлы проекта. Отчёт подготовки содержит происхождение рецепта
и SHA-256 всех выходов.

Вид рецепта должен соответствовать прямой форме документа. При выборе
рецепта режим fixture — `existing`, нужен тест с `command = verify`, а
параметры собственного fixture или reader считаются конфликтом. Прежние
вызовы `project-init` с явно заданными `.1s` по-прежнему применимы. Ошибка
валидации или записи не публикует частичный проект.

Проверка готовности запускает оба документа через `run` из установленного
wheel в отдельном каталоге. Для услуг берётся встроенный рецепт, для
счёта-фактуры — пользовательский TOML. После подготовки путь к исходному
TOML выводится из употребления, а созданный `project.toml` используется
без правок. Сверяются UI, JSON reader, хэши входов и сохранность стенда.

## Результат проверки

Wheel `harness77-0.17.0-py3-none-any.whl` собран из sdist. В установленном
пакете выполнено 649 тестов с 5 пропусками. Дополнительные проверки подтвердили
работу встроенного и пользовательского рецептов, отсутствие зависимости
проекта от исходного TOML, отказ при конфликте с `.1s` и отсутствие выходного
каталога при неверных входах. [Отчёт сборки](../../.artifacts/s113-package/summary.json).

В отдельном окружении `C:/MyProjects/h77-113-init-r2` сверены все 76 файлов
установленного wheel. Два `run` получили профили непосредственно из
`project-init`. «Оказание услуг» прошёл все 19 UI-шагов, «Счёт-фактура» —
все 25. В обоих случаях reader получил ожидаемый JSON. Для счёта-фактуры
использовано собственное имя товара, исходный TOML перед запуском перенесён.
SHA-256 профилей, ожиданий и сгенерированных `.1s` совпали до и после.
Исходная база, реестр и чужие процессы сохранены. Копия и lock отсутствуют.
[Нативный отчёт](../../.artifacts/s113-native-verification.json).

Первый запуск проверочной обвязки остановился до старта 1С. Консольная
кодировка диагностического JSON отличалась от ожидаемой UTF-8. После
исправления сериализации обвязки оба прогона выполнены на том же wheel.
[Журнал первой попытки](../../.artifacts/s113-initial-native.log).

По завершении убраны временные сборочные деревья и виртуальные окружения
обеих проверок. Сохранены wheel, журналы, отчёты и файлы проектов.
[Запись очистки](../../.artifacts/s113-cleanup.json).
