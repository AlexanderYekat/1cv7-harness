## 3. Публичный API и внутренние обязанности

Публичные точки входа одного модуля:

```python
def parse_protocol(data: bytes, *, encoding: str = "auto") -> dict:
    ...

def main(argv: list[str] | None = None) -> int:
    ...
```

`parse_protocol` возвращает JSON-совместимый словарь по разделу 6. Он не обращается к файловой системе, окружению, времени и процессам; не печатает и не изменяет вход. Для каждого вызова создаются независимые списки и словари.

- Допустимые `encoding`: `auto`, `utf-8`, `cp1251`; иной аргумент вызывает `ValueError` до обработки данных.
- Поддерживаемый тип `data` — `bytes`; неверный тип вызывает `TypeError`. Строки, `Path` и файловые объекты не декодируются неявно.
- Повреждённые входные байты и неполный протокол возвращают `blocked`, а не исключение. Ошибки программирования не маскируются общим `except Exception`.

`main` разбирает аргументы, проверяет пути, читает байты, вызывает функцию, сериализует отчёт, записывает его и возвращает код. При обычном запуске скрипта используется `raise SystemExit(main())`. Ошибки аргументов и `--help` также преобразуются в возвращаемые `main` коды `2` и `0`; сообщения `argparse` сохраняют стандартное назначение потоков.

Внутри модуля разделить обязанности: декодирование; выделение физических строк; разбор заголовка диагностики; построение отчёта; сериализация; проверка совпадения файлов; атомарная запись. Имена приватных помощников и применение `TypedDict` остаются выбором реализации. Отдельные классы сервисов, абстрактные backend и зависимости ради этих операций не нужны.

## 4. Декодирование и физические строки

### 4.1. Выбор кодировки

Сначала вычислить `hashlib.sha256(data).hexdigest()`, затем определить кодировку:

1. Проверить BOM UTF-32 LE/BE, затем UTF-16 LE/BE. Любой из них даёт единственный `unsupported_encoding`, независимо от режима. Такой порядок исключает ошибочное принятие префикса UTF-32 LE за UTF-16 LE.
2. UTF-8 BOM при режиме `cp1251` даёт `unsupported_encoding`. При `auto` или `utf-8` декодировать строго через `utf-8-sig`; при ошибке выдать `decode_error`, не пробовать CP1251.
3. Без BOM режим `utf-8` выполняет только строгий UTF-8, режим `cp1251` — только строгий CP1251.
4. Без BOM режим `auto` сначала пробует строгий UTF-8, затем строгий CP1251 только при `UnicodeDecodeError`. Если не удались оба способа, вернуть один `decode_error`.

Пустые байты и ASCII в режиме `auto` имеют `input_encoding: "utf-8"`. При успешном чтении UTF-8 BOM записывается `utf-8-sig`, в остальных случаях — имя успешного декодера. Убирать только ведущий BOM, распознанный этим правилом; не удалять U+FEFF внутри текста.

При отказе декодирования: `status: "blocked"`, хеш исходных байтов, `input_encoding: null`, пустые `diagnostics` и `unparsed_lines`, ровно один элемент `issues` с `protocol_line: null`. Номера строк не выдумываются из недекодированных байтов. Для `decode_error` сообщение называет применённые декодеры и байтовое смещение ошибки; для `unsupported_encoding` — обнаруженный BOM и выбранный режим.

### 4.2. Разделение текста

Разделять только по LF. CR удаляется из конца фрагмента только тогда, когда этот фрагмент в исходном тексте действительно завершён LF. Так распознаётся CRLF, а конечный одиночный CR сохраняется как ошибочный символ. При `\r\r\n` удаляется только последний CR.

Не использовать `str.splitlines()` без дополнительного ограничения: U+0085, U+2028 и U+2029 не должны создавать новые физические строки. Не применять `.strip()` к содержимому исходника, пути и сообщения.

- Пустой текст даёт ноль физических строк.
- Последний LF не создаёт фиктивной строки после конца файла: `a\n` — одна строка, `a\n\n` — две.
- Пустая либо состоящая только из U+0020 и TAB строка считается пустой для анализа структуры.
- Любая строка с оставшимся CR считается нераспознанной целиком, даже если остальное похоже на диагностику или завершение. Она не может стать исходной строкой следующей диагностики.

Индексы физических строк внутри алгоритма могут начинаться с нуля; наружу всегда выдаются номера с единицы.

## 5. Алгоритм разбора

Использовать два прохода по списку физических строк: сначала определить виды строк, затем связать исходники с диагностикой и проверить завершение. Это позволяет сохранить все найденные диагностики и однозначно учесть непривязанные строки. Сортировать сами диагностики по строкам модуля запрещено.

### 5.1. Распознавание заголовка диагностики

Рекомендуемая форма полного совпадения, без `IGNORECASE`, `MULTILINE` и `DOTALL`:

```text
\{(?P<file>.+?)\((?P<line>[0-9]+)\)\}: (?P<message>.+)
```

Использовать `re.fullmatch`, а не поиск фрагмента. Нежадный `file` заканчивается на первом синтаксически подходящем суффиксе `(цифры)}: `; обычные скобки внутри пути сохраняются, а похожие последовательности внутри сообщения не переносятся в путь. Эта граница входит в контракт версии 1.

После совпадения проверить, что путь и сообщение содержат что-либо кроме пробелов и TAB, а числовое значение номера больше нуля. Ведущие нули допускаются: `0007` даёт целое `7`. Знак, дробь, Unicode-цифры вместо ASCII, лишний текст перед `{`, отсутствие единственного обязательного пробела после `}:` и ноль не подходят. Дополнительные пробелы после разделителя являются частью сообщения.

Файл из заголовка — строковое значение. Не применять к нему `Path`, нормализацию, расширение переменных, проверку `.ert` или запрос к файловой системе.

### 5.2. Первый проход: классификация

Для каждой строки в указанном порядке определить один первичный вид:

1. `unknown`, если остался CR.
2. `blank`, если строка пуста либо содержит только пробелы/TAB.
3. `terminator`, если строка целиком совпала с `При проверке модуля обнаружены синтаксические ошибки!`.
4. `diagnostic`, если заголовок соответствует разделу 5.1.
5. `source_candidate`, если в оставшейся строке ровно один маркер `<<?>>`.
6. `unknown` во всех остальных случаях.

Названия видов — внутренние, они не попадают в JSON. Приоритет диагностики исключает повторное использование строки сообщения как исходника, даже если в её тексте есть `<<?>>`.

### 5.3. Второй проход: пары и остаток

Для каждого `diagnostic` создать запись с `file`, `line`, `message`, `protocol_line` и исходными `column: null`, `source_line: null`.

Если непосредственно предыдущая физическая строка имеет вид `source_candidate`, привязать её только к этой диагностике. Колонка равна `text.index("<<?>>") + 1`; исходная строка получается удалением единственного маркера. Пометить кандидата использованным. В остальных случаях оставить оба `null`.

После связывания добавить в `unparsed_lines` все `unknown` и неиспользованные `source_candidate`, по физическому порядку. Для каждой такой строки добавить `unparsed_line` в `issues`. Пустые строки не нарушают структуру сами по себе, но прерывают непосредственное соседство исходника и диагностики.

Два последовательных кандидата перед диагностикой: второй связывается с диагностикой, первый остаётся нераспознанным. Строка с двумя маркерами не связывается. Диагностика без исходника допустима и не создаёт issue сама по себе.

### 5.4. Завершение и итог

После разбора всех строк вычислить список терминаторов и последнюю значимую физическую строку. Диагностики после терминатора также остаются в результате.

Общие причины, в порядке добавления:

1. `empty_protocol`, если нет значимых строк.
2. `no_diagnostics`, если массив диагностик пуст.
3. `missing_terminator`, если терминаторов нет.

Для каждого терминатора добавить ровно один `invalid_terminator` на его номер, если выполняется хотя бы одно условие: терминаторов больше одного; этот терминатор не последняя значимая строка; перед ним нет ни одной распознанной диагностики. Таким образом, при двух терминаторах оба помечаются проблемными. Терминаторы не дублируются в `unparsed_lines`.

Окончательный порядок `issues`: сначала общие причины в перечисленном порядке, затем причины с номером строки по возрастанию `protocol_line`, при равенстве — по `code`. Пара `(code, protocol_line)` уникальна. Текст сообщения должен быть объяснимым и стабильным; потребители ветвятся по коду, а не по русскому тексту.

Если `issues` пуст, установить `failed`; иначе — `blocked`. Это правило применяется только после всех проверок и не допускает `failed` при нуле диагностик. `diagnostics` и `unparsed_lines` остаются в порядке физического появления.

## 6. Формат JSON и контрольные примеры

Версия схемы — `1`. В выдаче ровно девять верхнеуровневых полей, в порядке примера ниже. Диагностика содержит ровно шесть полей; `unparsed_lines` — объекты с `protocol_line` и `text`; issue — с `code`, `message`, `protocol_line`. Типы и допустимые значения определены в разделе 5 [методологического ТЗ](001-compiler-protocol.md).

Сериализовать через `json.dumps(report, ensure_ascii=False, indent=2, allow_nan=False)`, добавить один LF, закодировать в UTF-8 без BOM. Порядок ключей задаётся при создании словарей; `sort_keys` не включать. Выходные байты одинаковы в stdout и файле. Поля с неизвестными значениями сохраняются с JSON `null`, не опускаются.

### 6.1. Полный протокол с ошибкой

## 7. CLI и операции с файлами

### 7.1. Аргументы и последовательность вызова

```text
compiler_protocol77.py INPUT [--encoding auto|utf-8|cp1251]
                            [--format json] [--output OUTPUT]
```

По умолчанию: `auto`, `json`, stdout. Каталоги вместо входного файла, чтение stdin, glob и рекурсивный обход не поддерживаются. `-` не является специальным обозначением stdin/stdout.

Порядок: разобрать аргументы → проверить пути → прочитать вход один раз как байты → получить отчёт → полностью сериализовать в памяти → записать → вернуть код по `status`. Исходник из поля `file` никогда не читается. При `--output` не выводить копию JSON в stdout.

Для `failed` и штатного `blocked` stderr пуст: причины уже есть в JSON. Для файловой или операционной ошибки stderr содержит понятное сообщение с префиксом `compiler-protocol77:`, stdout пуст, если вывод ещё не начинался. Код `2` при невозможности доставки отчёта имеет приоритет над результатом разбора. `--help` выдаёт справку и код `0`, не читая файл.

### 7.2. Защита входа

Вход должен быть доступным обычным файлом. Файловая ссылка на такой вход допустима. Для проверки совпадения:

1. Получить абсолютные разрешённые пути через `Path.resolve`; для потенциально нового выхода допустим `strict=False`.
2. Сравнить нормализованные пути с учётом регистра ОС. На Windows разные написания регистра не должны обходить проверку.
3. Если выход существует, дополнительно проверить `os.path.samefile` либо эквивалентную идентичность файлов, включая hard link. Ошибка этой проверки не трактуется как доказательство различия.
4. При совпадении завершиться кодом `2` до создания временного файла. Если сравнение выполнить невозможно из-за прав или некорректной ссылки, также отказать с объяснением.

Разрешённый путь назначения используется и при проверках, и при публикации. Если OUTPUT является символической ссылкой, назначением считается её разрешённая цель; ссылка на вход поэтому отклоняется. Родитель назначения должен существовать и быть каталогом. Каталог в качестве OUTPUT отклоняется.

Защиту выполнить до записи и повторно непосредственно перед заменой существующего результата. Поддерживаемый сценарий предполагает отсутствие конкурентного изменения входа и назначения другими процессами; протокол блокировок для нескольких писателей в эту версию не входит.

### 7.3. Запись файла

1. Получить полный `payload: bytes` до любой записи в назначение.
2. Создать уникальный временный файл в том же каталоге через `tempfile`, не используя постоянное имя вроде `result.tmp`.
3. Записать байты в бинарном режиме, выполнить flush и закрыть дескриптор. На Windows замена выполняется после закрытия файла.
4. После повторной проверки путей вызвать `os.replace(temp_path, output_path)`. До этого момента старый результат не открывать на усечение и не удалять.
5. При обрабатываемой ошибке убрать только временный файл этого вызова. Если уборка тоже не удалась, указать его путь в stderr и сохранить код `2`; не скрывать первоначальную ошибку.

При невозможности чтения, проверки путей, сериализации либо замены новый отчёт не считается опубликованным. Если был указан OUTPUT, сообщение явно содержит «Новый результат не записан; существующий выходной файл не подтверждает этот запуск». Старый файл до успешной замены остаётся побайтно прежним. Корректный отчёт со статусом `blocked` публикуется тем же способом, что и `failed`.

### 7.4. stdout

Выводить готовые байты через бинарный stdout, затем flush; кодировка терминала и `PYTHONIOENCODING` не должны менять JSON при перенаправлении. Не использовать построчную печать частей отчёта и не добавлять сообщения «готово».

Обрабатывать ошибки записи/flush, включая `BrokenPipeError`, как код `2`, без traceback и повторной ошибки при завершении интерпретатора. После начала вывода возможен оборванный канал; целостность такого вывода не гарантируется и не объявляется подтверждённой. Вызов с текстовыми заменителями stdout без бинарного потока не является поддерживаемым интерфейсом API; проверять байтовый вывод реальным дочерним процессом.

## 8. Fixtures и независимые ожидания

Поставить `p1.txt` и `p2.txt` как UTF-8 без BOM и с LF. Использовать очищенные копии локальных протоколов, если достаточно замены личного пути; иначе — явно обозначенные синтетические эквиваленты по методологическому ТЗ. Исходные файлы не менять. Нормализацию кодировки/переводов строк и замену пути перечислить как преобразования.

`manifest.json` содержит `schema_version: 1` и массив `cases`. Для каждого случая обязательны: `id` (`p1`/`p2`), `kind` (`sanitized`/`synthetic`), `protocol_file`, `expected_file`, `sha256`, `encoding`, `diagnostic_count`, `origin`, `transformations`. Пути к поставляемым файлам — относительные к каталогу manifest; `origin` описывает источник без личного абсолютного пути. Для очищенной копии дополнительно сохранить `original_sha256` из локального манифеста, явно отличая его от хеша fixture.

`p1.expected.json` и `p2.expected.json` содержат полный ожидаемый отчёт версии 1, включая сообщения, колонки, физические номера и хеш поставляемого входа. Эталон сначала составляется и проверяется по исходным записям; он не генерируется тестируемой функцией во время теста и не перезаписывается при падении проверки.

Проверка manifest, наличие fixtures и сверка их хешей обязательны. Пути в тестах вычисляются от `__file__`, не от cwd. Тесты не должны загружать `research/kudir/corpus` через неявный относительный путь.

Варианты кодировок, повреждений и переводов строк для коротких примеров создавать прямо в тестах как байты. Не размножать P1/P2 для каждого варианта. Проверки оригиналов выполняются отдельно при приёмке; их отсутствие явно отмечается и не ослабляет обязательный переносимый набор.

## 9. План автоматических проверок

Использовать `unittest`, `subTest`, `tempfile`, `subprocess` и при необходимости `unittest.mock`. Ниже идентификаторы сценариев для трассировки приёмки; они не требуют отдельного метода на каждую строку перечисления.

### A. API и декодирование — разделы 3–4

- **A01:** повторные вызовы на одинаковых байтах равны; изменение списка в одном результате не меняет другой; импорт модуля не запускает CLI.
- **A02:** неверные тип данных и `encoding` вызывают оговорённые исключения; пустые байты возвращают отчёт примера 6.2.
- **A03:** один русский пример в UTF-8, UTF-8 BOM, CP1251; диагностики равны, `input_encoding` соответствует реальному чтению, хеш равен SHA-256 каждого входа.
- **A04:** явные режимы, ASCII и неоднозначные байты, допустимые одновременно как UTF-8 и CP1251: режим `auto` выбирает UTF-8, явный CP1251 не переопределяется.
- **A05:** UTF-8 BOM плюс невалидные байты — `decode_error` без fallback; UTF-16/32 BOM — `unsupported_encoding`; UTF-8 BOM при явном CP1251 — `unsupported_encoding`.
- **A06:** `b"\x98"` при CP1251 и `auto` — `decode_error`; проверяются единственный issue, `null` кодировки, пустые диагностические массивы и сохранённый хеш.
- **A07:** LF, CRLF, смешанные окончания, отсутствие последнего LF и несколько пустых строк; номера не сдвигаются. Одиночный CR в конце файла и `\r\r\n` не принимаются за обычный CRLF. U+2028 внутри сообщения не создаёт новую строку.

### B. Записи и координаты — раздел 5

- **B01:** точное совпадение с примером 6.1, включая колонку `32` и SHA-256.
- **B02:** путь с кириллицей, пробелами и скобками сохраняется; строка вида `(12)}: ` внутри сообщения не изменяет путь; начальные/конечные пробелы сообщения после разделителя сохраняются.
- **B03:** маркер в начале и конце, строка только из маркера, TAB и Unicode-символ вне BMP до маркера; колонка измеряется кодовыми точками.
- **B04:** отдельный заголовок без исходника даёт два `null`; неизвестная немаркированная строка перед ним остаётся в `unparsed_lines` и даёт `blocked`.
- **B05:** два маркера, кандидат без диагностики, пустая строка между кандидатом и заголовком, два кандидата подряд; проверить точное связывание и все остатки.
- **B06:** нулевой номер, знак, нечисловой номер, Unicode-цифры, пустой/пробельный путь и сообщение, неверный разделитель — нераспознанные строки; `0007` принимается как `7`.
- **B07:** диагностическая строка, содержащая `<<?>>` в сообщении, не становится исходником следующей диагностики; дубликаты записей сохраняются.

### C. Полнота — разделы 5.4 и 6

- **C01:** пустой и пробельный текст, произвольная строка, только терминатор; проверить точный набор, порядок и номера issues.
- **C02:** диагностика без терминатора; терминатор до диагностики; два терминатора; текст после терминатора; пустые строки после правильного терминатора.
- **C03:** повреждённая строка между двумя исправными записями и диагностика после преждевременного терминатора: обе диагностики сохраняются, итог `blocked`.
- **C04:** частичный результат примера 6.3; каждый неизвестный физический номер встречается один раз, ему соответствует `unparsed_line`; терминаторы не дублируются как неизвестные строки.
- **C05:** точные ключи/типы JSON, отсутствие `passed`, `source_hash`, `artifact_sha256` и классификации каскада; `failed` только при непустых диагностиках и пустых issues.

### D. CLI и файлы — раздел 7

- **D01:** реальный `subprocess.run` через `sys.executable`, аргументы списком, `shell=False`, захват stdout/stderr как байтов; `failed → 1`, `blocked → 2`, `--help → 0`, неверные аргументы → `2`.
- **D02:** stdout и OUTPUT содержат одинаковые UTF-8 байты; без BOM, с одним конечным LF. Запустить дочерний процесс с `PYTHONIOENCODING=cp1251`: JSON всё равно UTF-8. При OUTPUT stdout пуст; для штатных отчётов stderr пуст.
- **D03:** абсолютный путь скрипта, посторонний cwd, вход/выход с пробелами и кириллицей; относительные аргументы разрешаются от cwd процесса, fixtures — от пути теста.
- **D04:** отсутствующий вход, каталог вместо входа, недоступный родитель выхода и каталог вместо OUTPUT: код `2`, понятный stderr, отсутствие нового отчёта.
- **D05:** вход равен выходу буквально, через относительное/абсолютное написание и `..`; существующий hard link; отдельно Windows-регистр и символическая ссылка. В каждом случае код `2`, байты входа неизменны, временный файл не остаётся.
- **D06:** заранее существующий результат заменяется после нормальной обработки, включая `blocked`. Инъекция отказа создания/записи временного файла и `os.replace` проверяет сохранность старого результата и уборку временного файла.
- **D07:** отказ повторной проверки идентичности перед заменой не удаляет старый файл; отказ очистки временного файла сохраняет исходную причину и сообщает путь остатка. Ошибки прав моделировать детерминированно, не полагаясь только на chmod под Windows.
- **D08:** сбой записи/flush stdout, включая закрытый канал, даёт код `2` без traceback, в том числе при выходе процесса. Тест не зависает: у дочерних процессов есть конечный timeout.

Файловые отказы проверять на границе `main` с контролируемой подменой операции ОС, не проверяя приватную структуру парсера. Реальные сценарии stdout, кодировки, аргументов и cwd обязательно проверять дочерним процессом. Windows-специфичные тесты на другой ОС могут быть отмечены `skip` с причиной; успешная приёмка Windows требует реально выполненных проверок регистра и hard link. Недоступная проверка symlink указывается отдельно.

### E. Корпус и регрессия — раздел 8

- **E01:** оба поставляемых fixture совпадают с manifest по хешам и с ожидаемым JSON целиком. P2 — 7 диагностик на строках 423, 428, 1012, 1045, 1229, 1443, 2393; P1 — 60, из них 51 на строке 311.
- **E02:** отсутствующий fixture или неверный хеш дают падение, а не skip. Основной набор работает без локального прикладного корпуса и платформы 1С.
- **E03:** байты fixtures сохраняются после checkout с `core.autocrlf=true`; проверка выполняется в отдельном временном checkout после фиксации файлов, без изменения пользовательских Git-настроек.
- **E04:** прежние 31 тест линтера проходят без изменения их ожиданий. Исходные файлы корпуса, если они использовались для дополнительной проверки, сохраняют хеши.
