# Этап 5, задача 014: MCP-сервер над операциями CLI

Дата: 20 октября 2026 года. Статус: **принято** — [приёмка](014-mcp-server-acceptance.md). Предшествующая задача —
[013](013-kind-name-checks-acceptance.md). 20 октября владелец дал команду
перейти к реализации следующего этапа. По дорожной карте это пункт 5.1, шаг 3
(«MCP — дальше») и общее направление этапа 5 («MCP над теми же операциями»);
[ТЗ](../restructuring-spec.md) требует, чтобы MCP был оболочкой над операциями CLI
без собственных копий правил, и проверки равенства результатов CLI и MCP
на одинаковых входах.

## Зачем

Агент сейчас работает с harness77 только через оболочку: собирает командную строку,
читает stdout и stderr, сам разбирает коды выхода. MCP даёт клиенту (Claude Code,
Claude Desktop и другим) операции как инструменты со схемами аргументов и
машинным результатом — без оболочки и без знания CLI. Правила остаются в операциях:
сервер только переводит вызов инструмента в вызов CLI и возвращает его результат.

## Что известно (до работы)

- **Операции и их вывод.** Каждая команда пишет JSON: результат — в stdout,
  отказ (`blocked`) у `build`, `extract`, `form-extract`, `triage`, `catalog`, `run`
  и `visual` — в stderr; ошибка разбора аргументов — текст `usage` в stderr. Коды:
  0 — прошло, 1 — дефект проверяемого кода или провал теста, 2 — отказ входа или
  инфраструктуры.
- **Разделитель `--`.** Путь, начинающийся с `-`, CLI принимает после `--`, но только
  если перед `--` стоит хотя бы один ключ: `harness77 compiler-protocol -- -x.txt`
  отказывает («required: INPUT») — верхний разбор команды забирает `--` себе
  (Python 3.13). `harness77 lint --format=json -- -x.1s` работает.
- **Отмена `run`** — только сигналом: Ctrl+C, в Windows и Ctrl+Break (задача 006).
  Сервер, запущенный клиентом, может не иметь консоли, и сигнал консоли до дочернего
  процесса не дойдёт. Нужна отмена, не зависящая от консоли.
- **Зависимости.** У пакета нет runtime-зависимостей; официальный Python SDK MCP
  (`mcp` 2.3.0 на PyPI) тянет pydantic, anyio, starlette и другие. Транспорт stdio —
  это строки JSON-RPC 2.0, по одной на сообщение; он реализуется стандартной
  библиотекой.
- На машине есть Claude Code 2.1.304 и доступ к PyPI (для исследовательского клиента).
- **Новая ревизия протокола.** SDK 2.3.0 знает ревизию `2026-07-28` без рукопожатия
  (`server/discover` и поля протокола в `_meta` каждого запроса); клиент в режиме
  `auto` сначала пробует `server/discover` и при любой ошибке JSON-RPC переходит
  к `initialize` (эпохи `2024-11-05`…`2025-11-25`). Сервер этой задачи — эпохи
  `initialize`; на `server/discover` он отвечает `-32601`, переход проверяет C1.
- **Завершение сервера клиентом SDK (Windows).** Клиент SDK помещает процесс сервера
  в Job Object с `KILL_ON_JOB_CLOSE`; при выходе закрывает stdin, ждёт 2 с и снимает
  всё дерево. Своя 1С запускается отладчиком cdb как его дочерний процесс
  (`research/platform77/session77.py`), то есть она в том же дереве: такой клиент,
  закрытый во время `run`, принудительно остановит свою 1С, а временная регистрация
  COM launcher (`HKCU\Software\Classes\Harness77Diagnostic.*`) останется — следующий
  запуск launcher откажет («refusing to overwrite existing COM registration»), пока
  её не удалят. Сервер этого не предотвращает: время жизни сервера — решение клиента.
  Так же действует снятие дерева `harness77 run` из CLI (диспетчер задач).

## Что делается

1. **`harness77 mcp`** — MCP-сервер на stdio. Версии протокола: `2025-11-25`,
   `2025-06-18`, `2025-03-26`, `2024-11-05`; сервер отвечает версией клиента, если
   знает её, иначе последней своей. Возможности — только `tools`. Методы: `initialize`,
   `ping`, `tools/list`, `tools/call`; уведомления `notifications/initialized`
   и `notifications/cancelled`. Пакеты JSON-RPC (массивы) не поддерживаются —
   ошибка `-32600`. В stdout идут только сообщения протокола; случайный вывод
   перенаправлен в stderr, журнал сервера — в stderr.
2. **Инструменты — команды CLI один к одному** (имена как в CLI): `lint`
   (всегда `--format=json`), `compiler-protocol`, `triage`, `extract`, `form-extract`,
   `build`, `run`, `visual-compare` (`visual compare`). Аргументы — ключи CLI
   с `_` вместо `-` (`legacy_normalize`, `open_timeout_s`, `masks` — `--mask`).
   **Не входят:** `catalog` — обслуживание каталога из файлов платформы, агенту
   не нужен; `visual approve` — утверждение эталона остаётся явным действием
   человека в CLI, иначе агент мог бы «починить» проваленную визуальную проверку
   повторным утверждением; `--output` у `lint`, `compiler-protocol` и `triage` —
   отчёт возвращается в ответе.
3. **Вызов — дочерний процесс** `python -m harness77 <команда> <аргументы>` тем же
   интерпретатором, в рабочем каталоге сервера: относительные пути разрешаются как
   в CLI. Ключи передаются как `--ключ=значение`, позиционные пути — после `--`;
   перед `--` всегда есть ключ (`encoding` у `compiler-protocol`, `triage` и `build`
   передаётся всегда, по умолчанию `auto`). Почему процесс, а не вызов функции:
   равенство с CLI по построению (тот же разбор аргументов, те же коды), операции
   пишут в `sys.stdout`, который у сервера занят протоколом, `run` запускает 1С
   и launcher, падение или зависание одного вызова
   не роняет сервер. Цена — запуск Python на каждый вызов (в C1 на нагруженной
   машине вызов шёл 2–12 с, из них большая часть — запуск).
4. **Результат.** `structuredContent`: `tool`, `argv`, `cwd`, `exit_code`, `stdout`,
   `stderr`, `duration_s`; `stdout` и `stderr` — разобранный JSON, если операция
   вывела JSON, иначе текст, пустой вывод — `null`. Тот же JSON — текстом
   в `content`. `isError` — при коде вне 0 и 1 (код 1 — найденный дефект, это
   результат, а не сбой инструмента). Неверные аргументы (лишний или пропущенный
   ключ, не тот тип, значение вне перечня) — `isError` без запуска процесса, как
   требует протокол 2025-11-25; неизвестный инструмент — ошибка JSON-RPC `-32602`.
   Схема результата объявлена в `outputSchema`.
5. **Долгие вызовы.** Вызовы выполняются параллельно: `ping` и `tools/list`
   отвечают во время `run`. Если запрос несёт `_meta.progressToken`, сервер каждые
   10 с шлёт `notifications/progress` (прошедшие секунды и имя инструмента).
6. **Отмена.** `notifications/cancelled` для `run` создаёт файл отмены, переданный
   запуску ключом `--cancel-file`; дальше — как Ctrl+C (задача 006): ограниченное
   ожидание и остановка своей 1С. Остальные операции короткие и создают только новые
   файлы: сервер даёт процессу завершиться, чтобы не оставить недоопубликованный
   результат. На отменённый запрос ответ не отправляется (так требует протокол).
   Закрытый stdin (клиент завершает сеанс) отменяет активные `run` так же, остальные
   вызовы доходят до конца; ответы отправляются, пока клиент их читает (так работает
   и подача запросов через канал: `... | harness77 mcp`); сервер дожидается своих
   процессов и завершается с кодом 0. Клиент, который снимает дерево процессов
   раньше (SDK — через 2 с), прерывает это ожидание — см. «Что известно».
7. **Продукт `run`:** ключ `--cancel-file PATH` — запуск отменяется, когда файл
   появится (проверка каждые 0,2 с); файл, существующий до старта, — `blocked`,
   код 2, ничего не запускается. Путь отмены тот же, что у Ctrl+C.

Подсказки инструментов (`annotations`): `lint`, `compiler-protocol`, `triage` —
только чтение; `extract`, `form-extract`, `build`, `visual-compare` — пишут только
новые файлы, не разрушают; `run` — `destructiveHint` (исполняет код модуля на базе
стенда).

**Не входит:** CI; ресурсы и подсказки MCP; транспорт HTTP; пакеты JSON-RPC;
задачи (`tasks`) протокола 2025-11-25; содержимое созданных файлов в ответе
(клиент читает их сам); проверка прав клиента.

## Находка до нативных проб: окружение клиента SDK

Клиент SDK по умолчанию передаёт серверу только 12 переменных окружения
(`APPDATA`, `PATH`, `SYSTEMROOT`, `TEMP` и др.), без `WINDIR`. Launcher этапа 4 ищет
`cscript.exe` по `os.environ["WINDIR"]` — уже после того, как cdb запустил свою 1С.
Исправлено до проб: `research/platform77/session77.py` берёт `WINDIR`, иначе
`SYSTEMROOT` (в Windows это один каталог). N1 и N2 идут в урезанном окружении SDK —
это и проверка исправления.

Job Object, не выживает).

## Приёмка

Переносимо: протокол и ошибки JSON-RPC, неверные аргументы без процесса, равенство
каждого инструмента с CLI (включая отказ и путь с `-`), `run` на симуляции, прогресс,
отмена и закрытый stdin с поддельной операцией, `run --cancel-file`; прежние тесты
проходят. Клиенты: C1 — 13 из 13 вызовов SDK равны CLI; C2 — Claude Code вызывает
`lint`; C3 записана. Нативно: N1 равен CLI, N2 и N3 отменяют идущий расчёт с очисткой;
ошибки подготовки (N1 с не-UUID, N1b с опечаткой) записаны до повтора.
