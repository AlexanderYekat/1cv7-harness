# Задача 089. Диагностика стенда перед запуском

Реализована и проверена 12 ноября 2026 года.

Задача принята владельцем 12 ноября 2026 года.

## Контракт

```powershell
harness77 doctor --project project.toml --stand stand.toml --format json
harness77 doctor --project project.toml --stand stand.toml --output-root .artifacts/runs
```

Команда читает предпосылки запуска. Не выполняет launcher, не открывает сеанс
1С, не активирует COM, не создаёт каталоги/файлы/замки и не меняет реестр.
`--output-root` задаёт предполагаемый корень результатов `run` для проверки
пересечений путей; по умолчанию `.artifacts/runs` от CWD. Он не создаётся.
Пути проекта, стенда и CLI разрешаются по прежнему контракту: пути внутри
TOML — от каталога этого TOML, CLI-пути — от рабочего каталога команды.

По умолчанию выводится текст, `--format json` выдаёт один JSON в stdout
и при успехе, и при блокировке. Код 0 — `ready`, код 2 — `blocked`.
Ошибки синтаксиса самой командной строки обрабатывает argparse.

JSON: `schema_version=1`, `tool=harness77`, `operation=doctor`, `version`,
`status`, `exit_code`, `scope`, `platform_checked=false`, `launch_performed=false`,
`checks` и `counts`. Проверка содержит `id`, `status`, стабильный `code`,
читаемое `message` и `details`. Статусы проверок: `passed`, `blocked`,
`warning`, `skipped`. Любая блокировка даёт код 2. Предупреждения сами по
себе не блокируют. Отчёт содержит локальные пути для поиска проблемы,
но не выводит параметры сценария, имя пользователя базы или пароли.

## Проверки

- Профили читаются независимо. Проверяются исходник, шаблон ERT,
  дополнительные файлы form/metadata/globals и каталог configuration,
  а также согласованность сроков.
- Для нативного стенда: база, launcher, EXE, CDB, helper/identity DLL,
  MD/DD, 1С++/FormEx и таблицы 1SUSERS/1SJOURN. Бинарники читаются как
  PE-файлы, требуется x86; DLL не загружаются в Python.
- Объявленные `stand.pinned`: ключ `exe` обозначает EXE, остальные —
  простые имена файлов базы, как у NativeBackend. SHA-256 сравниваются
  с фактическими. Необъявленные хеши не подменяются хешами исследовательского
  стенда. При полном отсутствии закреплённых хешей выдаётся предупреждение.
- `stand.tool_hashes` дополнительно задаёт ожидаемые SHA-256 инструментов
  по ролям `exe`, `cdb`, `helper`, `identity`, `launcher`. Doctor проверяет
  эти значения; прежний `run` не получает новых правил проверки из этой задачи.
- Проверяется чтение таблиц базы. Отказ доступа обозначается как
  `base_busy_or_unreadable`: он может означать как блокировку, так и права.
- Путь копии проверяется для проекта с configuration. Проверяются его родитель,
  отсутствие копии/замка и регистрация в 32-битном списке баз пользователя.
  Существующий idle-guard не блокирует и не изменяется. Копия/замок дают
  `copy_requires_inspection`; doctor не определяет владельца и не выполняет
  восстановление, доступное последующему `run`.
  У проекта без configuration неиспользуемая копия не блокирует диагностику.
- База, копия и результаты не должны совпадать или вкладываться друг в друга.
  Существующие ссылки разрешаются перед сравнением. Файл вместо каталога
  результатов или его родителя блокирует запуск.
- Наблюдаются четыре временных COM-корня квалифицированного исполнителя.
  Наличие корня блокирует: он может принадлежать активному или прерванному
  сеансу. Никакие регистрации не удаляются.
- Процессы `1cv7*.exe` перечисляются только как наблюдение. Их наличие даёт
  предупреждение: принадлежность выбранной базе не доказана.

На другой ОС нативный профиль получает `windows_required`, реестр и
процессы помечаются как непроверенные. Для simulation/import проверяются
профили, файлы проекта, сроки и файл сценария/импортированного протокола;
нативные проверки пропускаются.

`ready` — снимок проверенных предпосылок. Он не подтверждает компиляцию,
импорты произвольного launcher, лицензию, вход в базу, выполнение сценария
или права записи. Отдельная проверка `output.writable` явно пропущена:
doctor не пробует создавать файлы. Состояние может измениться после снимка;
обычные проверки и блокировки `run` сохраняются.

## Воспроизведение приёмки

После сборки wheel и подготовки нового комплекта по
[инструкции 088](../../examples/clean-environment/README.md) выполните из
его чистого venv с очищенными PYTHONPATH/PYTHONHOME:

```powershell
& .artifacts/s89-kit-final/venv/Scripts/python.exe -B scripts/verify_doctor77.py --kit .artifacts/s89-kit-final --output .artifacts/s89
```

Проверяющий скрипт создаёт только свой новый каталог свидетельств и
отдельные профили отрицательных проверок. Он запускает установленный CLI
из чужого CWD, сверяет состояние базы, комплекта, реестра, guard и процессов
после каждого вызова doctor. Проверяет отсутствие DLL, неверный хеш,
незарегистрированную копию, неверный относительный launcher, пересечение
путей и существующий замок на отдельном пути. Затем выполняет четыре
прикладных сценария 088 и повторяет положительную диагностику.

Для проверки реестра и нативной регрессии нужны права обычного пользователя
стенда, доступ к его 32-битному списку баз и запуску 1С/CDB.

## Предварительные попытки и ограничение UI

Три предварительных полных прогона не засчитаны как успешная приёмка:
`.artifacts/s89-native`, `.artifacts/s89-native-final`,
`.artifacts/s89-acceptance`. Их проверки doctor прошли, но прикладная
сверка обнаружила дополнительный сбой ввода количества: отправка символа
вернулась без ошибки, текст редактора остался `1.000`, а сумма — 10 вместо 30.
В первых двух попытках это случилось в отрицательном сценарии/повторе,
в третьей — в сценарии после ожидаемого провала. Независимая сверка
отклонила такие результаты; все итоговые снимки очистки и неизменности
в этих трёх `verified.json` успешны.

Для сравнения прежний принятый комплект 088 без нового wheel и без doctor
выполнил все четыре сценария: `.artifacts/s89-old088-control/verified.json`.
Сравнение wheel показывает изменения только в cli.py и двух новых модулях
doctor; код run/suite/backend и файлы исполнителя не менялись. Причина
неустойчивого UI-ввода этой задачей не установлена и не исправлена.
Успешный заключительный прогон подтверждает конкретную полную проверку,
но не устраняет риск повторения этого сбоя. Автоматических повторов,
ослабления ожиданий или замены неуспешных свидетельств не добавлено.
