# Задача 094. Создание минимального проекта

Продолжение [093](093-stand-init.md). Реализована и проверена 12 ноября
2026 года.

Задача принята владельцем 13 ноября 2026 года.

## Команда

Wheel harness77 0.4.0 добавляет минимальный headless-проект:

```powershell
harness77 project-init --directory C:/work/hello77 --id hello77 `
  --template C:/stand/FIO.ERT --open-timeout-s 120 --calculation-timeout-s 60 `
  --cancel-timeout-s 15 --shutdown-timeout-s 30 --total-timeout-s 300 --format json
harness77 doctor --project C:/work/hello77/project.toml --stand stand.toml --format json
harness77 run --project C:/work/hello77/project.toml --stand stand.toml --output-root C:/runs/check
```

directory, id, template и все пять сроков обязательны. ID — 1–64 ASCII-
символа (буквы/цифры, точка, дефис, подчёркивание; начало — буква/цифра),
без завершающей точки и зарезервированных имён устройств Windows.
Он используется в имени собранной ERT, поэтому пути и разделители запрещены.
Относительные CLI-пути разрешаются от CWD, относительные пути проекта —
от его project.toml. Родитель directory должен существовать, сам каталог — нет.

Создаются ровно три файла и один пустой каталог:

- project.toml: UTF-8, относительные template/source/configuration, тест
  execute с expect=passed и expect_value=42, явно заданные сроки;
- module.1s: поставляемый в wheel минимальный headless-контракт, возвращающий
  6 * 7 при execute и маркеры loaded/completed;
- template.ert: побайтная копия выбранного шаблона;
- configuration/: пустой каталог для запуска неизменённой MD на копии базы.

Команда не выбирает стенд и не запускает 1С, doctor или сборку. Для реального
запуска нужен профиль с runtime=headless, например созданный stand-init.
Forms и генерация прикладных сценариев в этот первый охват не входят.

## Проверки и сохранность

Проверяются все потоки контейнера ERT и сжатый модуль CP1251, исходник из
пакета, конечные положительные сроки и сумма фаз по существующей политике
Deadlines. Проверка контейнера не заменяет компиляцию/исполнение реальной 1С.

Проект сначала записывается в отдельный временный каталог рядом с целевым.
Файлы flush/fsync, перечитываются и сверяются побайтно; профиль читается
штатным load_project. Перед публикацией повторно сверяется исходный шаблон.
Затем каталог публикуется целиком без замены существующего пути: Windows
os.rename, Linux renameat2(RENAME_NOREPLACE). Простого предварительного exists
недостаточно, поскольку другой процесс может создать даже пустой каталог.
Основание: [Python os.rename](https://docs.python.org/3/library/os.html#os.rename),
[Linux renameat2](https://www.man7.org/linux/man-pages/man2/renameat.2.html).
Если нужная операция не поддерживается, команда отказывает без копирования
поверх целевого каталога. Windows проверен нативно; Linux-ветвь проверена
моделью границы API, без утверждения нативной Linux-приёмки.

При отказе удаляются только известные файлы и пустые подкаталоги нашего
временного каталога, без рекурсивного удаления пользовательского дерева.
Существующий каталог, файл или ссылка не заменяются. Неожиданные файлы
во временном каталоге сохраняются и приводят к явной ошибке очистки.

Успех — created/0 с путями, размерами и SHA-256 файлов, хешем шаблона;
отказ — blocked/2 с причиной. Форматы text/json; ошибки аргументов —
обычный argparse exit 2. platform_checked=false и launch_performed=false.

## Проверка

12 новых тестов проверяют комплектность/переносимые пути, сборку ERT,
неизменность шаблона, существующие пути и позднюю гонку с пустым каталогом,
порчу/ошибку записи, изменение шаблона, неправильный контейнер/сжатый модуль,
сроки и ID, отсутствие fallback при неподдерживаемой публикации, CLI
и вызов Linux API с флагом NOREPLACE и передачей errno.
