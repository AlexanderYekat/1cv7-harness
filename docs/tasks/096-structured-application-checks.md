# Задача 096. Структурированные прикладные проверки

Дата — 13 ноября 2026 года. Продолжение принятой 095. Реализация и проверка
завершены; результат принят владельцем 13 ноября 2026 года.

## Контракт и ожидаемый результат

Проект объявляет `expect_json` — **строку с JSON**, а не путь к файлу.
Она заменяет `expect_value` в выбранном тесте с `expect = "passed"`.
Для неё обязательна версия **профиля проекта** `schema_version = 2`.
Harness до 0.5.0 отвергает её до запуска, вместо игнорирования незнакомого поля.
Профили проекта версии 1 и профили стенда версии 1 сохраняются; project-init
по-прежнему создаёт минимальный строковый проект версии 1.
`json_labels` — необязательная таблица подписей по точным JSON Pointer:

```toml
schema_version = 2

[[platform.tests]]
name = "persisted-document-and-entries"
command = "verify"
expect = "passed"
expect_json = '''{"entries":[{"amount":"30"},{"amount":"40"}]}'''
json_labels = { "/entries/0/amount" = "Проводка 1, сумма", "/entries/1/amount" = "Проводка 2, сумма" }
```

Операция приложения возвращает JSON-текст обычным кооперативным протоколом.
Harness получает именно значение связанного с текущими run_id/ERT результата,
сохраняет точный UTF-8 текст в `structured/test-NNNN.actual.json` и включает
путь, SHA-256, размер, run_id и команду в evidence теста и result_files.
Хеш и размер записанного файла сверяются обратным чтением с исходным ответом;
отказ чтения или несовпадение блокирует результат.
В строке структурированного теста raw value не дублируется: остаётся ссылка
на файл, включая синтаксически повреждённый, но допустимый UTF-8 текст.
Launcher и нативный протокол не меняются. Core не ищет внешний файл или
прежний результат; бухгалтерские правила и подписи остаются в проекте.

Сравнение точное по всему дереву: порядок ключей объекта не важен, порядок
массива важен, отсутствующее значение отличается от null, лишние поля/элементы
дают расхождения. Строка, число и boolean различаются; числовые записи 1 и
1.00 равны. Десятичные JSON-числа сравниваются через Decimal без округления
в binary float. В диагностике дробные числа представлены десятичной строкой
с явным `expected_type/actual_type = "number"`. Денежные поля примера уже
передаются приложением строками, без локализованных разделителей.

`structured` содержит status, difference_count, differences и признак
усечения. Каждое расхождение содержит code, path, label, сообщение,
expected_present/actual_present, типы и значения присутствующих сторон.
Массивы в JSON Pointer имеют индекс с нуля; человекочитаемая подпись задаётся
проектом. Большие значения в диагностике усечены с отдельным признаком.

Корректный JSON с расхождениями даёт failed/1. Отсутствующее значение,
пустая строка, некорректный JSON/Unicode, дубли ключей, NaN/Infinity,
превышение лимитов или отказ сохранения дают blocked/2 с отдельным кодом.
Синтаксически пригодный, но неполный объект — обычное расхождение полей.
Raw-текст повреждённого JSON сохраняется, если доступен и укладывается
в лимит. При отказе самой операции JSON не оценивается: сохраняется причина
операции. До успешной проверки платформы прикладные тесты не оцениваются.

Лимиты: 1 MiB UTF-8 на ожидаемый и фактический JSON, глубина 64,
20 000 узлов; выводятся первые 100 расхождений с полным счётчиком.
Подписи проверяются до запуска: только существующие пути ожидаемого дерева,
до 160 символов без управляющих символов. Некорректные ожидания — ошибка
профиля до запуска 1С. Старые expect_value сохраняют прежнюю семантику.

Run.reason показывает первые два расхождения. Suite/JUnit включают
структурированную диагностику неуспешного теста; MCP получает её через
существующие отчёты и причину, без нового бизнес-адаптера.

## Реализация и переносимая проверка

`structured77` реализует ограниченный parser, точное сравнение и проверяемое
сохранение ответа. `config77` проверяет новую декларацию и версию профиля
до запуска. `run77` связывает диагностики и файлы с тестом, `suite77`
переносит их в сводку/JUnit. В 33 нативных файлах изменений нет.

Финальная поставка 0.5.0 собрана из sdist и установлена без зависимостей
в новый venv без pip. Из другого CWD, без PYTHONPATH/PYTHONHOME и соседних
репозиториев прошли **588 тестов, 5 пропусков**: четыре ограничения создания
symlink и одна проверка только для не-Windows. Десять новых тестовых методов
покрывают сравнение, типы, Decimal, пути/подписи, отсутствие/повреждение,
лимиты, ошибки записи/обратного чтения, совместимость версий профиля,
полный цикл и передачу диагностик в suite/JUnit. Прежние строковые ожидания
проверены общим набором; нативный `form-open` также сохраняет expect_value=1.

Wheel `harness77-0.5.0-py3-none-any.whl`, SHA-256:
`35cf181a9b57d856da727f32da3463646ed4685e1314fd7d341728d64bc8f47e`.
Журнал: [summary.json](../../.artifacts/s96-package-release/summary.json).
Предварительные сборки и прогоны сохранены отдельно; итоговые свидетельства
ссылаются именно на этот wheel и `s96-final-release`.

## Нативная приёмка

Из нового установленного wheel 0.5.0, без checkout-импортов:

1. Тот же документ и UI-шаги 095; новый независимый reader возвращает JSON
   со всеми полями документа, строками и проводками.
2. Baseline/regression/fixed/repeat-fixed при неизменном тесте.
   При регрессии ровно два расхождения `/entries/0/amount` (30 → 10) и
   `/entries/1/amount` (40 → 20), остальное дерево совпадает.
3. Отдельные отрицательные проекты: reader возвращает повреждённый и пустой
   JSON. Ожидаются blocked/2 с разными кодами при успешных UI и очистке.
4. Сохранность источника, реестра, чужих процессов, SHA-256, копии/замка;
   штатный старт, один Initialize и отсутствие принудительной очистки.

## Итоговые результаты

Самостоятельный [пример](../../examples/structured-checks/README.md) выполнен
из чистого venv `.artifacts/s96-kit-release/venv`, без checkout-импортов:

- **baseline — passed/0**, `7ca2c9b3-276f-4aba-a546-2c9da9b59cdf`.
- **regression — failed/1**, `6fcf495f-7fba-4c6e-a787-62c55ace7da4`.
  Ровно два расхождения: `/entries/0/amount` — ожидалось "30", получено "10";
  `/entries/1/amount` — ожидалось "40", получено "20". Run.reason содержит
  обе подписи «Проводка 1, сумма» и «Проводка 2, сумма» с этими значениями.
  Поля документа, строки, количества, счета и ссылки товара совпали.
  Провалился только `persisted-document-and-entries`.
- **fixed — passed/0**, `b3e11f8e-0e01-40c5-8428-28e61c9486eb`.
- **repeat-fixed — passed/0**, `21ebb9d8-2dcf-492d-8af7-31c6ec800c2d`.
- **invalid-json — blocked/2**, `c7fa8723-7bb5-4490-a1ea-7c132f3e06eb`:
  reader вернул `{`, код `json_result_invalid`; raw файл сохранён.
- **empty-json — blocked/2**, `f267c119-84a7-4f3e-9f3c-990d6e4b0906`:
  reader вернул пустую строку, код `json_result_missing`; пустой raw файл
  сохранён и не засчитан как успешная проверка.

Все шесть запусков имеют platform_checked=true и успешный нативный цикл.
В отрицательных случаях платформа/UI отработали штатно, а оценка JSON
заблокировала итог. Нативный старый строковый тест form-open прошёл во всех
шести случаях. Core 096 не подменяет результат операции исходом сравнения:
`structured.status` показывает результат JSON-проверки, `operation_status`
сохраняет исход операции.

Между четырьмя основными фазами хеши профиля, ERT-модуля, шаблона и сценария
не изменились. Два отрицательных профиля меняют только reader, с теми же
ожиданиями. Подготовка данных и 21 UI-шаг совпадают с 095. Независимая сверка
повторно проверила raw-протоколы, JSON, expected/actual, run_id, SHA-256 и
содержимое каждого сохранённого файла.

Сверены **3598 потоков** каждой из шести MD. При регрессии изменён только
поток модуля проведения, другие сборки совпадают с исходной MD; плановая MD
совпала с MD каждого run. В каждом старте подтверждены 12 стадий, собственный
OLE proxy, один Initialize, отсутствие AV и принудительного завершения.
Серверы завершились с 0; копии удалены, замок освобождён. Источник, MD/DD/DLL,
реестр, существующий guard, внешние процессы и входы сохранены. Внешний
PID 18812 с теми же parent/image/creation_filetime сохранён во всех фазах.

36 файлов установленного ядра совпали с checkout. Все 33 нативных файла
совпали с принятой поставкой 095: новая версия меняет ядро проверок,
не управление 1С. Фактический CLI **0.4.0** отдельно вызван с итоговым
профилем версии 2: blocked/2, platform_checked=false, каталог запуска не
создан, инвентарь процессов не изменён. Старый harness не может молча
пропустить новые ожидания.
