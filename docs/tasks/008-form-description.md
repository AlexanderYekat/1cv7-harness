# Этап 5.1, задача 008: описание формы ERT и первая кнопка

Дата: 18 октября 2026 года. Статус: **принято** —
[приёмка](008-form-description-acceptance.md); решения владельца приняты 18 октября.
Предшествующая задача — [007](007-reindex-aware-open-acceptance.md). Направление —
[раздел 5.1 дорожной карты](../roadmap.md#51-собирать-и-изменять-формы-ert-по-текстовому-описанию);
18 октября владелец решил выполнить её до разметки корня и каскада протокола.

## Зачем

`build` заменяет только модуль, форма всегда берётся из шаблона. Разработчик
или агент не может описать изменение формы текстом, собрать ERT и проверить,
что элемент виден и вызывает свой обработчик. Задача выполняет первые два шага
5.1: описание формы без потерь и одна новая кнопка, проверенная в настоящей 1С 7.7.
Визуальные тесты с эталонными снимками — следующая отдельная задача.

## Что известно (статическое обследование 18.10)

Корпус — `ExtForms` тестовой базы (локально, вне Git): 423 ERT, 418 уникальных,
417 с потоком `Dialog Stream`. Скрипты, выводы и хеши корпуса —
`.artifacts/forms/survey-20261018/`. Платформа при обследовании не запускалась.

- Во всех 417 формах заголовок длины — `0xFF` и uint16. 416 разбираются имеющимся
  `parse_dialog`; в `Export77.ert` есть байт `0x98`, которого нет в Windows-1251,
  а поток `Main MetaData Stream` не читается (повреждена цепочка FAT).
  `ДоговорПК 2003.ert` — пустой контейнер: только корневая запись, потоков нет.
- Строение: `{"Dialogs", Frame, Controls, Cnt_Ver}`. У 57 форм перед `Controls`
  есть безымянный раздел `{{{}},{}}`, у одной нет `Cnt_Ver`. Запись `Frame` —
  31 поле (у одной формы 29), запись элемента — 43 поля (у шести элементов 42).
- **Форматирование однозначно:** CRLF перед каждым вложенным списком, `""` внутри
  строк, два пробела после корня. По этому правилу из разобранного дерева
  восстановлены все 416 диалогов байт в байт. Хранить разметку отдельно не нужно.
- Числовой ID элемента (поле 9) уникален в каждой из 416 форм — это устойчивый
  идентификатор. Классы: BUTTON 2938, STATIC 2641, BMASKED 1021, 1CGROUPBOX 612,
  CHECKBOX 502, 1CEDIT 462, COMBOBOX 252, RADIO 160, LISTBOX 74, TABLE 69, PICTURE 10.
- Поля 0, 1, 9, 11, 12 (подпись, класс, ID, формула, идентификатор) уже читаются
  `dialog_controls`. По статистике и форме FIO: 3–6 — x, y, ширина, высота;
  41 — слой; у `Frame` 14–15 — ширина и высота, 16 — заголовок, 28 — слои.
  Единицы координат (пиксели или единицы диалога) не установлены. Смысл
  остальных полей не определялся.
- 279 из 8741 элементов выходят за границы формы: правило границ к существующим
  элементам неприменимо.
- Формулы кнопок: 2314 вызывают процедуру своего модуля, 390 — действия `#…`,
  84 — глобальные и встроенные функции (`ВвестиПериод`, `ЗапуститьПриложение`),
  104 — произвольные выражения, 46 пусты.

## Что делается

### Описание формы (продукт, переносимо)

- Формат — версионированный JSON (п. 1 решений). Описание содержит только
  поддерживаемые свойства: у формы — заголовок, ширину, высоту и слои; у элемента —
  ID, класс, подпись, x, y, ширину, высоту, формулу, идентификатор и слой.
  Описание привязано к шаблону через SHA-256 текста его диалога.
- `harness77 form-extract ФОРМА.ert --output form.json` создаёт описание.
  Как у `extract`, выход — только новый файл.
- `harness77 build --template … --source … --form form.json --output …` собирает
  модуль и форму за один раз. Без `--form` поведение прежнее.
- Остальные поля и разделы берутся из шаблона без изменений. Описание без правок
  собирает диалог байт в байт. Остальные потоки и метаданные каталога проверяются
  как в `build`; в отчёте — хеши описания и диалога до и после.
- Первый охват изменений — свойства существующих элементов из списка выше
  и новая кнопка (`BUTTON`). Она получает следующий по порядку ID и встаёт в конец
  списка (правило уточнено после F0, см. ниже). Поля вне описания берутся из закреплённой записи по умолчанию — самой
  частой записи кнопки в корпусе (347 из 2936, как «Закрыть» в FIO). Шрифт в ней —
  как у всех кнопок корпуса; слой — из описания или первый слой формы.
- Проверяется только то, что задаёт описание. Идентификаторы и слои шаблона
  не перепроверяются: 1С их уже приняла (в корпусе есть элемент с именем `Дата`).
- **Явный отказ:** описание другого шаблона (не тот хеш диалога); удаление,
  перестановка, смена класса или ID; повтор ID; новый элемент другого класса;
  новая кнопка вне клиентской области формы (уточнено после F2, см. ниже);
  слой, которого нет в форме. Формула новой
  или изменённой кнопки должна быть вызовом `Имя(…)` процедуры модуля или имени
  каталога платформы, иначе — отказ. Также отказ: подпись вне Windows-1251,
  смена вида заголовка длины, нечитаемый контейнер или диалог (`Export77.ert`),
  контейнер без модуля и диалога (`ДоговорПК 2003.ert`).
- Повторная сборка из тех же входов даёт те же байты; входы не меняются.
- `lint` берёт контекст формы для L7711 из описания, если оно задано. `run`
  получает `[build] form = "form.json"` в профиле проекта и передаёт его сборке.

### Нативная проверка (исследовательский адаптер, как в 006)

- Адаптер формы к launcher этапа 4. Модуль открывает форму видимой (без
  `СтатусВозврата(0)`) на собственном desktop сеанса.
- Launcher находит окно формы своего процесса на своём desktop и дочерние окна
  по ID элементов. Записывает их положение относительно клиентской области
  и DPI. Снимает форму существующим механизмом снимков — это свидетельство,
  а не сравнение.
- Нажатие — сообщением `BM_CLICK` окну кнопки: без глобальной мыши и клавиатуры,
  без переключения рабочего стола. Обработчик пишет маркер в параметр формы,
  контроллер читает его и закрывает форму.
- Если `BM_CLICK` неактивному окну не сработает, это записывается как исход.
  Другой способ нажатия согласуется с владельцем.

**Не входит:** сравнение снимков с эталоном (следующая задача); удаление элементов,
другие классы новых элементов, формы с нуля и формы внутри MD; YAML (если выбран
JSON); MCP; перенос кода NKDK (AGPL-3.0-or-later) — берутся только идеи.

## Исход F0 и изменённый способ (до F1–F4)

Первая попытка F0 (`84ec3cac`) остановилась до формы: контроллер не скомпилировался.
Вложенная компиляция с протоколом (`research/forms/diagnose_controller77.py`) дала
`{(10)}: Неправильное использование арифметической или строковой операции`
на `Если Команда = "check" ИЛИ Команда = "open" Тогда`; в 7.7 сравнения вокруг
`ИЛИ` берутся в скобки. Переменные модуля (`Перем`) в `ВыполняемыйМодуль` допустимы.

Повтор F0 (`4633a2d0`): `ОткрытьФорму` = 1; форма — MDI-окно «Фамилия, Имя, Отчество»
(`Afx:…`), внутри — `#32770` с девятью окнами ID 4152–4160 (`Button`, `Static`,
`1CEDIT`); форма закрыта, своя 1С завершена штатно, чужие сеансы сохранены.
**Предположение «ID в записи = ID окна» опровергнуто:** окно 4152 — последняя
запись («Фамилия:»), окно 4160 — первая («Закрыть»). Во всех 416 формах корпуса
поле 9 идёт подряд с 4152 в порядке записей, поэтому правило записывается так:
**окно записи с индексом i из N получает ID 4152 + N − 1 − i.** При этом
соответствии все девять элементов ложатся на одно отображение: около 1,5 px
по x и 1,625 px по y на единицу (единицы диалога шрифта MS Sans Serif 8 при 96 DPI)
со смещением около (−6; −24), то есть от внешнего края окна с заголовком.
Главное окно 1С в OLE-сеансе скрыто, все окна формы невидимы (`IsWindowVisible`
= false), снимки однотонны (305 и 251 байт); видимость проверяет F2m.

Изменения до F1–F4: проба сопоставляет записи и окна по этому правилу, масштаб
и смещение подбираются по положениям элементов, размеры сверяются с ними.
`click_id` — ID записи в описании; окно для `BM_CLICK` выводится по правилу.
В F2 новая кнопка — последняя запись, поэтому её окно ожидается с ID 4152,
а окна прежних элементов сдвигаются на единицу. В продукте ID новой кнопки
только продолжает последовательность (следующий после последнего); другой ID
— явный отказ, потому что 1С назначает ID окон по порядку записей.

## Исход F2 и проба F2b (добавлена до запуска)

F2 (`d2b90fad`) совпал с записанным ожиданием: окно новой кнопки — ID 4152
(`Button`, «Проверка»), прежние окна сдвинулись на единицу, положение в единицах F0
(остаток 0,12 px), `BM_CLICK` вернулся, `clicked:1` ровно один раз. Но окно стоит
на (222; −17) при высоте 21 px: смещение по y около −24 px — это заголовок окна,
около 15 единиц формы. Видна была бы полоска в 4 px, то есть F2m на этой ERT
не подтвердит видимость. Клиентская область формы FIO в единицах формы —
примерно от (4; 15) до (W − 3; H − 3); в корпусе 8730 из 8741 элементов стоят
не выше y = 15 и 8728 — не левее x = 4.

Изменения: продукт принимает новую или сдвинутую кнопку только внутри
[4, W − 3] × [15, H − 3] (наблюдение F0 на закреплённом стенде: Windows 11,
96 DPI, шрифт формы MS Sans Serif 8). Проба добавляет к нажатию признак
«кнопка целиком внутри клиентской области» и без него не засчитывает нажатие.

| № | Случай | Ожидание |
|---|---|---|
| F2b | кнопка «Проверка», ID 4161, x 152, y 16, 66×13, формула `Harness77Нажатие()` | окно 4152 около (222; 2), 99×21 px, целиком внутри клиентской области 329×174; `clicked:1` ровно один раз; `passed` |

F2m выполняется на ERT из F2b.

## Что нужно от владельца

1. **Формат описания.** Рекомендуется JSON: стандартная библиотека, без новых
   зависимостей (правило проекта), агенты пишут его надёжно. YAML можно добавить
   позже над той же моделью. Либо YAML сразу (PyYAML — новая runtime-зависимость
   с закреплением версии и проверкой офлайн-установки), либо TOML (чтение есть
   в Python 3.11, запись — своя).
2. **Шаблон нативной пробы.** Рекомендуется `FIO.ERT`: он закреплён на этапах 2 и 4,
   это небольшая настоящая форма. Либо другая форма.
3. **Ручная проверка.** Автоматическое нажатие — `BM_CLICK`. Нужна ли, кроме него,
   одна проверка вами: открыть собранную ERT из F2 в 1С, увидеть кнопку, нажать
   и увидеть сообщение обработчика (эталон «нажатие пользователем»)?
4. **Где код.** Рекомендуется: описание и сборка — продукт (`src/harness77`),
   нативный адаптер — `research/forms/`.
5. **Окно для прогонов.** Около 10 минут работы 1С на `base-for-test`;
   исполнитель запускает 1С сам.

## Решения владельца (18 октября 2026 года)

Приняты все предложенные варианты: формат описания — JSON; шаблон — `FIO.ERT`;
описание и сборка — в продукте, нативный адаптер — `research/forms/`; исполнитель
запускает 1С сам, около 10 минут на `base-for-test`. Кроме `BM_CLICK` — одна
ручная проверка владельцем (F2m): эталон нажатия пользователем.

## Приёмка

Переносимо: каждый отказ и каждое поддерживаемое изменение покрыты тестом
на синтетических формах. Все 416 читаемых форм корпуса проходят `form-extract`
и `build --form` без правок с диалогом байт в байт, `Export77.ert`
и `ДоговорПК 2003.ert` дают явный отказ. Повторная сборка воспроизводима, прежние тесты проходят. Нативно:
F0–F4 и F2m дали записанные исходы; завершение своей 1С подтверждено, чужие сеансы
сохранены; единицы координат установлены и записаны. Компиляция модуля или
проверка контейнера сама по себе работу формы не подтверждает.
