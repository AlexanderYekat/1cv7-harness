# Первая фича — разбор протокола ошибок 1С 7.7

Статус: задача подготовлена к разработке; реализация ещё не начата.

## Результат

Разработчик сохраняет текст ошибок Конфигуратора в файл и получает JSON с путём модуля, строкой, колонкой и сообщением каждой ошибки. Агент может использовать этот результат для исправления кода без ручного пересказа протокола.

Первый вариант обрабатывает сохранённые протоколы **ошибочной проверки внешней обработки ERT**. Он не запускает 1С, не определяет правильность прикладной логики и не классифицирует сообщения на первичные и каскадные.

## Место реализации

В существующем репозитории `1cv77-devtools`: модуль `compiler_protocol77.py` с отдельно вызываемой функцией разбора и тонким CLI; проверки — в `tests/test_compiler_protocol77.py`. Общий пакет и общий CLI harness для этой задачи не требуются.

Предлагаемый запуск из каталога devtools после реализации:

```powershell
python compiler_protocol77.py protocol.txt --format json --output result.json
```

Без `--output` JSON выводится в stdout. Служебные сообщения идут в stderr. Входной протокол не изменяется; выходной путь не может совпадать с входным.

## Вход и выход

Поддержать UTF-8, UTF-8 BOM и CP1251, окончания строк LF/CRLF. Формат записи: строка исходника с маркером `<<?>>`, затем `{путь(номер строки)}: сообщение`. Завершение текущих протоколов отмечено строкой `При проверке модуля обнаружены синтаксические ошибки!`.

Пример входа с условным путём:

```text
ОбработкаПрерыванияПользователя<<?>>();
{C:\project\report.ert(423)}: Процедура не обнаружена (ОбработкаПрерыванияПользователя)
При проверке модуля обнаружены синтаксические ошибки!
```

Диагностика из этого примера:

```json
{
  "file": "C:\\project\\report.ert",
  "line": 423,
  "column": 32,
  "message": "Процедура не обнаружена (ОбработкаПрерыванияПользователя)",
  "source_line": "ОбработкаПрерыванияПользователя();",
  "protocol_line": 2
}
```

Общий JSON содержит `schema_version: 1`, `tool: "compiler-protocol77"`, `scope: "imported_platform_protocol"`, `status`, SHA-256 исходных байтов протокола в `protocol_sha256`, массив `diagnostics` и массив `unparsed_lines` с номерами строк.

Строки и колонки нумеруются с единицы. Колонка — число Unicode-символов перед маркером плюс один; табуляция считается одним символом. При отсутствии маркера колонка равна `null`, без догадок. Строка исходника без маркера и сам текст сообщения сохраняются. Если предыдущая строка не является распознанной строкой исходника, `source_line` равен `null`.

Сохранить порядок и все повторяющиеся сообщения. Разбирать пути с пробелами, кириллицей и скобками. Путь из протокола остаётся текстовым значением, не открывается как файл и не разрешается относительно текущего каталога. Хеш или версия исходной ERT не выводятся из имени файла и не приписываются результату.

## Неполные и неизвестные входы

- Полностью распознанный протокол с диагностикой и завершающей строкой: `status: "failed"`, код возврата `1` — платформа сообщила об ошибках в импортированном протоколе.
- Пустой файл, произвольный текст, оборванная запись, непонятная значимая строка или отсутствие завершающей строки: `status: "blocked"`, код `2`. Уже извлечённые диагностики сохранить, непонятные строки перечислить в `unparsed_lines`.
- Отсутствие диагностик не означает успешную компиляцию. Распознавание протокола успешной проверки — отдельное расширение после появления подтверждённого образца.
- Пустые строки допустимы. Один завершающий маркер без диагностик не подтверждает пригодный результат. Ошибка чтения файла даёт код `2` и понятное сообщение; старый выходной файл не выдаётся за новый результат.

Статус относится к импортированному свидетельству. Он не подтверждает, что текущая версия ERT совпадает с проверявшейся, или что проверена вся конфигурация.

## Проверяемая приёмка

1. Локальный P2 из `research/kudir/corpus/p2-compile-errors/compiler-protocol.txt` даёт **7 диагностик**, строки 423, 428, 1012, 1045, 1229, 1443, 2393; порядок и сообщения сохранены.
2. Локальный P1 из `research/kudir/corpus/p1-compile-errors/compiler-protocol.txt` даёт **60 диагностик**, включая повторения на строке 311. Каскадные сообщения не удаляются эвристикой.
3. Пустой, неизвестный и обрезанный протокол дают `blocked` и код `2`; результаты не выглядят успешной проверкой.
4. Небольшие тесты проверяют кодировки, окончания строк, отсутствие маркера, пути со скобками, повторения и запрет записи поверх входа. Структура JSON и коды CLI проверяются автоматически.
5. Для воспроизводимого набора в Git подготовлены компактные синтетические либо очищенные примеры без личных путей. Исходные локальные P1/P2 остаются неизменными и не добавляются в Git автоматически. Их отсутствие не скрывает провал обязательных тестов: основная приёмка запускается на поставляемых fixtures, проверка оригиналов обозначается отдельно.
6. Все существующие **31 тест линтера** продолжают проходить. Не изменены правила lint77, сборка ERT и синхронизация модулей.

Готовый результат задачи: функция разбора, CLI, тесты, минимальные fixtures и короткая инструкция с примером. Автоматизация платформы, новые правила языка и переработка архитектуры в эту фичу не входят.
