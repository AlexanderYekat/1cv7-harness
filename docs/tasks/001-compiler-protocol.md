# Методологическое ТЗ: разбор протокола ошибок 1С 7.7 в JSON

Дата: 10 октября 2026 года. Версия: 1.1. Статус: реализовано и принято; фактические проверки и ограничения — в [отчёте приёмки](001-compiler-protocol-acceptance.md).

Это задание на **шаг 1 [дорожной карты](../roadmap.md)**. Оно развивает ранее подготовленное короткое задание и задаёт достаточные условия реализации и приёмки. [Архитектура](../architecture.md) определяет границы компонентов, [рамочное ТЗ](../restructuring-spec.md) — дальнейшее развитие, [манифест](../baseline.json) — исходное состояние инструментов.

Устройство реализации, алгоритм, файловые операции и тестовые сценарии определены в отдельном [техническом ТЗ](001-compiler-protocol-technical.md). Разработка выполняется по обоим документам; подготовка технического ТЗ не меняет статус реализации.

## 1. Проблема и ожидаемый результат

Разработчик сохраняет текст ошибок Конфигуратора 1С 7.7 в файл. Инструмент преобразует его в JSON: путь модуля, номер строки, колонка, сообщение и фрагмент исходника. Разработчик или агент получает пригодные для обработки диагностики без ручного пересказа и может запросить повторную проверку после исправления кода.

Результат этапа — самостоятельная функция разбора, тонкий CLI, переносимые тестовые данные, автоматические проверки и инструкция. Фича работает без установленной 1С, базы, ERT и 77MCP.

**Ключевой принцип:** инструмент сообщает, что содержится в предоставленном протоколе. Он не утверждает, что проверил текущую ERT, весь проект или прикладную логику. Даже полностью распознанный протокол не доказывает подлинность, актуальность или полный охват исходной проверки.

## 2. Основания и границы

### Подтверждённые исходные данные

При подготовке ТЗ прочитаны локальные протоколы из [корпуса КУДиР](../../research/kudir/README.md); их SHA-256 совпадают с локальным `research/kudir/corpus/manifest.json`:

- **P2:** `research/kudir/corpus/p2-compile-errors/compiler-protocol.txt`, 15 строк протокола, 7 диагностик. Строки модуля: 423, 428, 1012, 1045, 1229, 1443, 2393.
- **P1:** `research/kudir/corpus/p1-compile-errors/compiler-protocol.txt`, 121 строка протокола, 60 диагностик. Первые девять относятся к строкам 63, 64, 66, 101, 107, 304, 306, 307, 309; остальные 51 — к строке 311.
- В обоих образцах каждая диагностика имеет предыдущую строку с одним маркером `<<?>>`; последняя строка — `При проверке модуля обнаружены синтаксические ошибки!`.

Это проверка сохранённых файлов, а не новый запуск платформы. Поддержка дополнительных кодировок и пограничных случаев ниже задаётся как требование и должна подтверждаться тестами.

### Что входит

Чтение одного текстового файла; декодирование; последовательный разбор записей; сохранение всех диагностик и необработанного текста; определение полноты поддерживаемого формата; выдача JSON и кода завершения.

### Что остаётся за пределами этапа

- Запуск и управление 1С, создание копии базы, автоматическое получение протокола.
- Чтение, сборка или изменение ERT; сопоставление протокола с текущей версией исходника.
- Распознавание успешной компиляции, журналов исполнения и других форматов сообщений платформы.
- Классификация ошибок на первичные и каскадные, удаление повторов, предложение исправлений, новые правила lint77.
- Общий пакет harness77, общий CLI, CI, MCP и перенос кода между репозиториями.

Эти работы не являются скрытыми условиями приёмки. Описанные в исследовании КУДиР эвристики каскада в этот контракт не переносятся.

## 3. Пользовательский сценарий и интерфейс

Ниже — доступные команды реализации. Из каталога `1cv77-devtools`:

```powershell
python compiler_protocol77.py protocol.txt --format json --output result.json
python compiler_protocol77.py protocol.txt --format json
python compiler_protocol77.py protocol.txt --encoding cp1251 --format json
```

- Обязательный позиционный аргумент — путь одного протокола. Путь к входу и выходу разрешается относительно рабочего каталога вызывающего процесса.
- `--format json` — единственный формат, также используемый по умолчанию.
- `--encoding auto|utf-8|cp1251`, по умолчанию `auto`; явный выбор позволяет устранить неоднозначность кодировки.
- Без `--output` stdout содержит ровно один JSON-документ с завершающим переводом строки. С `--output` JSON записывается в указанный файл, stdout пуст. Служебные сообщения идут в stderr.
- JSON выдаётся в UTF-8 без BOM. Перенаправление stdout должно сохранять этот формат независимо от кодовой страницы Windows.
- Запуск по абсолютному пути к скрипту из другого каталога даёт тот же содержательный результат. Пользовательские пути, соседние базы и локальный корпус не являются неявными зависимостями.

Пользователь обязан учитывать код возврата текущего вызова. Само наличие `result.json` от прежнего запуска не является результатом нового вызова.

## 4. Правила чтения и разбора

### 4.1. Байты, кодировка и строки

1. Вход читается как байты. SHA-256 вычисляется до декодирования, удаления BOM и обработки переводов строк; используется шестнадцатеричная строка из 64 символов в нижнем регистре.
2. В режиме `auto`: UTF-8 BOM означает строгое чтение UTF-8 с удалением BOM; без BOM сначала проверяется строгий UTF-8, при ошибке — строгий CP1251. UTF-16/UTF-32 с BOM отклоняются как неподдерживаемые. Ошибка UTF-8 после его BOM не запускает fallback на CP1251.
3. При явном `utf-8` допустим UTF-8 с BOM или без него; при `cp1251` выполняется строгое чтение CP1251. Замены ошибочных байтов, `errors="ignore"` и исправление текста запрещены. Известный BOM другой кодировки отклоняется и при явном выборе.
4. `input_encoding` фиксирует фактически применённый вариант: `utf-8`, `utf-8-sig` или `cp1251`. При невозможности декодирования — `null`. Автовыбор является правилом обработки, а не доказательством исходной кодировки произвольного файла.
5. Поддерживаются LF и CRLF, включая их смесь и отсутствие перевода строки после последней строки. Одиночный CR не считается допустимым разделителем и делает содержащую его строку нераспознанной.
6. Нумерация физических строк начинается с единицы и учитывает пустые строки. Пустые строки и строки только из пробелов/табуляций допустимы; они не удаляются до вычисления номеров.

### 4.2. Формат записи

Обычная запись состоит из двух соседних физических строк:

```text
ОбработкаПрерыванияПользователя<<?>>();
{C:\project\report.ert(423)}: Процедура не обнаружена (ОбработкаПрерыванияПользователя)
```

Вторая строка распознаётся самостоятельно по форме `{путь(номер)}: сообщение`. Номер — непустая последовательность ASCII-цифр, числовое значение не меньше 1. Путь и сообщение непустые, не состоят только из пробелов/табуляций. После `}:` один пробел служит разделителем; остальные символы сообщения сохраняются, включая начальные и конечные пробелы.

Уточнение версии 1.1: после удаления ведущих нулей номер содержит не более **640 значащих цифр**. Это технический предел импорта для гарантированной JSON-сериализации без обхода ограничения Python. Более длинный заголовок целиком остаётся нераспознанным и приводит к `blocked`; `<<?>>` в его сообщении не превращает его в исходник следующей диагностики. Количество ведущих нулей не входит в предел.

Суффикс с номером находится у закрытия `}:`, поэтому пробелы, кириллица и скобки внутри пути не обрезают его. Путь хранится без нормализации и проверки существования, расширения или доступности файла. Например, `C:\Тест (копия)\отчёт.ert` должен сохраняться целиком.

### 4.3. Исходная строка и колонка

- Строка исходника признаётся частью записи, если она непосредственно предшествует распознанной строке диагностики и содержит ровно один `<<?>>`. Строки диагностик и завершающий маркер имеют приоритет перед распознаванием исходника.
- `source_line` — эта строка с удалением только маркера; пробелы, табуляции и прочий текст сохраняются. Строка только из маркера даёт `source_line: ""`.
- `column` — число Unicode-кодовых точек до маркера плюс один. Табуляция считается одним символом, визуальная ширина и байты кодировки не учитываются.
- При отсутствии подтверждённой строки исходника диагностика сохраняется с `column: null` и `source_line: null`. Отдельная корректная строка `{путь(номер)}: сообщение` допустима.
- Произвольная предыдущая строка без маркера не объявляется исходником по сходству с кодом. Если она значимая, она попадает в `unparsed_lines`, а весь протокол получает `blocked`.
- Два и более маркера, маркер без следующей диагностики или пустая строка между исходником с маркером и диагностикой не дают достоверной пары. Непривязанная значимая строка сохраняется в `unparsed_lines`; диагностика, если она распознаётся отдельно, остаётся в результате.

Для примера выше результат записи:

```json
{
  "file": "C:\\project\\report.ert",
  "line": 423,
  "column": 32,
  "message": "Процедура не обнаружена (ОбработкаПрерыванияПользователя)",
  "source_line": "ОбработкаПрерыванияПользователя();",
  "protocol_line": 2
}
```

`protocol_line` указывает на строку с `{путь(номер)}: сообщение`, а `line` — на строку модуля из неё. Эти координаты не смешиваются.

### 4.4. Завершение и неизвестные строки

Единственный поддерживаемый завершающий маркер — точная строка:

```text
При проверке модуля обнаружены синтаксические ошибки!
```

Для полного протокола он встречается ровно один раз и является последней значимой строкой после хотя бы одной диагностики. Пустые строки после него допустимы. Повторный маркер, значимый текст после него или маркер перед диагностикой нарушают контракт.

Разбор продолжается после неизвестной строки и после неверно расположенного завершения: последующие распознаваемые диагностики также сохраняются. Это позволяет получить полезную частичную информацию, сохраняя статус `blocked`.

Каждая значимая строка должна быть учтена как часть диагностики, завершающий маркер или запись `unparsed_lines`. Нельзя молча пропускать заголовки, служебные сообщения, непонятные окончания и оборванные записи. Каждый повтор диагностик сохраняется в исходном порядке.

## 5. Контракт результата

Результат функции разбора и JSON CLI используют одну структуру. Все перечисленные поля обязательны:

- `schema_version`: целое `1`.
- `tool`: строка `compiler-protocol77`.
- `scope`: строка `imported_platform_protocol`.
- `status`: `failed` или `blocked`, по правилам раздела 6.
- `protocol_sha256`: SHA-256 исходных байтов, включая BOM и исходные переводы строк.
- `input_encoding`: значение из раздела 4.1 либо `null`.
- `diagnostics`: массив записей с шестью полями из примера выше. `file` и `message` — строки; `line` и `protocol_line` — положительные целые; `column` — положительное целое или `null`; `source_line` — строка или `null`.
- `unparsed_lines`: массив объектов `{"protocol_line": 5, "text": "неизвестный текст"}` в порядке исходного файла. Текст сохраняется без разделителя строки, каждая физическая строка включается не более одного раза.
- `issues`: массив объектов с полями `code`, `message`, `protocol_line`. Сообщение объясняет причину блокировки; номер — положительное целое для локальной проблемы или `null` для проблемы всего входа.

Коды `issues` фиксируются для машинной обработки:

- `empty_protocol` — после декодирования нет значимых строк.
- `no_diagnostics` — не извлечено ни одной диагностики.
- `missing_terminator` — завершающий маркер отсутствует.
- `invalid_terminator` — маркер повторяется или не является последней значимой строкой после диагностик; указывается номер проблемного маркера.
- `unparsed_line` — значимая строка не распознана; номер соответствует записи `unparsed_lines`.
- `unsupported_encoding` — обнаружен неподдерживаемый или противоречащий явному выбору BOM.
- `decode_error` — строгое декодирование доступными в выбранном режиме способами не удалось.

После успешного декодирования перечисляются все применимые причины без дублирования одной причины на одной строке; общие причины могут иметь `protocol_line: null`. При ошибке декодирования фиксируется причина чтения байтов, `input_encoding: null`, остальные массивы, кроме `issues`, пусты; проверка текстовой структуры не выполняется. При `failed` массивы `unparsed_lines` и `issues` пусты.

Результат детерминирован: одинаковые байты и выбранная кодировка дают одинаковые значения полей и порядок элементов. Сериализация CLI также стабильна. В JSON не включаются текущее время и случайные идентификаторы.

Из пути ERT нельзя выводить её хеш, версию или связь с текущими исходниками. Поля вроде `source_hash`, `artifact_sha256`, признака успешной компиляции и классификации `root`/`cascade` в версии 1 не добавляются.

## 6. Статусы, коды возврата и сохранность файлов

- **`failed`, код `1`:** есть хотя бы одна диагностика, ровно один правильно расположенный завершающий маркер, все значимые строки распознаны, проблем декодирования нет. Значение означает: в импортированном протоколе сообщено об ошибках платформы.
- **`blocked`, код `2`:** нарушено хотя бы одно условие пригодности протокола. В частности, пустой файл, один завершающий маркер, неизвестный текст, оборванная запись и отсутствие завершения не являются успехом. Извлечённые диагностики сохраняются.
- При одновременном наличии диагностик и неполноты приоритет имеет `blocked` и код `2`.
- Обработка входного протокола **никогда не возвращает код `0`**. Код `0` допустим для `--help`, который не является проверкой протокола.

Ошибки аргументов, чтения входа, конфликта путей или записи результата завершают CLI кодом `2` и понятным сообщением в stderr. При этих ошибках JSON не гарантируется; частичный документ не должен выдаваться за законченный результат. Штатные ошибки не сопровождаются traceback.

Входной файл не изменяется. До записи необходимо исключить совпадение входа и выхода: относительное/абсолютное написание, регистр на Windows и файловые ссылки не должны позволять перезаписать вход. Для существующих файлов сравнивается также их файловая идентичность, а не только строки путей.

При `--output` сначала полностью формируется JSON, затем записывается во временный файл в каталоге назначения и заменяет результат после успешной записи. Родительский каталог должен существовать. Старый результат сохраняется при ошибке до замены; stderr явно сообщает, что новый результат не записан и прежний файл не относится к этому вызову. Временный файл, созданный этим вызовом, убирается при обрабатываемой ошибке.

Корректно сформированный отчёт `blocked` также записывается: это новый отчёт о непригодном входе. Для stdout гарантируется подготовка полного JSON до начала вывода; сбой самого канала вывода означает код `2` и не подтверждает получение отчёта адресатом.

## 7. Место реализации и последовательность работ

Реализация находится в самостоятельном репозитории `1cv77-devtools`; корневой репозиторий хранит это ТЗ. Истории Git не объединяются, существующие пользовательские изменения сохраняются.

Предусмотреть:

- `compiler_protocol77.py`: отдельно вызываемая функция `parse_protocol(data: bytes, *, encoding: str = "auto") -> dict` и тонкий CLI.
- `tests/test_compiler_protocol77.py`: тесты разбора и запуска CLI, совместимые с `unittest discover`.
- `tests/fixtures/compiler_protocol77/`: переносимые образцы, ожидаемые результаты и описание происхождения.
- Короткую инструкцию в README devtools либо отдельном документе со ссылкой из него: входной формат, команды, значения статусов, ограничения и запуск тестов.

Достаточно стандартной библиотеки Python 3.11+. Функция разбора не читает и не пишет файлы, не печатает сообщения, не запускает процессы и не импортирует платформенные компоненты. Непригодные входные байты возвращают `blocked`; неверное значение программного аргумента `encoding` считается ошибкой вызова API и вызывает `ValueError`. CLI проверяет варианты аргумента до вызова функции.

Порядок разработки:

1. **Зафиксировать свидетельства.** Подготовить переносимые P1/P2, описать очистку, проверить число, порядок и текст диагностик независимо от будущего парсера.
2. **Реализовать разбор байтов.** Сначала проверяемые записи и координаты, затем полноту, неизвестные строки и кодировки. Подтвердить результат тестами функции.
3. **Добавить файловую оболочку.** CLI, кодировку вывода, коды завершения, защиту входа и замену выходного файла; проверить вызов отдельным процессом из постороннего каталога.
4. **Провести приёмку.** Проверить весь переносимый набор и прежние тесты линтера. При наличии оригиналов отдельно сверить P1/P2, не меняя их.
5. **Описать результат.** Записать выполненные команды, число прошедших/пропущенных тестов и ограничения; обновить статус шага 1 в дорожной карте и выбрать шаг 2 для следующего задания.

## 8. Методика подготовки переносимого корпуса

Оригинальные P1/P2 остаются локальными свидетельствами и не редактируются. Их нельзя автоматически добавить в Git вместе с реализацией.

Для обязательной приёмки предпочтительны очищенные текстовые копии: личные каталоги заменяются постоянным условным путём, исходные сообщения, строки модуля, маркеры, порядок и повторения сохраняются. Перед включением нужно просмотреть весь текст на прикладные и личные сведения. Если очистки пути недостаточно, готовится явно обозначенный синтетический эквивалент с теми же проверяемыми свойствами; совпадение исходных сообщений тогда проверяется отдельно на локальном оригинале.

Для каждого образца фиксируются идентификатор P1/P2, вид `sanitized` или `synthetic`, происхождение, сделанные преобразования, кодировка, SHA-256 поставляемого файла и ожидаемые диагностики. Хеш очищенного файла не выдаётся за хеш оригинала.

Ожидания хранятся как проверенный эталон или явные независимые утверждения. Нельзя получать ожидаемый JSON тем же парсером во время теста: совпадение двух вызовов не доказывает правильность разбора.

Основной набор работает из чистого checkout devtools без `research/kudir/corpus`, 1С и базы. Отсутствие поставляемого fixture — ошибка обязательного теста. Проверка локальных оригиналов запускается отдельно, а их отсутствие обозначается как «не выполнена» и не превращается в успешную проверку оригиналов.

## 9. Проверяемая приёмка

Задача принимается только при выполнении всех обязательных пунктов:

1. **P2:** переносимый образец даёт `failed`, код `1`, ровно 7 диагностик с указанными в разделе 2 строками; проверяются сообщения, порядок, координаты и исходный текст каждой записи.
2. **P1:** переносимый образец даёт `failed`, код `1`, ровно 60 диагностик, из них 51 на строке 311; повторяющиеся записи и сообщения не удаляются и не объединяются. Для очищенных копий тексты сообщений совпадают с оригиналом; для синтетических — с документированным эталоном.
3. **Декодирование:** один небольшой пример в UTF-8, UTF-8 BOM и CP1251 даёт одинаковые диагностики; `input_encoding` и SHA-256 соответствуют реальным байтам каждого файла. Проверяются явная кодировка, невалидный UTF-8 после BOM, неподдерживаемый BOM и строгая ошибка CP1251. При изменении только BOM или LF/CRLF хеш меняется, содержательные диагностики сохраняются.
4. **Координаты:** кириллица, табуляция, маркер в начале/конце строки, Unicode-символ вне BMP и пустая исходная строка дают ожидаемые колонки. Проверяются `protocol_line` с пустыми строками, LF/CRLF и файл без конечного перевода строки.
5. **Границы записи:** путь с пробелами и скобками, сообщение с дополнительными двоеточиями/скобками, диагностика без исходной строки, нулевой и нечисловой номер, пустой путь/сообщение, несколько маркеров и непривязанный исходник обрабатываются по контракту. Путь из протокола не открывается.
6. **Неполнота:** пустой файл, произвольный текст, только завершающий маркер, обрыв пары, отсутствие завершения, неизвестная строка между записями, одиночный CR, повторный или преждевременный маркер дают `blocked` и код `2`. Уже найденные диагностики остаются; неизвестные строки и причины имеют точные номера. Проверяется продолжение разбора после повреждённого участка.
7. **CLI и файловые ошибки:** JSON корректен в stdout и файле; служебный текст отсутствует в stdout; коды совпадают со статусами. Недоступный вход, невалидные аргументы и отказ записи дают `2`. Старый выход при отказе не изменён и не объявлен новым; штатный `blocked` заменяет его полноценным новым отчётом.
8. **Сохранность и переносимость:** запрет записи поверх входа проверен для разных написаний пути и существующего hard link; вход побайтно прежний. Windows-проверки ссылок/регистра выделяются явно, отсутствие возможности создать ссылку не выдаётся за пройденную проверку защиты. Запуск скрипта из постороннего каталога работает; обязательные fixtures доступны без локального корпуса.
9. **Регрессия:** все существующие 31 тест линтера продолжают проходить. Не изменены правила lint77, сборка ERT и синхронизация модулей. Набор 77MCP не требуется: этот этап не меняет и не использует его код.
10. **Комплектность:** доступны реализация, тесты, fixtures с происхождением, инструкция и фактический отчёт приёмки. Структура JSON и отсутствие неподтверждённого `passed` проверяются автоматически.

Целевые команды из каталога devtools:

```powershell
python -B -m unittest discover -s tests -p test_compiler_protocol77.py -v
python -B -m unittest discover -s tests -p test_lint77.py -v
```

Ожидается проходящий набор нового парсера и 31 проходящий тест линтера. Число новых тестов определяется содержательными сценариями; формальное увеличение количества не является критерием качества. Тестовые файлы создаются во временном каталоге, оригиналы корпуса не перезаписываются.

## 10. Условия завершения и переход дальше

Подготовка этого ТЗ не означает завершения шага 1. Статус меняется только после реализации и подтверждения раздела 9; результаты проверок должны быть отделены от планируемых возможностей.

По завершении обновляются [дорожная карта](../roadmap.md) и [корневой README](../../README.md). Исторический `baseline.json` сохраняет исходный срез; результаты новой приёмки описываются отдельно.

Следующее задание — **шаг 2: эксперимент с настоящей 1С 7.7**. Его цель — подтвердить способ запуска, реальный охват проверки и различимость ошибки кода, сбоя среды и успеха. Парсер предоставляет формат импортированного свидетельства, но не заменяет этот эксперимент. Успешный протокол и привязка к конкретной ERT потребуют подтверждённых образцов и отдельного расширения контракта.
