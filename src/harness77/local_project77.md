# Локальное подключение harness77 (099)

Требуется Python >=3.11. Для подготовки wheel нужен pip >=22.3 в Python,
которым запущен launcher (`python -m pip --version`). uv не требуется.
Python, pip, 1С, компоненты и PATH автоматически не устанавливаются.

Первичное подключение — явный вызов из установленного дистрибутива:

```powershell
python -m harness77 connect --directory C:/work/application --wheel C:/releases/harness77-0.7.0-py3-none-any.whl --bundle --format json
```

Подключение сохраняет существующий AGENTS.md и добавляет отделённый блок;
создаёт `.harness77/` и пустой `harness77.txt`. Исходники, профили, база,
внешние окружения, глобальные правила, skills, настройки Codex и регистрация
MCP не меняются. При несовместимых файлах — отказ до записи; при ошибке —
откат своих изменений. Повтор той же команды сохраняет настройки и байты.
Изменённые настройки не перезаписываются молча.

В корне автоматически распознаются TOML с `[project]`, `[stand]`, `[suite]`.
Несколько профилей одного типа требуют явного `--project`, `--stand` или
`--suite`. Нужны существующий стенд и проект либо suite. Для профилей в других
каталогах передайте пути явно. Привязки сохраняются в config.json; дальнейшие
вызовы не требуют повторного выбора базы. База берётся только из `[stand.base]`
`path`, с разрешением относительно профиля стенда. Списки запуска 1С, v8project,
v8stands и произвольные строки подключения автоматически не распознаются.
Проверку совместимости и квалификации выполняет прежний doctor/runtime.

```powershell
python C:/work/application/.harness77/launch.py status --format json
python C:/work/application/.harness77/launch.py prepare --format json
python C:/work/application/.harness77/launch.py doctor --format json
python C:/work/application/.harness77/launch.py run
python C:/work/application/.harness77/launch.py suite
python C:/work/application/.harness77/launch.py mcp
```

Статус не скачивает и не устанавливает пакет, не запускает harness или 1С.
Он проверяет целостность имеющейся поставки и показывает источник, версию,
SHA-256, Python, пакет, привязки и базу. Подготовка установки отдельная либо
при первом вызове. `ready` означает готовность подключения; нативную готовность
проверяйте doctor. Коды run/suite и диагностика failed/blocked сохраняются.
Результаты по умолчанию — `.harness77/results/`, можно задать `--output-root`.
Пути привязок и поставок в config.json разрешаются от `.harness77/`, а не CWD.
Параметры остальных команд и явно переданные параметры run/suite — по их
обычному контракту; дочерняя команда работает из корня проекта.

Три способа получить одну закреплённую поставку:

1. Внешний wheel: `connect --wheel C:/releases/harness77-0.7.0-py3-none-any.whl`
   без `--bundle`. Установка идёт в окружение проекта. Либо
   `connect --external-python C:/tools/h77/Scripts/python.exe`: окружение только
   читается; закрепляются версия и SHA-256 карты всех файлов пакета. Это
   отпечаток установленной поставки, не SHA-256 исходного wheel. Не выбирается
   произвольная команда harness77 из PATH. Внешний путь обязателен, если задан:
   при его потере/повреждении нет перехода к другой поставке.
2. Wheel внутри проекта: `connect --wheel ... --bundle`. Wheel и SHA-256 входят
   в переносимый комплект; подготовка и работа офлайн, checkout не требуется.
3. Скачивание: `connect --version 0.7.0 --url URL --sha256 TRUSTED_SHA256`.
   URL должен указывать конкретный wheel через HTTPS, например asset
   GitHub Releases: `https://github.com/OWNER/REPO/releases/download/v0.7.0/harness77-0.7.0-py3-none-any.whl`.
   Это форма адреса, не обещание существующего опубликованного релиза.
   SHA-256 берите из доверенного канала; токены, пароли и query в URL запрещены.
   Для закрытого GitHub сначала скачайте wheel авторизованным клиентом и
   используйте способ 1 или 2. Код не публикует релизы и не меняет аутентификацию.

Выбор: явный путь → включённый wheel → проверенный кеш → закреплённый URL.
Чтобы разрешить bundled fallback при отсутствии локального wheel, можно
задать одновременно `--bundle --wheel ... --url ...`. Имеющийся повреждённый
wheel/кеш или неверная версия дают отказ. Сеть и установка выполняются pip
с `--no-index --no-deps`, версия не обновляется автоматически. SHA-256 проверяется
до установки. Зависимостей времени исполнения у дистрибутива нет.
Повтор использует проверенное окружение без сети и переустановки.

Команда подготовки сериализована fail-fast lock; незавершённый кеш никогда
не готов. После штатной ошибки собственный неполный кеш удаляется. После
жёсткого завершения процесса явно удалите только указанные в диагностике
каталог кеша/lock и повторите prepare. Повреждённые готовые кеши автоматически
не заменяются. Для смены версии сохраните конфигурацию и вызовите connect в
чистой `.harness77/` после явного удаления старого управляемого блока либо
подготовьте новый каталог проекта; новая версия/хеш всегда задаются явно.

В Git/архив включайте AGENTS.md, harness77.txt, `.harness77/launch.py`, README,
config.json, `.gitignore`, профили и при необходимости packages/*.whl.
Кеш, окружение и результаты игнорируются внутренним .gitignore. Готовый venv
не переносите. В копии/клоне запускайте prepare заново; для переносимости
используйте относительные привязки и bundled wheel, удалите абсолютные пути
автора. Путь установленной 1С и базы остаётся настройкой выбранного стенда.

Удаление `harness77.txt` выключает новые обращения. Без маркера launcher не
читает конфигурацию, не делает сеть/установку и не запускает harness/1С;
status/prepare возвращают disabled/0, попытка операции — disabled/2.
Содержимое маркера игнорируется. Открытый MCP проверяет маркер перед каждой
новой tools/call; initialize, ping, tools/list и штатная отмена доступны.
Удаление маркера не отменяет уже принятую операцию; используйте штатную отмену.
Слежения Codex за файловой системой не обещается. Прямой вызов внешнего
harness77 остаётся самостоятельным явным действием пользователя.
