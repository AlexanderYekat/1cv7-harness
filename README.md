# harness77

Инструментарий для воспроизводимой разработки и проверки кода **1С 7.7**.

Цель проекта: исходники и контекст → статические проверки → сборка ERT → проверка настоящей платформой → тесты на выбранной тестовой базе → отчёт. Пакет `harness77` объединяет статический анализ, импорт ошибок Конфигуратора, извлечение модулей, проверяемую сборку новой ERT и полный цикл с проверкой настоящей платформой.

Куда двигаться дальше — в [короткой дорожной карте](docs/roadmap.md). Границы компонентов описаны в [начальной архитектуре](docs/architecture.md), выполненные переносы — в [журнале упорядочивания](docs/housekeeping.md). Подробный проект требований — [методологическое ТЗ](docs/restructuring-spec.md).

## Что находится в проекте

```text
harness77/
  README.md                 назначение и вход в проект
  pyproject.toml            устанавливаемый пакет и команда harness77
  src/harness77/            код продукта и встроенный словарь
  tests/                    переносимые проверки без 1С
  examples/                 минимальный текстовый модуль
  docs/                     архитектура, ТЗ и журнал изменений структуры
  1cv77-devtools/            существующие инструменты, отдельный Git-репозиторий
  77MCP/                    чтение метаданных и MCP, отдельный Git-репозиторий
  third_party/              исходники 1С++ и FormEx, адреса и хеши загрузок
  research/
    README.md               назначение исследовательских материалов
    kudir/                  опыт КУДиР, прототипы и корпус примеров
    rules77/                нативные пробы правил анализа (задача 005)
    76av/                   скрипты исследования 76.АВ и инструкция
    archive/                первоначальные вспомогательные материалы
  .local/
    bases/base-for-test/    локальная база, ранее лежала в корне
    configurations/reference/  снимок MD/DD для статического анализа
    research/76av/          локальные выгрузки и исторические отчёты 76.АВ
    maintenance/            снимок и проверки этого упорядочивания
```

`1cv77-devtools` и `77MCP` остаются самостоятельными репозиториями на прежних местах. Полезные модули devtools импортированы в пакет; [карта переноса](docs/migration.md) и [происхождение](docs/provenance.json) фиксируют ревизии и хеши. Исследование 76.АВ разделено на [скрипты](research/76av/README.md) и локальные данные; прежний `.diagnostics` полностью разобран.

Исходники внешних компонент для исследования платформы собраны в [third_party](third_party/README.md). Архивы и распакованные снимки находятся локально; в корневом Git сохраняются их происхождение, версии и контрольные суммы.

MD/DD перенесены из корня в `.local/configurations/reference`. Они совпадали с файлами базы при обследовании; это зафиксированный снимок для анализа, автоматической синхронизации с базой нет. Его происхождение и хеши записаны в локальном `manifest.json`. Не редактируйте обе копии как независимые версии одной конфигурации.

В корневом Git хранятся код пакета, тесты, документация и исследовательские скрипты. Для установки продукта достаточно корневого репозитория. Вложенные репозитории исключены из него, их истории сохранены; они нужны для работы с исходными инструментами и прежними исследованиями. [Манифест исходного состояния](docs/baseline.json) остаётся историческим снимком. Локальные данные восстанавливаются отдельно.

## Что уже можно использовать

- `harness77 lint`: частичный статический анализ текста, ERT и MD; JSON-диагностики. Имена встроенных функций и методов — из каталога платформы 7.70.027; правила L7708–L7711 (зарезервированные имена, лишние аргументы метода, длинная строка, необъявленная переменная) откалиброваны пробами на настоящей 1С. Успех линтера не подтверждает компиляцию или исполнение.
- `harness77 catalog`: каталог имён и сигнатур из `1cv7Lang.als` и `1crcrus.dll` установленной платформы, с хешами источников; каталог 7.70.027 входит в пакет.
- `harness77 compiler-protocol`: импорт сохранённых ошибок Конфигуратора в JSON. Сохраняет повторы, сообщает о непригодном входе, не запускает 1С.
- `harness77 extract`: извлечение модуля ERT в новый UTF-8 файл.
- `harness77 build`: текст + шаблон → новая ERT, проверка текста и сохранности остальных потоков, хеши входов и результата. По умолчанию строгая CP1251.
- `harness77 run`: полный цикл по профилям проекта и стенда — статика → сборка → проверка платформой → тесты → общий отчёт. Новый `run_id` и каталог на запуск, связывание по хешам, сроки раздела 8.5, отмена по Ctrl+C. Короткий нативный цикл подтверждён; `simulation`-стенд проводит цикл без 1С. См. [пример](examples/full-cycle/README.md).

Параметры, схемы JSON, коды возврата и ограничения — в [контрактах](docs/contracts.md).
77MCP и его структурированные метаданные не входят в поставку или её приёмку.

В devtools также находятся публикация ККТ-релизов и каталоги ATOL/Штрих. Они принадлежат исходному набору инструментов и не входят в универсальное ядро будущего harness. Во время начального упорядочивания они не переделывались.

## Установка и быстрая проверка без 1С

Нужен Python 3.11+. Из корня репозитория:

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install .
.\.venv\Scripts\harness77 --version
.\.venv\Scripts\harness77 lint examples/hello.1s --format json
```

Ожидаются ноль диагностик и код `0`. Команда доступна также через
`python -m harness77` в окружении, где установлен пакет. После установки можно
перейти в другой каталог и передать абсолютные пути. На Linux используйте `.venv/bin`.

Импорт переносимого отрицательного примера:

```powershell
.\.venv\Scripts\harness77 compiler-protocol tests/fixtures/compiler_protocol77/p2.txt
```

Ожидаются семь диагностик, `status=failed` и код `1` — это ошибки сохранённого
протокола. Пустой протокол даёт `blocked`/2, а не успешную компиляцию.

Сборка из собственного шаблона (каталог результата должен существовать):

```powershell
.\.venv\Scripts\harness77 build --template C:/project/form.ert --source C:/project/module.1s --output C:/project/result.ert
.\.venv\Scripts\harness77 extract C:/project/result.ert --output C:/project/readback.txt
```

Обе команды требуют нового выходного файла. Сборка возвращает JSON с SHA-256
и проверками контейнера, `platform_checked=false`. Произвольные формы и
прикладные обработки в платформе этим не проверяются.

[Подготовка разработки](docs/development.md), [однокомандная проверка поставки](docs/testing.md).

## Данные и исследования

Локальная база теперь находится в `.local/bases/base-for-test`. Если она зарегистрирована в списке запуска 1С по прежнему пути, запись нужно перенастроить на новый путь. Регистрация базы и настройки установленной платформы этим упорядочиванием не менялись.

Состав базы сохранён целиком. Она пока не объявляется минимальным, обезличенным или неизменяемым тестовым эталоном. Сама база, исследовательские выгрузки и исходные журналы исключены из корневого Git.

Для эксперимента с платформой владелец указал использовать эту тестовую базу напрямую, без копирования и создания новых баз. Все прогоны используют один каталог базы; отдельно создаются только тестовые ERT и отчёты. Можно выбрать любого пользователя базы с пустым паролем.

Новые описания и скрипты исследований размещайте в тематическом каталоге `research`, данные исследований — в `.local/research`, локальные базы — в `.local/bases`. Производные результаты будущих запусков предназначены для `.artifacts`, а не для корня. Пока этот каталог не создаётся без необходимости.

## Следующий шаг

Первая фича — [разбор протокола ошибок 1С 7.7 в JSON](docs/tasks/001-compiler-protocol.md) — реализована. После ревью подтверждены P1/P2 (60/7 диагностик), 42 новых теста и 31 прежний тест линтера; 3 проверки symlink пропущены из-за прав Windows. Проверены короткий TEMP 8.3 и directory junction. Ревизия, чистый checkout и ограничения описаны в [отчёте приёмки](docs/tasks/001-compiler-protocol-acceptance.md); [скрипт приёмки](scripts/verify_compiler_protocol77.py) доступен в репозитории.

Эксперимент с настоящей 1С 7.7 [принят для указанного охвата](docs/tasks/002-platform77-acceptance.md): автоматические P00–P08 и сравнение четырёх ERT с Конфигуратором на тех же байтах. Подтверждены проверка модуля, невызванный код, контрольное значение 42, различение ошибок и тайм-аутов, восстановление и сохранность чужих сеансов. Прошли 105 переносимых тестов. Видимые формы, вся конфигурация и произвольные прикладные обработки остаются непроверенными.

Этап 3 — пакет, общий CLI и проверяемая сборка ERT — описан в
[задании](docs/tasks/003-package-cli.md) и [приёмке](docs/tasks/003-package-cli-acceptance.md).
Этап 4 — первый полный цикл `harness77 run` — описан в
[задании](docs/tasks/004-full-cycle.md) и [приёмке](docs/tasks/004-full-cycle-acceptance.md):
переносимые проверки и короткий нативный цикл пройдены, долгий прикладной
нативный отчёт остаётся отдельным прогоном владельца. Долгие расчёты раздела 8.5
реализованы и проверены переносимо.

Этап 5 начат с КУДиР как первого прикладного проекта: задача 005 —
[задание](docs/tasks/005-kudir-rules.md) и [приёмка](docs/tasks/005-kudir-rules-acceptance.md).
Каталог платформы и четыре правила из подтверждённых случаев КУДиР; уровни
установлены 34 нативными сеансами. Линтер совпал с 1С на 31 из 31 пробы и находит
все пять корневых строк P1, которые раньше пропускал; на OK1/OK2 новых ошибок нет.
