# harness77

Инструментарий для воспроизводимой разработки и проверки кода **1С 7.7**.

Цель проекта: исходники и контекст → статические проверки → сборка ERT → проверка настоящей платформой → тесты на выбранной тестовой базе → отчёт. Пакет `harness77` объединяет статический анализ, импорт ошибок Конфигуратора, извлечение модулей, проверяемую сборку новой ERT и полный цикл с проверкой настоящей платформой.

Куда двигаться дальше — в [короткой дорожной карте](docs/roadmap.md). Границы компонентов описаны в [начальной архитектуре](docs/architecture.md), выполненные переносы — в [журнале упорядочивания](docs/housekeeping.md). Подробный проект требований — [методологическое ТЗ](docs/restructuring-spec.md).

```text
    kudir/                  опыт КУДиР, прототипы и корпус примеров

  .local/

    configurations/reference/  снимок MD/DD для статического анализа
    research/76av/          локальные выгрузки и исторические отчёты 76.АВ
    maintenance/            снимок и проверки этого упорядочивания
```

`1cv77-devtools` и `77MCP` остаются самостоятельными репозиториями на прежних местах. Полезные модули devtools импортированы в пакет; [карта переноса](docs/migration.md) и [происхождение](docs/provenance.json) фиксируют ревизии и хеши. Исследование 76.АВ разделено на [скрипты](research/76av/README.md) и локальные данные; прежний `.diagnostics` полностью разобран.

Исходники внешних компонент для исследования платформы собраны в [third_party](third_party/README.md). Архивы и распакованные снимки находятся локально; в корневом Git сохраняются их происхождение, версии и контрольные суммы.

MD/DD перенесены из корня в `.local/configurations/reference`. Они совпадали с файлами базы при обследовании; это зафиксированный снимок для анализа, автоматической синхронизации с базой нет. Его происхождение и хеши записаны в локальном `manifest.json`. Не редактируйте обе копии как независимые версии одной конфигурации.

В корневом Git хранятся код пакета, тесты, документация и исследовательские скрипты. Для установки продукта достаточно корневого репозитория. Вложенные репозитории исключены из него, их истории сохранены; они нужны для работы с исходными инструментами и прежними исследованиями. [Манифест исходного состояния](docs/baseline.json) остаётся историческим снимком. Локальные данные восстанавливаются отдельно.

## Что уже можно использовать

- `harness77 lint`: частичный статический анализ текста, ERT и MD; JSON-диагностики. Имена встроенных функций и методов — из каталога платформы 7.70.027; правила L7708–L7711 (зарезервированные имена, лишние аргументы метода, длинная строка, необъявленная переменная) откалиброваны пробами на настоящей 1С; L7712–L7714 сверяют имена объектов конфигурации и их реквизиты в коде (`Перечисление.Вид.Значение`, `СоздатьОбъект("Справочник.Вид")`, `Спр.Реквизит`) с метаданными базы (`--metadata 1Cv7.MD`) и молчат внутри `Если`, проверяющего имя через `Метаданные`. Модули самого `1Cv7.MD` проверяются в контексте своего объекта (реквизиты документа или справочника, форма), формы — с областями своей таблицы. Когда известен и глобальный модуль конфигурации (модули самого `1Cv7.MD`, `--globals 1Cv7.MD`, `run` — глобальный модуль базы из `[build] metadata` или базы стенда), чтение необъявленного имени (L7711) — ошибка: 1С такой модуль не компилирует. Успех линтера не подтверждает компиляцию или исполнение.
- `harness77 catalog`: каталог имён и сигнатур из `1cv7Lang.als` и `1crcrus.dll` установленной платформы, с хешами источников; каталог 7.70.027 входит в пакет.
- `harness77 compiler-protocol`: импорт сохранённых ошибок Конфигуратора в JSON. Сохраняет повторы, сообщает о непригодном входе, не запускает 1С.
- `harness77 extract`: извлечение модуля ERT в новый UTF-8 файл.
- `harness77 build`: текст + шаблон → новая ERT, проверка текста и сохранности остальных потоков, хеши входов и результата. По умолчанию строгая CP1251. С `--form` собирает и форму по описанию, с `--metadata` сверяет виды полей справочников, документов и т. п. с метаданными целевой базы по именам: вид, которого там нет, — отказ.
- `harness77 form-extract`: описание формы ERT в JSON (схема 3) — подписи, координаты, формулы, идентификаторы, типы полей, в том числе ссылочные по имени (`Справочник.Контрагенты`); без правок пересобирается байт в байт. Поддержаны изменения свойств и новые элементы: кнопка, надпись, рамка группы, поле строки, числа, даты или ссылочного типа, флажок; остальное — явный отказ.
- `harness77 md-extract` и `md-build`: модули конфигурации `1Cv7.MD` в файлы по именам объектов (`ГлобальныйМодуль.1s`, `Документ/<Имя>/МодульДокумента.1s`, `…/Форма.1s` и т. д.) и обратно — новый `1Cv7.MD`, в котором заменены только изменённые модули, а метаданные и остальные потоки сохранены байт в байт; правка модуля, который шаблон изменил после извлечения, — отказ. Рядом с модулем формы лежит описание её диалога (`…/Форма.json`, как у `form-extract`): правка описания пересобирает диалог формы конфигурации — новые кнопки, надписи, поля (поле с именем реквизита объекта — поле этого реквизита), перенос и подписи; проверка в 1С — `run` с `[configuration]` и launcher форм (`form_object`).
- `harness77 visual`: визуальные тесты формы. `run` с разделом `[visual]` снимает форму в своей 1С (сразу после открытия и после нажатия кнопки) и сравнивает снимки с утверждёнными эталонами по пикселям вне масок; `visual approve` явно утверждает снимки запуска эталонами, `visual compare` сравнивает два PNG. Без эталона, при неустойчивом снимке или другой среде (DPI, тема, шрифты, локаль) сравнение блокируется.
- `harness77 run`: полный цикл по профилям проекта и стенда — статика → сборка → проверка платформой → тесты → общий отчёт. Новый `run_id` и каталог на запуск, связывание по хешам, сроки раздела 8.5, отмена по Ctrl+C или файлом (`--cancel-file`). Короткий нативный цикл подтверждён; `simulation`-стенд проводит цикл без 1С. См. [пример](examples/full-cycle/README.md). С `[configuration]` в профиле проекта `run` проверяет и изменённые модули `1Cv7.MD`: собирает конфигурацию, открывает в 1С копию базы стенда по зарегистрированному в списке баз пути (`[stand.base] copy_path`) и удаляет её после; ошибка компиляции изменённого модуля (глобального, документа при проведении, формы при открытии) — провал с файлом и строкой, база стенда не меняется.
- `harness77 mcp`: MCP-сервер на stdio для агентов (Claude Code и другие клиенты MCP). Инструменты `lint`, `compiler-protocol`, `triage`, `extract`, `form-extract`, `build`, `md-extract`, `md-build`, `run`, `visual-compare` — те же команды CLI с теми же ключами; ответ — код выхода и JSON операции, равные CLI. Подключение к Claude Code из каталога проекта: `claude mcp add harness77 -- python -m harness77 mcp`; в Windows PowerShell — `claude.cmd mcp add harness77 -- python -m harness77 mcp` (PowerShell не передаёт `--` в `claude.ps1`, и `claude` отвечает `unknown option '-m'`). Не выходите из клиента во время `run`: Claude Code снимает сервер вместе с его процессами, и своя 1С останавливается принудительно (см. [контракт](docs/contracts.md)).

Параметры, схемы JSON, коды возврата и ограничения — в [контрактах](docs/contracts.md).
77MCP и его структурированные метаданные не входят в поставку или её приёмку.

В devtools также находятся публикация ККТ-релизов и каталоги ATOL/Штрих. Они принадлежат исходному набору инструментов и не входят в универсальное ядро будущего harness. Во время начального упорядочивания они не переделывались.

## Установка и быстрая проверка без 1С

Нужен Python 3.11+. Из корня репозитория:

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install .
.\.venv\Scripts\harness77 --version
.\.venv\Scripts\harness77 lint examples/hello.1s --format json
```

Ожидаются ноль диагностик и код `0`. Команда доступна также через
`python -m harness77` в окружении, где установлен пакет. После установки можно
перейти в другой каталог и передать абсолютные пути. На Linux используйте `.venv/bin`.

Импорт переносимого отрицательного примера:

```powershell
.\.venv\Scripts\harness77 compiler-protocol tests/fixtures/compiler_protocol77/p2.txt
```

Ожидаются семь диагностик, `status=failed` и код `1` — это ошибки сохранённого
протокола. Пустой протокол даёт `blocked`/2, а не успешную компиляцию.

Разметка корня и каскада того же вида протокола:

```powershell
.\.venv\Scripts\harness77 triage tests/fixtures/compiler_protocol77/p1.txt --output C:/project/p1-triage.json
```

Ожидаются `status=failed`, код `1`, 60 диагностик, `complete=false`
и `compiled_through_line=311`: компиляция остановилась, строки ниже 1С не проверяла.
Корни — 63, 66, 304 (`high`) и 101, 107, 306, 307, 309 (`medium`). С модулем
(`--source` или `--ert`) строки 306–309 распознаются как следствие ошибки
заголовка 304, и корней остаётся пять.

Сборка из собственного шаблона (каталог результата должен существовать):

```powershell
.\.venv\Scripts\harness77 build --template C:/project/form.ert --source C:/project/module.1s --output C:/project/result.ert
.\.venv\Scripts\harness77 extract C:/project/result.ert --output C:/project/readback.txt
```

Обе команды требуют нового выходного файла. Сборка возвращает JSON с SHA-256
и проверками контейнера, `platform_checked=false`. Произвольные формы и
прикладные обработки в платформе этим не проверяются.

[Подготовка разработки](docs/development.md), [однокомандная проверка поставки](docs/testing.md).

## Данные и исследования

Локальная база теперь находится в `.local/bases/base-for-test`. Если она зарегистрирована в списке запуска 1С по прежнему пути, запись нужно перенастроить на новый путь. Регистрация базы и настройки установленной платформы этим упорядочиванием не менялись.

Состав базы сохранён целиком. Она пока не объявляется минимальным, обезличенным или неизменяемым тестовым эталоном. Сама база, исследовательские выгрузки и исходные журналы исключены из корневого Git.

Для эксперимента с платформой владелец указал использовать эту тестовую базу напрямую, без копирования и создания новых баз. Все прогоны используют один каталог базы; отдельно создаются только тестовые ERT и отчёты. Можно выбрать любого пользователя базы с пустым паролем.

Новые описания и скрипты исследований размещайте в тематическом каталоге `research`, данные исследований — в `.local/research`, локальные базы — в `.local/bases`. Производные результаты будущих запусков предназначены для `.artifacts`, а не для корня. Пока этот каталог не создаётся без необходимости.

## Следующий шаг

Первая фича — [разбор протокола ошибок 1С 7.7 в JSON](docs/tasks/001-compiler-protocol.md) — реализована. После ревью подтверждены P1/P2 (60/7 диагностик), 42 новых теста и 31 прежний тест линтера; 3 проверки symlink пропущены из-за прав Windows. Проверены короткий TEMP 8.3 и directory junction. Ревизия, чистый checkout и ограничения описаны в [отчёте приёмки](docs/tasks/001-compiler-protocol-acceptance.md); [скрипт приёмки](scripts/verify_compiler_protocol77.py) доступен в репозитории.

Эксперимент с настоящей 1С 7.7 [принят для указанного охвата](docs/tasks/002-platform77-acceptance.md): автоматические P00–P08 и сравнение четырёх ERT с Конфигуратором на тех же байтах. Подтверждены проверка модуля, невызванный код, контрольное значение 42, различение ошибок и тайм-аутов, восстановление и сохранность чужих сеансов. Прошли 105 переносимых тестов. Видимые формы, вся конфигурация и произвольные прикладные обработки остаются непроверенными.

Этап 3 — пакет, общий CLI и проверяемая сборка ERT — описан в
[задании](docs/tasks/003-package-cli.md) и [приёмке](docs/tasks/003-package-cli-acceptance.md).

[задании](docs/tasks/004-full-cycle.md) и [приёмке](docs/tasks/004-full-cycle-acceptance.md):
переносимые проверки и короткий нативный цикл пройдены, долгий прикладной
нативный отчёт выполнен позже в задаче 006. Долгие расчёты раздела 8.5
реализованы и проверены переносимо.

Этап 5 начат с КУДиР как первого прикладного проекта: задача 005 —

превышение срока и отмена останавливают только свою 1С и не публикуют пакет.

Задача 008 ([задание](docs/tasks/008-form-description.md),

в своей 1С.

Задача 009 ([задание](docs/tasks/009-protocol-root-cascade.md),
[приёмка](docs/tasks/009-protocol-root-cascade-acceptance.md)) — разметка
протокола компилятора: `harness77 triage` и `run` помечают каждую диагностику
как корень, каскад или ошибку связывания, по каталогу сообщений `1crcrus.dll`
и правилам, установленным 19 нативными пробами. На P1 КУДиР из 60 сообщений
корнями остаются пять, остановка компиляции на строке 311 видна в отчёте.

Задача 010 ([задание](docs/tasks/010-visual-form-tests.md),
[приёмка](docs/tasks/010-visual-form-tests-acceptance.md)) — визуальные тесты
формы: harness показывает скрытое главное окно своей 1С на своём рабочем столе,
снимает форму и сравнивает снимок с утверждённым эталоном. Нативно неизменённая
форма прошла дважды без единого отличающегося пикселя, сдвинутая и пропавшая
кнопка дали отказ с рамкой различий на её месте, отсутствие эталона и другая
среда заблокировали сравнение.

Задача 012 ([задание](docs/tasks/012-reference-fields.md),
[приёмка](docs/tasks/012-reference-fields-acceptance.md)) — поля ссылочных типов:
описание называет вид по имени (`Справочник.Контрагенты`, `Перечисление.Пол`,
`Счет.Основной`), сборка берёт номер из метаданных целевой базы. Проба показала,
что 1С ищет вид поля в копии метаданных внутри самой ERT, поэтому при необходимости
сборка кладёт туда метаданные базы. Нативно шесть полей показали значения базы,
а модуль получил их тип и вид.

Задача 013 ([задание](docs/tasks/013-kind-name-checks.md),
[приёмка](docs/tasks/013-kind-name-checks-acceptance.md)) — сверка видов по именам:
1С переводит номер поля в имя по копии метаданных внутри ERT и ищет вид по имени
в открытой базе. Поэтому номера внутри ERT сверяются с её копией, а целевая база —
по именам: другой номер того же вида больше не отказ, а вид, которого в базе нет
(поле молча потеряло бы вид), — отказ со списком таких видов. При замене копии
номера прежних полей переводятся по имени. Нативно шаблон другого выпуска
конфигурации («Тарифы» под 25507 против 26051 в базе) дал полям нужные виды и
с прежней копией, и с заменённой.

Задача 014 ([задание](docs/tasks/014-mcp-server.md),
[приёмка](docs/tasks/014-mcp-server-acceptance.md)) — MCP-сервер `harness77 mcp`:
операции CLI как инструменты агента с тем же результатом, что у командной строки.
Официальный клиент SDK получил на 13 вызовах ровно то же, что CLI; Claude Code
подключил сервер, и агент проверил модуль через `lint`; полный цикл с настоящей 1С
через MCP совпал с CLI, отмена и закрытие клиента во время расчёта останавливают свою
1С с очисткой; Esc в интерактивном Claude Code отменяет `run` так же.
